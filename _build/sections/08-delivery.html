Topic T5

Continuous safe delivery: build once, three ways back, code vs data

Tag an image by commit id, roll back by redeploying, reverting or flipping a flag, and write migrations that make rollback safe.

Mental model

The pipeline runs in a fixed order: Test, Build, Migrate, Deploy, Check health. Build the image once, tag it with the commit id, and promote that same image. When production breaks there are three ways back, fastest first: switch a flag off (seconds, no deploy), redeploy the previous image (about 1 minute, nothing is rebuilt), and revert the commit and run the pipeline again (minutes, permanent). All three bring back code. None of them brings back data: a renamed or dropped column, deleted rows or a sent email stay as they are. Code is reversible. Data is not. So migrations must only add (expand), and must never break the old code that is still running.

Build once, tag with the commit id

A tag like 2.4 is for people. The commit id says exactly which code is inside the image. Commit first, then build, so that the id names the code you built. Use one build with two -t, or one build followed by docker tag. Building twice can give a different image, which means production would get something that was never tested.

docker build --build-arg RELEASE=2.4 -t shop:2.4 -t shop:$(git rev-parse --short HEAD) .
  1. build an image from ./Dockerfile
  2. fills ARG RELEASE in the Dockerfile (an ENV RELEASE=${RELEASE} line keeps it in the image)
  3. first name: the human version
  4. second name: the shell runs git rev-parse --short HEAD first and puts its output (e.g. b7d70c4) here
  5. the build context. It is required.
CommandWhat it does
git rev-parse --short HEADprints the short commit id (7 characters)
docker tag shop:2.4 shop:b7d70c4adds a second name to the same image (no build)
docker image inspect -f '{{.Id}}' shop:2.4the full image id; both tags must print the same one
docker image ls shopboth rows show the same IMAGE ID
docker image rm shop:wrongtagremoves only that name, as long as another tag still points at the image
Trap

If you build before you commit, the "commit id" tag names the previous commit. Fix it by committing, adding the right tag with docker tag, and removing the wrong one with docker image rm.

Way back 1: redeploy the previous image

The old image still exists, and it was tested when it was built. Start a container from it with the same name, port and env. There is no test, build or migration step, which is why this takes about 1 minute. It only works if the database still fits the old code.

$ docker logs web                         # evidence: ERROR ... request: /checkout?customer=kabir&group=1
$ docker inspect -f '{{.Config.Env}}' web  # [STORE=pune PATH=... RELEASE=2.4]: copy only the -e you gave
$ docker port web                         # 3000/tcp -> 127.0.0.1:8402
$ docker rm -f web                        # frees the name AND the port
$ docker run -d --name web -p 127.0.0.1:8402:3000 -e STORE=pune shop:2.3
$ docker exec web wget -qO- http://localhost:3000/healthz     # no curl? ask from inside
{"status":"ok","version":"2.3","store":"pune"}
Conflict. The container name "/web" is already in use by container "3b1f..."

Means: the old container still exists, even if it is stopped.

Fix: run docker rm -f web first. Don't pick a new name or port, because users and the proxy know the old ones.

Trap

Don't copy RELEASE=2.4 into a -e. It comes from the image, and overriding it would make 2.3 report itself as 2.4. Don't rebuild 2.3 either: a rebuild is slower and may not give the image that was tested. Keep the 2.4 image so the developers can reproduce the bug. Quote URLs that contain &.

Way back 2: revert the commit (and ship it linearly)

git revert adds a new commit that undoes an old one. History only grows, so it is safe after a push, and the pipeline rebuilds from main. Use reset only for commits that were never pushed.

git revert --no-commit 7d02b1f
  1. undo that commit's diff
  2. stage the undo but don't commit yet, so you can choose the message
  3. the bad commit (from git log --oneline)
$ git revert --no-commit 7d02b1f
$ git commit -m "Roll back group orders"     # exact message from the task
$ git push
 ! [rejected]        main -> main (fetch first)  # a teammate pushed meanwhile
$ git pull --rebase                           # fetch + replay MY commit on top: no merge commit
$ git push
Trap

git revert -m "msg" is not "message". -m chooses a parent of a merge commit, and you get option `mainline' expects a number. A plain git revert --no-edit gives the message Revert "...", so if the task asks for a different message, use --no-commit + commit -m, or git commit --amend -m before you push. A plain git pull creates a merge commit, which gives the wrong commit count and a history that isn't linear (Quiz 3 Q9).

Tip

Q9 pattern: you have a local change and a teammate pushed. Do git add, git commit -m "exact message", git pull --rebase, then git push. If you already made a merge commit, run git reset --hard ORIG_HEAD before you push, then run pull --rebase.

Way back 3: the kill switch (feature flags)

A flag is an if whose condition lives outside the code: in a file, a database row or a flag service. If the app reads it on every request, a change applies on the next request, with no deploy and no restart. The buggy code stays in the image but is never reached.

# flags.json (edit in the Files panel, save, done: no restart)
{
  "group_order": { "rollout_percent": 0 },
  "new_menu": { "rollout_percent": 50 }
}
$ docker exec web cat /flags/flags.json       # the container sees the same (mounted) file
$ docker ps                                   # still "Up 10 minutes": same container, never restarted

In the lecture demo the flag is a database row: UPDATE flags SET enabled = false WHERE name = 'group_order';

Trap

Keep the file valid JSON: double quotes, numbers without quotes, and no trailing comma. Broken JSON breaks every request that reads it. Don't restart or re-create the container "to be safe": the task is graded on the container id and start time. If the app reads the flag only once at start-up, a change needs a restart, and then it is not a kill switch any more.

Percentage rollout: sha256 bucket, not random()

sha256("group_order:meena") first 4 bytes, big-endian % 100 < rollout_percent
  1. hash the flag name and the user, so each flag picks its own users
  2. turn the hash into a number from 0 to 4,294,967,295 (JS readUInt32BE(0), Python int.from_bytes(d[:4], "big"))
  3. the remainder gives the bucket, 0-99 (meena = 5, asha = 67)
  4. ON when the bucket is below the line. 0 = nobody (kill switch), 100 = everyone.
import hashlib

def bucket(flag, user):
    digest = hashlib.sha256(f"{flag}:{user}".encode()).digest()
    return int.from_bytes(digest[:4], "big") % 100

def is_enabled(flag, user, percent):
    return bucket(flag, user) < percent
  • Sticky: the same user always gets the same answer. With random() the button flickers on and off.
  • Monotonic: going 10 → 50 → 100 only moves the line, so nobody loses the feature.
  • Salted: with hash(user) alone, two flags at 10% hit the same 10% of users (978 of 978). With flag:user, about 1% of users get both (99).
Trap

Python's built-in hash() on strings changes on every run (it is randomised per process), so it isn't sticky. Use <, not <=: with <=, 0% still turns the flag on for bucket 0. Compare with percent, not percent/100.

Code vs data: the rename trap and expand/contract

The pipeline migrates before it deploys, so the old code is still serving while the migration runs. RENAME COLUMN items TO order_items breaks 2.3 straight away, and it stays broken after a rollback: /healthz says 2.3 is ok, but every checkout fails with column "items" does not exist. The only way out is forward, with a new migration that renames the column back.

-- V3__add_order_items.sql : EXPAND (additive only, old code unaffected)
ALTER TABLE orders ADD COLUMN order_items TEXT;
UPDATE orders SET order_items = items WHERE order_items IS NULL;   -- backfill
-- no RENAME, no DROP. Later releases: write both, read new, use only new,
-- then CONTRACT: ALTER TABLE orders DROP COLUMN items;   <- the irreversible point
Trap

Adding ADD COLUMN ... NOT NULL without a default fails on a table that has rows (SQLite: Cannot add a NOT NULL column with default value NULL), and it would break the old code's inserts. Make the new column nullable.

An applied migration was edited (Quiz 3 Q10: checksum mismatch for migration version 02): put the file back to exactly what production ran, as its own commit. Don't write a migration for the edit.

$ git log --oneline -- migrations/V2__add_group_id.sql
$ git restore --source=<production commit> migrations/V2__add_group_id.sql
$ git add migrations/V2__add_group_id.sql
$ git commit -m "Restore V2 to production version"
Drill Two tags, one image

You committed "Release 2.6". Build tiffingo:2.6 and tiffingo:<short id> with RELEASE=2.6, as one image.

Show answer
docker build --build-arg RELEASE=2.6 -t tiffingo:2.6 -t tiffingo:$(git rev-parse --short HEAD) .
docker image ls tiffingo      # same IMAGE ID twice

One build gives one image id. The commit-id tag tells you exactly which code is running.

Quiz-style Roll back, keep the config

app runs app:2.4 with -p 8080:3000 -e DB_URL=... and fails. Roll back to app:2.3 with the same name and port. Don't rebuild.

Show answer
docker inspect -f '{{.Config.Env}}' app     # copy DB_URL
docker rm -f app
docker run -d --name app -p 8080:3000 -e DB_URL=... app:2.3

Settings belong to the container, not the image, so read them before you remove it.

Quiz-style Revert with a message, teammate pushed first

Undo the pushed commit "Add coupons" with message Remove coupons. Push. History must be linear, and you must not force-push.

Show answer
git revert --no-commit <hash>
git commit -m "Remove coupons"
git push                 # rejected (fetch first)
git pull --rebase
git push

Don't use -m on revert. Don't use plain pull, because it makes a merge commit.

Quiz-style Which way back?

"Split the bill" (behind a flag) charges the wrong friend. The rest of 2.5 is fine. What is the fastest fix?

Show answer

Switch the flag off (rollout 0, or enabled = false). It takes seconds, there is no deploy, and everything else in 2.5 keeps running. Redeploying 2.4 would also remove the good parts of 2.5.

Twist Healthy but 100% failing

After you roll back to 2.3, /healthz says ok, 2.3, yet every checkout fails with column "items" does not exist. Why, and what is the fix?

Show answer

The 2.4 migration renamed the column. The rollback restored the code but not the schema, and the health check only runs SELECT 1. To fix it forward, add a new migration: ALTER TABLE orders RENAME COLUMN order_items TO items;. Next time, use expand: add order_items, backfill it, and keep items.

Practice labs

Cheat sheet

  • Test → Build → Migrate → Deploy → Check health the pipeline order; one failure stops it
  • docker build --build-arg RELEASE=2.4 -t x:2.4 -t x:$(git rev-parse --short HEAD) . build once, two tags
  • docker tag x:2.4 x:abc1234 add a name, no build
  • docker image inspect -f '{{.Id}}' x:2.4 compare image ids
  • docker inspect -f '{{.Config.Env}}' web / docker port web read settings before removing
  • docker rm -f web && docker run -d --name web -p H:C -e K=V x:2.3 redeploy the previous image
  • docker exec web wget -qO- "http://localhost:3000/healthz" test from inside, with no curl
  • git revert --no-commit <hash> + git commit -m "..." revert with your own message
  • git pull --rebase after a rejected push: linear, no merge commit
  • git restore --source=<hash> path put a file back to an old version, then commit
  • flags file / UPDATE flags SET enabled=false kill switch: seconds, no deploy, no restart
  • sha256(f"{flag}:{user}")[:4] big-endian % 100 < percent sticky percentage rollout
  • ADD COLUMN new TEXT; UPDATE t SET new = old; expand + backfill. Never RENAME or DROP while old code runs.
  • Flag off (seconds) < redeploy image (~1 min) < revert + pipeline (minutes). None of them undoes data.
