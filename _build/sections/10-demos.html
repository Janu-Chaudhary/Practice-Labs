Lecture demos

T5 demos: deploy, break, go back, flag, roll out

Run the professor's two T5 demos yourself, predict every output, and tie each moment to the slide idea it proves.

Mental model

A pipeline is a row of gates: Test → Build → Migrate → Deploy → Check health → Switch. Any gate fails, the pipeline stops and production is unchanged. Every build is an image tagged twice (version + content id), so going back = start an old image again. That is fast, but it only changes code. The database stays as the last migration left it. So a migration must keep the old code working (add, don't rename or drop). And a flag is an if whose condition lives in the database or a file: flipping it changes behaviour on the next request, with no deploy. A percentage rollout puts each user in a fixed bucket sha256(flag:user) % 100. The user is ON if their bucket is < percent.

Step 9 · The only way out is forward

$ docker exec t5-db psql -U postgres -c 'ALTER TABLE orders RENAME COLUMN order_items TO items;'
ALTER TABLE
# terminal 2 recovers on the next request
18:47:06  ok     order #292  Rs 240  single  (v2.3)

Notice: the fix is a new change to the database (fix forward), not a rollback. Done safely, it would have been expand/contract. First ADD COLUMN order_items, then write both columns, backfill, read the new one. DROP COLUMN items comes last, and that is the irreversible step.

Trap

This manual ALTER is not recorded in schema_migrations (it still lists 2.4-rename as applied). In a real team, write it as the next migration file so every database gets it.

"A flag is an if-statement whose condition lives outside the code." Kill switch = the fastest way back, seconds. "Read on every request: changes land at once, but every request hits the database." The slide-17 poll answer: C, switch the flag off.

Demo 2 (slide 19): percentage rollout with sticky buckets

Each step runs docker run --rm -v "$PWD":/demo -w /demo node:22-alpine node rollout.js <cmd>. If you have Node, node rollout.js <cmd> gives the same output.

sha256("group_order:" + user) .readUInt32BE(0) % 100 < rollout_percent
  1. hash the flag name and the user id together (same input → same hash, always)
  2. first 4 bytes as a number, 0 to 4,294,967,295
  3. remainder → bucket 0..99
  4. ON if the bucket is below the percentage read from flags.json (on every call)

Steps 4–5 · Is it fair?

$ node rollout.js spread
Smallest bucket: 72 users (-28% from average). Largest: 133 (+33%). Average: 100.

Notice: single buckets wobble, but ten together come out close to 10%, and closer with more users. It is about 10%, never exactly.

Step 6 · Why not Math.random()? (three runs; the random row changes every run)

$ node rollout.js random asha
Math.random() < 0.10:               off off off off off off ON  off off off

Math.random() < 0.10:               off off ON  off ON  off ON  off off off

Notice: with random() asha's button appears and disappears. The hash gives the same answer every time.

Step 9 · Why the flag name is inside the hash

$ node rollout.js overlap
hash(flag name + user id):  group_order 1005, new_menu 1016, in both: 99
hash(user id) only:         group_order 978, new_menu 978, in both: 978
Without the flag name, the same 1,000 people test every new feature.
Slide idea

"Percentage rollout uses hash(user_id) % 100 < 10, not random() < 0.1." Deterministic means sticky. A higher percentage only adds users. Salting with the flag name gives each flag an independent 10% (overlap ≈ 10% × 10% = 1%).

Practice labs

Cheat sheet

  • ./preflight.sh smoke pull images, pre-build, check 8080, test once
  • ./setup.sh network tiffingo + t5-db + t5-proxy on :8080
  • ./deploy.sh 2.4 Test → Build (2 tags) → Migrate → Deploy beside old → Health → Switch
  • ./rollback.sh 2.3 start old image → health → switch. No test, build or migrate. DB untouched.
  • ./flag.sh on|off = UPDATE flags SET enabled = … WHERE name = 'group_order';
  • curl -s localhost:8080/healthz version + SELECT 1 only
  • docker images tiffingo same IMAGE ID for :2.3 and :cdf64da
  • docker exec t5-db psql -U postgres -c '\d orders' see the real columns
  • docker exec t5-db psql -U postgres -c 'ALTER TABLE orders RENAME COLUMN order_items TO items;' fix forward
  • Safe while old code runs: ADD COLUMN (nullable), CREATE TABLE. Unsafe: RENAME, DROP.
  • Expand/contract: add new → write both → backfill → read new → stop using old → DROP old (irreversible)
  • Three ways back: revert + pipeline (minutes) · redeploy previous image (~1 min) · flag off (seconds)
  • bucket = sha256(flag + ":" + user)[0..4] % 100, ON if bucket < percent
  • Raise the percent → nobody turns off. 0% = kill switch. Flag name in the hash → independent groups.
  • ./reset-all.sh remove everything the demos created
