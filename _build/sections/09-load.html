Topic 9

Surviving: the database under load (RailBook Tatkal)

Count and remove N+1 queries, pick the right composite index and prove it with EXPLAIN, size connection pools with the formula, and fix the last-seat race with one conditional UPDATE, all checked with pytest.

Mental model

At 10:00 Tatkal opens and thousands of requests hit one database. Four things break, in this order of "where the time goes": round trips (too many queries: N+1), finding rows (no usable index: full SCAN), connections (each pool holds real Postgres processes; they multiply with servers; #101 is refused), and the last seat (check-then-act: two requests read 99 before either writes). Each has a measurable symptom (query count, plan line, connection total, booked > capacity) and that symptom is what a test asserts.

N+1: count the round trips

One query for a list, then one more query per row. N rows = N+1 queries. Each query may be fast; the cost is round trips x latency. Laptop: DB 1 ms away, 51 x 1 ms = 51 ms (nobody notices). Production: DB 30 ms away, 51 x 30 ms = 1,530 ms ≈ 1.5 s.

# the warning sign: a query INSIDE a loop
rows = conn.execute("SELECT id, pnr, train_id FROM bookings WHERE user_id = ?", (uid,)).fetchall()   # 1
for booking_id, pnr, train_id in rows:
    train = conn.execute("SELECT train_no FROM trains WHERE id = ?", (train_id,)).fetchone()     # + N

# the fix: ONE trip with a JOIN
conn.execute("SELECT b.pnr, t.train_no FROM bookings b JOIN trains t ON t.id = b.train_id "
             "WHERE b.user_id = ? ORDER BY b.id", (uid,))

Counting queries in a test (sqlite3): conn.set_trace_callback(f) makes sqlite call f(sql) once per statement it runs.

Trap

With a JOIN, SELECT * returns columns of both tables, so row[1] is not what it was. Name the columns. And an inner JOIN drops parents with no children: use LEFT JOIN + count(b.id) (not count(*), which counts the NULL row as 1).

Indexes, the leading column, and reading the plan

No index: the database reads every row (Seq Scan in Postgres, SCAN in sqlite). An index is a sorted copy of some columns with pointers to the rows (a B-tree): a handful of steps even among crores of rows. A composite index is sorted by the first column, then by the second inside each first value: the phone-book rule.

CREATE INDEX idx_trains_station_date ON trains (from_station, journey_date);
  1. make a B-tree index (plain = blocks writes while building)
  2. its name (you will see it in the plan)
  3. which table
  4. column order matters: leading column first = the one you ALWAYS filter on
Query on (from_station, journey_date)Uses the index?
WHERE from_station = 'PUNE'yes (leading column)
WHERE from_station = 'PUNE' AND journey_date = '2026-11-14'yes (order in the WHERE does not matter)
WHERE journey_date = '2026-11-14'no (second column alone)
WHERE train_no = '12124'no (not in the index)

Read the plan. sqlite: EXPLAIN QUERY PLAN <query> (from Python: conn.execute("EXPLAIN QUERY PLAN " + sql, params), column 3 is the text). Postgres: EXPLAIN / EXPLAIN ANALYZE (really runs it, shows times).

Trap

Indexes are not free: every INSERT/UPDATE updates every index, and they use disk. Index the queries you run often; don't index every column. And a correct index can be correctly ignored: if the query returns a big share of the table, a Seq Scan is cheaper.

Tip

Join columns (foreign keys like bookings.train_id) are the classic missing index. Postgres indexes primary keys and UNIQUE columns for you, not foreign keys.

Why a new migration file

Add the index as migrations/02_....sql, never by editing 01_...: production already applied 01 (Flyway would refuse the changed checksum). On a live Postgres table use CREATE INDEX CONCURRENTLY: writes continue, but it builds slower and cannot run inside a transaction (plain CREATE INDEX blocks writes, not reads).

Connections and pool math

A Postgres connection is a separate server process with its own memory, so there is a hard cap: max_connections (default 100). A pool keeps up to pool_size connections open per app process. Every server brings its own pool, so connections multiply when you scale out. Connection 101 is refused:

FATAL:  sorry, too many clients already

Means: the total of all pools + other clients went over max_connections. Postgres does not queue it.

Fix: size pools on purpose, add a pool wait timeout, leave autoscaler headroom, or put a pooler (PgBouncer / Supavisor) in front.

# the formula: count EVERY client at the WORST case
servers_max x pool_size + other pools (workers, cron) + humans  <=  max_connections - spare

8 x 10 + 5 = 85  <= 100 - 10 = 90    OK
8 x 14 + 5 = 117 >  90                OVER  (fits at 6 servers: 6 x 14 + 5 = 89, breaks when the autoscaler adds 2)
8 x 11 + 5 = 93  >  90                OVER  (forgot the spare)
200 serverless x 5 = 1000             10x over -> a pooler, not a bigger limit

Trap

"Scale out the app servers" makes the DB problem worse (more pools). "90% busy is fine" is wrong: queues explode near 100% (wait ~ ρ/(1−ρ): 1 at 50%, 9 at 90%, 99 at 99%).

The last seat: check-then-act and its fixes

booked = 99, capacity = 100. Two requests both read 99, both decide "seat free", both write: 2 bookings for 1 seat. Unit tests pass because they send one request at a time.

# BUG: two statements, a gap between them
booked, capacity = conn.execute("SELECT booked, capacity FROM trains WHERE id = ?", (tid,)).fetchone()
if booked >= capacity: return 409
#   <- the other request runs here
conn.execute("UPDATE trains SET booked = booked + 1 WHERE id = ?", (tid,))

# FIX 1: check AND act in one statement
cur = conn.execute("UPDATE trains SET booked = booked + 1 WHERE id = ? AND booked < capacity", (tid,))
conn.commit()
return 409 if cur.rowcount == 0 else 201       # Postgres: ... RETURNING booked; 0 rows = full
ApproachStops the oversell?Notes
Fix 1: UPDATE ... WHERE booked < capacityyessimplest; 1 row = seat, 0 rows = 409 Conflict
Fix 2: BEGIN; SELECT ... FOR UPDATE; ...; COMMIT;yeslocks that row (not the table); others wait; for multi-statement logic
Fix 3: CHECK (booked <= capacity), UNIQUE (train_id, seat_no)yes (as an error)safety net: turns an oversell into an error (500), not a friendly 409

Testing a race without luck. Real threads make a flaky test. Instead, put a hook in the gap (pause()) and let the test run user B inside it. Same interleaving every run:

def test_last_seat_two_users():
    conn = make_db(capacity=100, booked=99)
    results = two_users_at_once(conn, 1)     # B runs inside A's pause()
    assert sorted(results) == [201, 409]
    assert booked(conn) == 100

$ pytest
E   assert [201, 201] == [201, 409]          # before the fix: both got the seat
Trap

WHERE booked <= capacity lets 100 become 101: it must be <. In sqlite you put a CHECK in CREATE TABLE; in Postgres: ALTER TABLE trains ADD CONSTRAINT booked_le_capacity CHECK (booked <= capacity);

Show answer

Quiz-style 12 servers, pool 8, plus a cron job

max_connections = 100. 12 app servers with pool 8, a cron job with pool 5. What happens at peak? With 10 spare and up to 9 servers and no cron job, what is the largest pool?

Show answer

Quiz-style "We wrapped it in a transaction and still oversold"

The code does BEGIN; SELECT count(*) FROM bookings WHERE train_id = 1; -- if < capacity: INSERT ...; COMMIT;. 10 requests at once for the last seat: 3 succeed. Why, and give two fixes plus a safety net.

Show answer
-- why: all 10 read the same count before any of them inserted (a transaction is not a lock)
-- fix 1
UPDATE trains SET booked = booked + 1 WHERE id = 1 AND booked < capacity RETURNING booked;  -- 0 rows -> 409
-- fix 2
BEGIN; SELECT capacity FROM trains WHERE id = 1 FOR UPDATE; SELECT count(*) ...; INSERT ...; COMMIT;
-- safety net
ALTER TABLE trains ADD CONSTRAINT booked_le_capacity CHECK (booked <= capacity);
ALTER TABLE bookings ADD CONSTRAINT uniq_seat UNIQUE (train_id, seat_no);

A full train is an expected outcome: 409 Conflict, not 500.

Practice labs

Cheat sheet

  • N+1 1 list query + 1 per row; cost = queries x latency (51 x 30 ms ≈ 1.5 s)
  • JOIN / WHERE id IN (...) / = ANY($1) fix N+1 (1-2 queries); an index does not
  • conn.set_trace_callback(list.append) count sqlite statements in a test
  • LEFT JOIN ... count(b.id) keep parents with 0 children, count them as 0
  • CREATE INDEX idx ON t (always_filtered, sometimes_filtered); leading column first
  • (a, b) helps a and a + b; not b alone
  • EXPLAIN QUERY PLAN sql sqlite: SCAN = full read, SEARCH ... USING INDEX = lookup
  • EXPLAIN ANALYZE sql Postgres: Seq Scan vs Index Scan + Index Cond, real times
  • CREATE INDEX CONCURRENTLY no write blocking, slower, never inside BEGIN/COMMIT
  • every index slows every INSERT/UPDATE; index join (foreign key) columns
  • servers_max x pool + other clients <= max_connections - spare (default limit 100)
  • FATAL: sorry, too many clients already = over the limit; refused, not queued
  • pool wait timeout: bounded wait for a free connection (0 = fail at once)
  • pooler (PgBouncer, Supavisor): transaction mode shares more, loses prepared statements / session locks
  • UPDATE ... SET booked = booked + 1 WHERE id = ? AND booked < capacity; rowcount == 0 → 409
  • SELECT ... FOR UPDATE inside BEGIN/COMMIT locks the row; others wait
  • CHECK (booked <= capacity), UNIQUE (train_id, seat_no) = safety net, not the fix
  • BEGIN/COMMIT around check-then-insert does not stop overselling
