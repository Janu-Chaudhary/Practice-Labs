Topic 5

Testing with pytest, the failing-test-then-fix workflow, and reading CI config

Run and select tests, write boundary tests that catch real bugs, commit "failing test" then "fix" in exactly the right order, undo a wrong commit, and read a GitHub Actions workflow.

Mental model

A test is a claim you can run: set up (Arrange), call the code (Act), check the result (Assert). No assert = no claim. A bug fix is two commits: commit 1 adds a test that is red on the old code (proof the bug exists), commit 2 is the smallest change that makes it green. The grader looks at those commits by position: HEAD~1 = your test commit, HEAD = your fix. CI just reruns the same tests on a clean machine; branch protection is what turns a red CI run into a blocked merge.

The vocabulary (what the MCQs ask)

These words come straight from the T2L2 slides. Know each one in one sentence.

WordMeaning
Arrange-Act-AssertThe shape of every test: set up the world, do the thing, check the claim.
Test case / suite / runnerOne scenario / a named group of cases / the program that runs them and reports (pytest).
AssertionStates the expected outcome and fails loudly if wrong. Code without one only proves "it did not crash".

Integration testSeveral real parts together: route + validation + database. E.g. duplicate-email check against a real table; POST /api/login returns an error.

Testing pyramidMany unit, some integration, few E2E. A budget, not a law.

StubReturns a fixed, canned value in place of a real dependency.
FakeA working but simplified implementation, e.g. an in-memory database.

Trap

"100% coverage" does not mean the code is tested. A test that calls signup and asserts True covers every line and checks nothing. Quiz 2 Q2: a Mock test proves save was called, not that the response was 201; an in-memory fake + asserting 201 and the stored user checks the behaviour.

Running pytest and reading its output

pytest looks in the current folder (and subfolders) for files named test_*.py or *_test.py, and inside them runs every function whose name starts with test_. Always run it from the project folder (where the files are).

pytest -v -k "password and not short" test_users.py
  1. the test runner
  2. -v = verbose: one line per test with PASSED/FAILED
  3. -k = keep only tests whose name matches this expression (and / or / not; quote it)
  4. optional: which file (or folder) to run; default is everything
CommandWhat it does
pytestrun all tests; one character per test: . pass, F fail, E error (crash before/outside the assert, e.g. import error)
pytest -qquiet: less header, short summary
pytest -vverbose: full name + result for every test
pytest -xstop at the first failure (fast feedback)
pytest -k emailonly tests with "email" in the name (case-insensitive)
pytest test_validate.pyonly that file
pytest test_validate.py::test_accepts_exactly_eight_charactersonly that one test (its "node id", copy it from the FAILED line)
pytest -sshow print() output (normally hidden for passing tests)
pytest --lfrerun only the tests that failed last time

Tip

In assert X == Y pytest prints the evaluated values in the same order: assert 190 == 180 means the code gave 190 and the test expected 180. The + where line tells you which call produced the value.

ERROR: file or directory not found: and

Means: you wrote pytest -k password and not short without quotes; the shell split it and pytest thinks and is a file.

Fix: pytest -k "password and not short"

ERROR: file or directory not found: test_password_too_short

Means: a bare test name is treated as a path.

Fix: pytest test_users.py::test_password_too_short or pytest -k test_password_too_short.

ModuleNotFoundError: No module named 'validate'

Means: pytest was run from the wrong folder, or the import name doesn't match the file name.

Fix: cd into the folder that holds validate.py and run pytest there. In tests: from validate import is_valid_length (file name without .py).

no tests ran in 0.00s

Means: exit code 5: nothing collected. The file isn't named test_*.py, the function doesn't start with test_, or -k matched nothing.

Fix: rename, or check the -k word.

Writing tests: assert, boundaries, pytest.raises

A pytest test is just a function named test_... that uses plain assert. Name it like a specification: the name should say what broke when it goes red.

# test_validate.py
import pytest
from validate import is_valid_length

def test_accepts_exactly_eight_characters():   # boundary, at the limit
    # Arrange
    password = "abcdefgh"
    # Act
    result = is_valid_length(password)
    # Assert
    assert result is True

def test_rejects_seven_characters():           # boundary, one below
    assert is_valid_length("abcdefg") is False

def test_none_is_rejected():                   # invalid input -> must raise
    with pytest.raises(TypeError):
        is_valid_length(None)
with pytest.raises(ValueError): is_adult(-1)
  1. passes only if the indented block raises ValueError (or a subclass); otherwise the test fails with DID NOT RAISE
  2. the call that should blow up goes inside the block

Which values to test for a rule "at least N": N-1 (last bad), N (first good), one normal value, one invalid input. 3 and 20 are useless for the edge: they give the same answer for >= 8, > 8 and >= 7.

Bug (mutant) in the codeTest that catches (kills) it
len(pw) > 8 instead of >= 8exactly 8 chars must be accepted
len(pw) >= 7exactly 7 chars must be rejected
len(pw) >= 9exactly 8 chars must be accepted
Trap

A test with no assert always passes unless the code crashes:

def test_ten_percent_off_200():
    result = apply_discount(200, 10)
    print("result is", result)      # green, even though result is 190, not 180

Also weak: assert result (any non-zero number passes) and assert status != 201 (a 500 passes). Assert the exact value.

Trap

Two test functions with the same name in one file: Python keeps only the last one, so the first test silently disappears. pytest -v shows the real list.

Failed: DID NOT RAISE <class 'ValueError'>

Means: the code inside with pytest.raises(...) returned normally.

Fix: either the code has a bug (good, you found it) or you put the wrong call / wrong exception type in the block.

NameError: name 'pytest' is not defined

Fix: add import pytest at the top of the test file (only needed for pytest.raises etc.; plain asserts don't need it).

Failing test, then fix: exactly two commits

This is quiz 2 Q16 (5 marks) and Milestone 1. The checks look at commit positions: HEAD~1 must contain the new test and the old code; HEAD has the fix. So the order and the "only one file per commit" rule matter.

$ cat validate.py                     # find the bug first: len(password) > 8
$ pytest                              # 2 passed: existing tests miss the edge
$ code test_validate.py               # add test_accepts_exactly_eight_characters, save
$ pytest                              # 1 failed, 2 passed  -> RED is what you want now
$ git status --short
 M test_validate.py
$ git add test_validate.py            # ONLY the test file
$ git commit -m "Add failing test for 8-character password"
$ code validate.py                    # > 8   becomes   >= 8
$ pytest                              # 3 passed -> GREEN
$ git add validate.py
$ git commit -m "Fix password length check to accept 8 characters"
$ git log --oneline
c3d4e5f (HEAD -> main) Fix password length check to accept 8 characters
a1b2c3d Add failing test for 8-character password
b8b4933 Add password length check

Check yourself the way the grader does:

CommandWhat it shows
git log --onelinenumber of commits and their order (newest on top)
git show --stat HEAD~1which files the test commit changed (should be only the test file)
git show HEAD~1:validate.pythe file as it was in that commit (must still have the bug)
git log -1 --format=%s HEAD~1that commit's message (must contain "failing test")
git diff HEAD~1 HEADwhat the fix commit changed
Trap

git add . or git commit -am "..." after you already touched validate.py puts the fix into the "failing test" commit. Then HEAD~1:validate.py is no longer the original and the test never failed in history. Always git status before committing and add the one file by name.

Why

The red commit is evidence the bug existed and that your test can see it. If you fix first, you never saw the test fail, so you don't know it can fail. Six months later, the test is what stops the bug coming back (regression).

Tip

The labs ignore __pycache__/ and .pytest_cache/ with a .gitignore. In the quiz, if git status shows those folders as untracked, just don't add them: add your file by name.

Undo: reset --soft, --amend, and what not to use

Made an extra commit, or committed the wrong thing? Nothing pushed yet = you can safely rewrite your local history.

git reset --soft HEAD~1
  1. move the current branch pointer
  2. --soft = keep the changes from the undone commit, still staged
  3. to one commit before HEAD (the commit is removed from the branch)
CommandCommitYour changes end up
git reset --soft HEAD~1removedstaged (ready to commit again)
git reset HEAD~1 (= --mixed)removedin the files, unstaged
git reset --hard HEAD~1removeddeleted - careful
git revert HEADkept, plus a NEW commit that undoes it-- (adds a commit: wrong when the count must be exact)
git commit --amend -m "msg"last commit replaced (new ID)whatever is staged is added into it
git restore --staged f--f unstaged, content kept
git restore f--f's unstaged edits thrown away
# Q16 gone wrong: you committed a typo fix as a 3rd commit. Fold it into the fix commit:
$ git reset --soft HEAD~1         # 3rd commit gone, its change is staged
$ git commit --amend --no-edit    # add the staged change into the fix commit, keep its message
$ git log --oneline               # back to exactly 2 new commits

# Wrong message on the last commit (e.g. forgot "failing test"):
$ git commit --amend -m "Add failing test for 8-character password"
Trap

--amend always changes the last commit. If you already made the fix commit, amending to fix the test commit's message would rewrite the fix instead. Then: git reset --soft HEAD~1 (fix changes now staged), git stash, amend the test commit, git stash pop, commit the fix again. Easier: check the message before the second commit. git commit with no -m (and --amend without -m/--no-edit) opens an editor; in nano save with Ctrl+O, Enter, Ctrl+X.

Trap

Never amend or reset commits you already pushed to a shared branch: everyone else's history stops matching. The quiz says "Don't push", so local rewriting is fine.

Coverage (concept + command)

Coverage needs the pytest-cov plugin. It is not installed on this machine, so the labs don't use it; know the command and how to read it.

$ pip install pytest-cov
$ pytest --cov=. --cov-report=term-missing
Name          Stmts   Miss  Cover   Missing
-------------------------------------------
validate.py       2      0   100%
# 100% = every line RAN during the tests. It says nothing about whether the result was asserted.
# --cov-branch adds branch coverage (were both sides of each if taken?)
Why

The slides' example: a signup test that posts a user and asserts True gives 100% coverage of the route, but the route could return 500 and the test would still pass. Mutation testing is the stronger signal: it checks that the tests would notice a change.

Reading a GitHub Actions workflow

A workflow is a YAML file in .github/workflows/. GitHub runs it on a fresh, clean machine ("runner") when the events under on: happen. Any step that exits non-zero (pytest exit code 1) fails the job: a red X.

name: CI
on:                            # WHEN to run
  push:
    branches: [main]           # after commits land on main
  pull_request:
    branches: [main]           # on every PR that targets main -> the PR shows a check
jobs:
  test:                        # job id - this name shows up as the status check
    runs-on: ubuntu-latest     # fresh VM each run
    steps:                     # run in order; first failure stops the job
      - uses: actions/checkout@v4          # get the repo code
      - uses: actions/setup-python@v5      # install a runtime
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: pytest -q                     # exit code 1 -> job red
KeyMeaning
on: push: branches: [main]runs only after code is already on main. Too late to stop a bad merge.
on: pull_request: branches: [main]runs on PRs into main, so reviewers see green/red before merging
jobs: / steps:jobs run in parallel on separate machines; steps run in order inside one job
uses: vs run:use a ready-made action / run a shell command
continue-on-error: truea failing step counts as success: hides red tests. Remove it.
services:a throw-away container (e.g. test database) for this job only; same level as steps:
env:environment variables for a step, e.g. a test-only DATABASE_URL
Trap

Required status checks are a GitHub setting, not YAML. Repo Settings -> Branches (branch protection rule) or Rules -> Rulesets -> "Require status checks to pass" -> pick the job (e.g. test). Quiz 2 Q3: to block merging a PR with failing tests you need BOTH the pull_request trigger (so the check runs on the PR) AND the required check (so red blocks the merge). Without the trigger, a required check never reports and every PR waits. Without the rule, red is only a warning. continue-on-error and "ask people in the README" are wrong answers.

Trap

YAML indentation is spaces only, and siblings must line up. pull_request: indented under push: becomes a setting of push, not a second trigger. A tab character = parse error. Quick local syntax check: python3 -c "import yaml; print(yaml.safe_load(open('.github/workflows/ci.yml')))". (Fun fact: PyYAML prints the key on as True, because YAML 1.1 reads bare on as a boolean. GitHub reads it correctly.)

Tip

Debugging a red CI run: read the first meaningful error, find which step/command failed, run that same command locally, fix, push again. "Works on my machine" failures usually mean something was installed on your laptop but not declared in requirements/lockfile.

Drill Which test failed, and what did the code return?

pytest ends with FAILED test_cart.py::test_total_with_tax_adds_15_percent - assert 15.0 == 115.0. Which value came from the code, and how do you rerun only this test? What does echo $? print?

Show answer
$ pytest test_cart.py::test_total_with_tax_adds_15_percent
$ echo $?
1

The test is assert total_with_tax([100]) == 115.0, so the left value 15.0 is what the code returned (it multiplied by 0.15 instead of 1.15). Exit code 1 = tests failed.

Drill Pick the boundary tests

Rule: "free shipping for orders of 50 or more". The code says if total > 50. Existing tests use 10 and 120. Which two totals should you add, and which one fails today?

Show answer
def test_order_of_exactly_50_ships_free():
    assert shipping_cost(50) == 0        # fails today (code says 5)

def test_order_just_under_50_pays():
    assert shipping_cost(49.99) == 5     # passes; guards the other side

Test the last value on each side of the edge. 10 and 120 can't tell > from >=.

Quiz-style Duplicate email returns 201

signup(repo, email) returns 201 for a second signup with the same email; it should return 409. Tests use FakeUserRepo, an in-memory fake. Write the failing test and the fix as two commits. Why not use Mock() for the repo?

Show answer
def test_signup_rejects_duplicate_email():
    repo = FakeUserRepo()
    signup(repo, "user@example.com")
    status = signup(repo, "user@example.com")
    assert status == 409
    assert repo.count() == 1
$ pytest ; git add test_signup.py ; git commit -m "Add failing test for duplicate email signup"
# signup.py, before repo.save(email):
    if repo.find(email) is not None:
        return 409
$ pytest ; git add signup.py ; git commit -m "Return 409 for duplicate email"

A Mock stores nothing, so find never sees the first user; you could only assert "save was called". The fake really stores users, so the test checks the behaviour.

Quiz-style Oops, a third commit

You finished Q16 and then ran git add . && git commit -m wip, which committed notes.txt and a debug print. The check needs exactly 3 commits. Remove the wip commit, keep notes.txt on disk (untracked), drop the debug print.

Show answer
$ git reset --soft HEAD~1                  # wip commit gone, its changes staged
$ git restore --staged notes.txt grade.py  # unstage both
$ git restore grade.py                     # throw away the debug print
$ git status                               # Untracked: notes.txt

git revert would add a 5th commit; --hard would delete notes.txt; --amend would fold the junk into your fix commit.

Twist The surviving mutant

Code is return len(pw) >= 8. Tests check "abc" (False) and a 19-char password (True). A mutation tool reports: mutant >= 8 -> > 8 SURVIVED, mutant >= 8 -> >= 7 SURVIVED. Which tests kill them? Does the code need a fix?

Show answer
def test_accepts_exactly_eight_characters():
    assert is_valid_length("abcdefgh") is True    # kills > 8

def test_rejects_seven_characters():
    assert is_valid_length("abcdefg") is False    # kills >= 7

No code fix: the code is right, the tests were weak. Both new tests pass on the real code and fail on the mutants. Commit only the test file.

Twist Two bugs, four commits

shipping_cost(50) returns 5 (should be free) and is_valid_postcode("3000") returns False (4 digits is valid). The team wants one failing-test + fix pair per bug. What are the four commits and what does pytest say at each?

Show answer
1. test shipping_cost(50) == 0       "Add failing test for free shipping at 50"   pytest: red
2. total > 50  ->  total >= 50       "Fix free shipping at 50"                    pytest: green
3. test is_valid_postcode("3000")   "Add failing test for 4-digit postcode"      pytest: red
4. len(code) == 5  ->  == 4          "Fix postcode length"                        pytest: green

If you write both tests first, commit 2 is still red. If you fix both bugs in commit 2, the postcode test in commit 3 never fails, so it proves nothing.

Practice labs

Cheat sheet

  • pytest / pytest -q / pytest -v run all tests (normal / quiet / one line each)
  • pytest -x stop at the first failure; pytest -s show print output
  • pytest -k "email and not long" run tests whose name matches (quote it)
  • pytest file.py::test_name run one test
  • echo $? right after: 0 pass, 1 tests failed, 4 bad path/usage, 5 no tests collected
  • assert f(x) == expected a test needs an assert; no assert = always green
  • with pytest.raises(ValueError): f(-1) expect an error (import pytest)
  • Boundary for "at least N": test N-1 and N (plus a normal and an invalid value)
  • git add test_x.py && git commit -m "Add failing test for ..." commit 1: test only, red
  • git add x.py && git commit -m "Fix ..." commit 2: fix only, green
  • git show --stat HEAD~1 / git show HEAD~1:file inspect the test commit like the grader
  • git reset --soft HEAD~1 undo last commit, keep changes staged
  • git restore --staged f unstage; git restore f discard edits
  • git commit --amend -m "msg" rewrite the LAST commit (only before pushing)
  • Coverage = lines that ran, not lines that were checked. pytest --cov=. --cov-report=term-missing (needs pytest-cov)
  • Stub = canned value; fake = working in-memory version; mock = records calls
  • on: pull_request: branches: [main] run CI on PRs into main
  • Required status checks = GitHub branch protection setting, not YAML; remove continue-on-error: true
