Topic 3

Git remotes, history and recovery

Push, fetch and pull with confidence, fix "rejected" and "diverged", find lost commits with the reflog, and rewrite or undo history (rebase, cherry-pick, reset, revert) without losing anyone's work.

Mental model

Four locations: working directory → staging area → local repository → remote repository. git status only compares the first three, plus your last downloaded copy of the remote.

A commit is a snapshot + the hash of its parent. Its id is a hash of all of that, so changing anything (even just the parent) makes a new commit with a new id.

A branch is a pointer: a tiny file holding one hash. origin/main is also a pointer, your local note of "where main was on origin last time I talked to it". HEAD says which branch (or bare commit) you're on.

Almost every command here just moves pointers or adds commits. Commits that nothing points to aren't gone yet: the reflog still remembers them.

Remotes: origin is just a name

A remote is just another repository (GitHub hosts the same format you have locally). origin is not special: it's the nickname git gives the first remote (on git clone), or the one you add yourself. The remote only knows what you've pushed.

In the labs, the "GitHub" is a bare repository remote.git in the same folder: a repository with no working directory (just what's normally inside .git). You can't edit files in it; you only push to it and fetch from it. Make one with git init --bare remote.git.

git remote add origin remote.git
  1. register a new remote
  2. the nickname you'll type later
  3. its URL or path (on GitHub: https://github.com/you/repo.git)

push: move the remote's pointer to match yours

git push sends the commits the remote is missing, then asks it to move its branch pointer to your commit. The remote only agrees if that is a fast-forward: its current commit must already be in your history (you're just ahead). Otherwise someone's commits would be dropped, so it refuses.

git push -u origin main
  1. upload commits + move the remote's branch
  2. --set-upstream: remember origin/main as main's partner, so later plain git push / git pull work and status shows ahead/behind
  3. which remote
  4. which local branch (it becomes main on the remote)
$ git push -u origin main
To remote.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
$ git push                       # later: no arguments needed
   f141ba5..246fe06  main -> main   # old..new remote position
Tip

git push origin main pushes only main, whatever branch you are on. Plain git push pushes the branch you're on to its upstream. If a task says "don't push branch X", use the explicit form and never git push --all.

Means: someone pushed commits you don't have, and you haven't even fetched them yet.

Fix: integrate first (git pull --no-rebase or git pull --rebase), then push again.

 ! [rejected]        main -> main (non-fast-forward)
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart.

Means: same problem, but you've fetched already: origin/main has commits your main lacks (behind or diverged).

Fix: git merge origin/main (or git rebase origin/main), then push. Never --force on a shared branch.

fatal: The current branch main has no upstream branch.

Means: plain git push doesn't know where to push.

Fix: git push -u origin main once. (fatal: No configured push destination = there's no remote at all: git remote add first.)

Why not the "quick fixes"

git push --force makes origin's main = your main, so the teammate's commit vanishes from origin. git reset --hard origin/main moves your main back to origin's and overwrites your files, so your commit is thrown away. Only merging (or rebasing) keeps both. That's the whole of quiz 1 Q11.

Detached HEAD: on a commit, not a branch

Normally HEAD points at a branch (cat .git/HEAD → ref: refs/heads/main) and committing moves that branch. git checkout <hash> (or git switch --detach <hash>) makes HEAD hold the hash itself. You can look around and even commit, but the new commits are pointed to only by HEAD. Switch away and nothing points at them anymore.

$ git checkout 21e158d
Note: switching to '21e158d'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.
...
$ git commit -m "Try x"
[detached HEAD eb596e0] Try x
$ git switch main
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  eb596e0 Try x

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> eb596e0
Tip

Still detached and want to keep the work? git switch -c new-name right there. Already left? Use the reflog (next section). git status shows HEAD detached at 21e158d while you're detached.

reflog: find lost commits, put a branch on them

git reflog is a local diary of every place HEAD has been: each commit, checkout, merge, rebase, reset. Newest first. git log follows parent links from branches, so it can't see commits no branch reaches; the reflog can (entries are kept ~90 days).

$ git reflog

bc59506 HEAD@{1}: commit: Add rate limit config        # the lost commit
e8bf956 HEAD@{2}: checkout: moving from main to e8bf956  # went detached here
0f9523b HEAD@{3}: commit: Add README
e8bf956 HEAD@{4}: commit (initial): Add request handler
$ git reflog | grep "rate limit"
bc59506 HEAD@{1}: commit: Add rate limit config
bc59506 HEAD@{1}: commit: Add rate limit config

  2. "where HEAD was 1 move ago"; also usable as a name: git branch x HEAD@{1}
  3. what moved HEAD + the commit message

Trap

The branch must exist with that name, pointing at that commit. git merge bc59506 or git cherry-pick bc59506 skips the branch (quiz check "rate-limit is the commit ..." fails), and cherry-pick even makes a copy with a new hash, so the original isn't "merged".

rebase: replay your commits on a new base

git rebase main (while on feature) takes the commits that are on feature but not on main, and re-creates them one by one on top of main. Then it moves feature to the last new copy. Each copy has a new parent, so each gets a new hash. main doesn't move. The old commits stay in the repository (and the reflog) until garbage collection.

# before                              # after: git switch feature ; git rebase main

* 1dbf664 Add notes                      * 484ae4b Add notes

|/                                       * 47b8a42 Add README
* 47b8a42 Add README

Trap

Direction matters. git rebase main moves the branch you're on. On main, git rebase feature would move main instead. Check with git branch first. And don't rebase commits that are already pushed and pulled by others: their copies would no longer match.

cherry-pick: copy one commit here

git cherry-pick <hash> takes the change that commit made (its diff against its parent) and applies it as a new commit on your current branch. New parent → new hash. The original commit and its branch stay as they are. Typical use: a hotfix made on one branch that main needs right now.

$ git switch main
$ git log --oneline --all | grep "Fix timeout"
9a1b2c3 Fix timeout
$ git cherry-pick 9a1b2c3
[main 5d6e7f8] Fix timeout                     # same message, different hash

Conflicts work the same: fix, git add, git cherry-pick --continue (or --abort).

reset (soft / mixed / hard) and revert

git reset <commit> moves your current branch pointer to that commit. The mode decides which of the 3 local locations are also reset to match it:

CommandLocal repo (branch)Staging areaWorking directory
git reset --soft HEAD~1moves backkept (changes staged)kept
git reset HEAD~1 (= --mixed)moves backreset (changes unstaged)kept
git reset --hard HEAD~1moves backresetreset: edits are lost

HEAD~1 = parent of HEAD, HEAD~2 = grandparent. The "removed" commits are not deleted: git reflog + git reset --hard <hash> brings them back. Uncommitted edits wiped by --hard are truly gone.

$ git reset --soft HEAD~1          # "uncommit", keep everything staged
$ git restore --staged debug.log   # unstage the file that shouldn't be in it
$ git commit -m "Add discount"      # recommit, fixed

git revert <hash> is the opposite approach: it adds a new commit that undoes that commit's change. History only grows, so it's the right tool for commits that are already pushed.

$ git revert --no-edit 0866799
[main 632cb80] Revert "Disable auth check"
$ git push                          # fast-forward, teammates just pull
Why

Reset on a pushed commit moves your main behind origin's: the push is rejected, and forcing it rewrites history everyone else already has. Rule: not pushed → reset is fine. Pushed → revert.

Trap

git revert HEAD undoes the latest commit, which may not be the bad one. Look up the hash with git log --oneline | grep. Without --no-edit, revert opens an editor for the message.

Secrets in history

Deleting a file makes a new snapshot without it. Every older snapshot still has it, in every clone. So a committed .env is leaked even after "Remove env file".

CommandWhat it does

# Files panel: + New file -> .gitignore, type the line  .env  then Ctrl+S
$ git add .gitignore && git commit -m "Ignore .env"
Why rotate

Once pushed, assume it's copied (forks, clones, scanners find it in minutes). The fix that works is rotate: change the password where it's used so the leaked one is dead. Rewriting history afterwards is clean-up, not a fix. Prevent it with .gitignore + a committed .env.example. Note: .gitignore doesn't affect files git already tracks (untrack with git rm --cached .env).

Drill Push a brand-new repo

You have commits on main and an empty repository at remote.git. No remote is set. Connect it as origin and push so that later a plain git push works.

Show answer
$ git remote add origin remote.git
$ git push -u origin main

-u stores origin/main as main's upstream; from then on git push/git pull need no arguments.

Drill Which locations changed?

A teammate pushed 2 commits. You run git fetch. Which of the four locations changed? Then you run git pull. Which now?

Show answer

After fetch: only the local repository (new objects + origin/main moved). main, staging and working directory are untouched; status says "behind by 2". After pull: the merge moves main and updates the working directory (and staging matches it).

Quiz-style Push rejected, diverged (quiz 1 Q11)

status: "have diverged, and have 1 and 1 different commits each". Which get your commit onto origin and keep the teammate's? (a) git push --force (b) git pull then git push (c) git fetch, git merge origin/main, git push (d) git reset --hard origin/main, git push.

Show answer

(b) and (c). Force erases the teammate's commit on origin; reset --hard throws yours away. On a real terminal (b) may need git pull --no-rebase because of the "divergent branches" message.

Quiz-style After a rebase (quiz 2 Q1)

main: README → "Update changelog". feature: README → "Add notes" → "Strip whitespace in notes". You run git switch feature, git rebase main. True or false: (a) the two feature commits get new ids (b) feature's tip contains CHANGELOG.md (c) main now points at feature's tip (d) the old commits are deleted immediately.

Show answer

(a) true: new parent → new hash. (b) true: they're replayed on top of "Update changelog". (c) false: rebase moves only the branch you're on. (d) false: they stay (reflog) until garbage collection.

Quiz-style Bad commit already pushed

"Disable auth check" was pushed 2 commits ago; teammates pulled. Undo just that change and push, keeping the later commit.

Show answer
$ git log --oneline | grep "Disable auth"
0866799 Disable auth check
$ git revert --no-edit 0866799
$ git push

Revert adds a new commit, so it's a normal fast-forward push. reset --hard HEAD~2 would also delete the later commit and need a force push.

Twist Unseen: you committed on the wrong branch

You made commit "Fix typo" on main (not pushed), but it belongs on docs (which exists). Get it onto docs and remove it from main.

Show answer
$ git log --oneline -1          # note the hash, e.g. 4f5e6d7
$ git switch docs
$ git cherry-pick 4f5e6d7       # copy it onto docs (new hash)
$ git switch main
$ git reset --hard HEAD~1       # OK: not pushed, and the work now lives on docs

Cherry-pick copies; reset removes it from main. If it had been pushed, use git revert on main instead.

Twist Unseen: undo a "reset --hard" mistake

You ran git reset --hard HEAD~2 by accident and two commits vanished from git log. Get main back to where it was.

Show answer
$ git reflog
1a2b3c4 HEAD@{0}: reset: moving to HEAD~2
9f8e7d6 HEAD@{1}: commit: Add totals      # where main was before
$ git reset --hard 9f8e7d6            # or: git reset --hard HEAD@{1}

Commits are never deleted by reset; only the pointer moved. The reflog shows the old position. (Uncommitted edits lost by the first --hard can't be recovered this way.)

Quiz-style Hard: read ahead/behind, then the two-dot logs

After git fetch, status says: "Your branch and 'origin/main' have diverged, and have 2 and 1 different commits each". (a) Which command lists the commits you would be pushing? (b) Which lists the commits you are missing? (c) How many lines does each print? (d) Team rule: linear history. Which two commands get your work onto origin?

Show answer
$ git log --oneline origin/main..main   # (a) yours, not on origin: 2 lines
$ git log --oneline main..origin/main   # (b) theirs, not in main: 1 line
$ git rebase origin/main                 # (d) or: git pull --rebase
$ git push

A..B = "reachable from B, not from A". The first number in "2 and 1" is always your side. After the rebase status says "ahead by 2", and the push is a fast-forward.

Quiz-style Hard: undo a whole merged feature that's pushed

main: "Add app" → "Add README" → Merge branch 'discount' (brought discount.py + a change to app.py) → "Add logging config". All pushed, teammates pulled. Take the whole discount feature out with one new commit. What happens with a plain git revert <merge>, and what's the right command? What does the wrong parent number do?

Show answer
$ git revert 2ceabd1
error: commit 2ceabd1... is a merge but no -m option was given.
$ git revert -m 1 --no-edit 2ceabd1    # parent 1 = main side = keep it
$ git push

A merge has two parents; -m 1 says "main line is parent 1, undo what parent 2 (the feature) brought in". -m 2 does the opposite: keeps discount and removes "Add README". Reverting the two feature commits one by one also works but makes 2 commits. To bring the feature back later: revert the revert (merging the branch again does nothing).

Twist Unseen: the rebase stops on a conflict

You run git rebase origin/main with 3 local commits. It prints CONFLICT (content): Merge conflict in routes.txt and "Could not apply b2c3d4e... Add search". (a) Which branch are you on now? (b) What are your two ways forward? (c) Inside the conflict markers, which side is HEAD?

Show answer
$ git status
interactive rebase in progress; onto 9f8e7d6
You are currently rebasing branch 'main' on '9f8e7d6'.
# Files panel: open routes.txt, remove <<<<<<< ======= >>>>>>>, keep both lines, Ctrl+S
$ git add routes.txt
$ git rebase --continue           # a terminal editor opens for the message: vim :wq Enter
# or give up completely:
$ git rebase --abort              # main back exactly as before the rebase

(a) No branch: HEAD is detached while the rebase replays commits; main moves only at the end. (b) fix + git add + --continue (repeat for each commit that conflicts), or --abort. (c) During a rebase HEAD = the commit you are replaying onto (origin's side); the bottom part is your commit. That's the reverse of a merge. Don't run git commit in the middle; use --continue.

Twist Unseen: you rebased a branch you had already pushed

Your own branch feature (only you use it) was pushed yesterday. Today you ran git rebase main on it. Now git push says ! [rejected] feature -> feature (non-fast-forward) and status says "have diverged, 3 and 2 different commits". git pull would merge the old copies back in. What do you run, and why is it safer than --force?

Show answer
$ git push --force-with-lease

Rebase gave the commits new hashes, so origin's feature (old hashes) is not in your history: any normal push is rejected. You really do want to replace it. --force-with-lease replaces it only if origin's feature is still where your origin/feature says. If someone pushed to it since your last fetch, it refuses instead of erasing their work. --force erases blindly. Never do this on main or any branch others build on: use revert or merge there.

Practice labs

Cheat sheet

  • git remote -v / git remote add origin URL list / add a remote
  • git push -u origin main first push + set upstream; afterwards just git push
  • git fetch moves only origin/main; git pull = fetch + merge (files change)
  • git pull --no-rebase / git pull --rebase merge or rebase when diverged
  • git log --oneline --graph --all --decorate see every branch and where origin/main is
  • git log --oneline main..origin/main what you're missing (swap = what you haven't pushed)
  • Rejected push → integrate (pull/merge or rebase), then push. Never --force / reset --hard origin/main
  • git reflog | grep "msg" find lost commits (detached, deleted branch, after reset)
  • git branch name HASH branch at a commit (stay put); git switch -c name HASH (and switch)
  • git merge --no-edit X merge without opening the editor
  • git switch feature; git rebase main replay feature on main (new hashes, main stays)
  • git add f; git rebase --continue / git rebase --abort during a rebase conflict
  • git cherry-pick HASH copy one commit onto the current branch
  • git reset --soft|--mixed|--hard HEAD~1 move branch back; keep staged / keep files / lose all
  • git revert --no-edit HASH undo a pushed commit with a new commit
  • git revert -m 1 --no-edit MERGE undo a whole pushed merge (keep parent 1 = main side)
  • git fetch --prune / git push origin --delete B drop stale origin/* names / delete B on origin
  • git switch B (origin/B exists) / git branch -u origin/B create tracking branch / set upstream later
  • git push --force-with-lease only for your own rebased branch; refuses if someone pushed meanwhile
  • git cat-file -t/-p HASH, cat .git/HEAD, git rev-parse main look inside
  • git log --all --oneline -- .env, git show HASH:.env find a leaked secret → rotate it
  • git rev-list --count main, git merge-base --is-ancestor A B check your own work like the grader
