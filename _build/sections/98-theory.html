Question bank

Theory question bank (quiz 2 syllabus)

About 85 new multiple-choice questions in the quiz style (a scenario, then "choose all that apply" or one answer), each with the reason every option is right or wrong.

How to use this

Answer before you open. Write down your letters first, then click Show answer. If you open it first, you only learn to recognise the answer. You don't learn to produce it.

For "choose all that apply", look at each option on its own and decide true or false. Several options can be right, and the wrong ones are common misconceptions.

The explanation says why each wrong option is wrong. Read it even when you got the question right.

Levels: Drill = recall, Quiz-style = quiz level, Twist = harder than the quiz, or mixes two topics.

What the quiz covers

Quiz 2A tested git internals and rebase (T2L1), testing and CI (T2L2), containers (T3L1), database migrations (T3L2) and architecture (T4L1). This bank gives those topics the most questions. The last question set before the rapid-fire facts is a short review of the earlier lectures (T0/T1), because ideas like the four locations, ports and secrets come up again inside the later topics.

Git internals: objects, hashes, diff and merge (T2L1)

Drill What a blob knows

A repo has src/app.py and backup/app.py, and the two files have exactly the same bytes. You then rename src/app.py to src/main.py and change nothing else. Which statements are true? Choose all that apply.

  1. A blob stores only the file's bytes. It has no file name or path.
  2. The two identical files are stored as one blob.
  3. The rename creates a new blob, because the name is part of the blob.
  4. The file name lives in the tree object that points to the blob.
Show answer

A, B, D. A blob's id is a hash of its content alone, so identical bytes give the same id, and Git never stores the same bytes twice. Names live one level up, in a tree (100644 blob 3f9a1c2 app.py). After the rename, the tree changes and so the commit is new, but the blob is reused. C is wrong because the name is not inside the blob.

Drill What is inside a commit object?

git cat-file -p HEAD prints a commit object. Which of these does a commit object store? Choose all that apply.

  1. The hash of one tree (the snapshot of the whole project)
  2. The hash of its parent commit(s)
  3. A diff of the lines that changed since the parent
  4. Author, committer, timestamps and the message
  5. The name of the branch it was made on
Show answer

A, B, D. A commit is tree + parent + author/committer + message. It is a full snapshot, not a diff, so C is wrong: git diff works out the changes each time you ask. Branch names are not stored in commits (E). A branch is a separate file that points to a commit.

Quiz-style Two branches, one commit, then a commit

main and feature both point to commit c41a2e0. You are on feature and you make one commit, 9d03b7f. Which statements are true? Choose all that apply.

  1. .git/refs/heads/feature is overwritten with the hash 9d03b7f….
  2. .git/refs/heads/main still holds c41a2e0….
  3. The parent of 9d03b7f is c41a2e0.
  4. main also moves, because the two branches shared a commit.
  5. Git copied all project files into a new folder for feature when the branch was created.
Show answer

A, B, C. A branch is a small text file holding one commit hash. Committing rewrites only the file of the branch HEAD points to. Branches are separate pointers, not containers, so pointing at the same commit doesn't tie them together (D). Making a branch writes one pointer file and copies no files (E). That is why branching is instant.

Quiz-style Amend only the message

You just made commit 5e1f0aa "Add lgoin form". You run git commit --amend -m "Add login form" and change no files. Which statements are true? Choose all that apply.

  1. The commit gets a new ID, because the message is part of the hashed content.
  2. The new commit points to the same tree as 5e1f0aa.
  3. 5e1f0aa is deleted from .git/objects at once.
  4. 5e1f0aa is still listed in git reflog.
Show answer

A, B, D. The ID is a hash of the tree, parent, metadata and message, so a new message means a new commit. No file changed, so the tree hash is identical. The old commit is now unreachable from any branch, but it is still in the object database and in the reflog. It only disappears when git gc prunes it after the grace period, so C is wrong.

Twist Fix one old message: which IDs change? 
d4e5f60 (HEAD -> main) Add tests
c3d4e5f Add search route
b2c3d4e Add databse layer
a1b2c3d Initial commit

You use an interactive rebase to change only the message of b2c3d4e to "Add database layer". Which commits on main get a new ID?

  1. Only the commit whose message changed
  2. That commit and every commit after it ("Add search route" and "Add tests")
  3. All four, because rebase rewrites the whole branch
  4. None, because no file content changed
Show answer

B. Each commit stores its parent's hash. A new message gives "Add database layer" a new ID. Then "Add search route" has a new parent hash, so it gets a new ID too, and the change carries on to the tip. That is why rewriting history changes every later ID. "Initial commit" is not touched, so C is wrong. D is wrong because the message is hashed as well as the files.

Quiz-style One byte flipped on disk

A disk error flips one byte inside a blob file under .git/objects. Which statements are true? Choose all that apply.

  1. Git can detect it, because the content no longer hashes to the object's name.
  2. Git can't notice, because objects are looked up by file name.
  3. The content still exists but the address is wrong, so the object can no longer be trusted.
  4. Content addressing is the same idea used for CDN cache keys and Merkle trees.
Show answer

A, C, D. An object's name is the hash of its content (id = SHA1(content)), so a change of one byte breaks the match and git fsck reports it. Git looks everything up by hash, not by file name (B). Because the name is derived from the content, you can check data without trusting whoever gave it to you.

Quiz-style Predict the diff

The committed steps.txt has 4 lines: a, b, c, d. You delete line b. What does git diff show (ignoring the header)?

  1.  a
-b
 c
 d
  2. -a
-b
-c
-d
+a
+c
+d
  3.  a
-b
+c
-c
 d
  4. Nothing. Git stores diffs only for commits, not for the working tree.
Show answer

A. Myers finds the shortest edit script: one deletion, with the matching lines kept as context (diagonal moves cost 0). B is a valid edit script, but it is 7 edits, not the shortest. C makes no sense. D is wrong: git diff computes the change between the working tree and the staging area on demand.

Twist Two shortest scripts: which one does Myers pick?

Old file: x, y. New file: y, x. Two edit scripts of length 2 exist: (1) delete x, keep y, insert x; (2) insert y, keep x, delete y. Which statements are true? Choose all that apply.

  1. Both scripts are shortest (d = 2).
  2. Myers prefers deleting over inserting, so git shows -x, then y, then +x.
  3. Myers picks one at random each run, so the output can change.
  4. A replace-all script (delete both, insert both, d = 4) is equally good because the result is the same.
Show answer

A, B. When two scripts are equally short, Myers takes the deletion first. That gives the same output every run, so C is wrong. D gives the same file but is not the shortest edit script, and that is the only thing Myers looks for.

Drill Why git diff is fast on huge, almost identical files

Two versions of a 200,000-line file differ in 3 lines. Why does git diff answer at once?

  1. Myers runs in O((m+n)·d) time, and d (the number of edits) is tiny here.
  2. Git stored the 3-line diff when you committed.
  3. Myers compares every line with every other line, O(m·n), and computers are fast.
  4. Git compares only the file sizes.
Show answer

A. Myers's cost grows with the size of the edit script d. It follows the free diagonals (matching lines) and never walks one twice. Its memory is O(m+n). Git stores snapshots, not diffs (B). O(m·n log m) is roughly the older Hunt–McIlroy LCS approach (C). Sizes alone can't say which lines changed (D).

Quiz-style Why a three-way merge needs the base

You merge feature into main. Which statements about the three-way merge are true? Choose all that apply.

  1. Git computes diff(base, main) and diff(base, feature) with the same diff engine.
  2. Without the base, Git couldn't tell whether a line was added on one side or deleted on the other.
  3. Git compares the two tips directly and makes a conflict wherever they differ.
  4. If main edits line 10 and feature edits line 40, both changes are kept with no conflict.
  5. A conflict means Git has crashed and the merge must be redone from scratch.
Show answer

A, B, D. Two Myers edit scripts are made against the common ancestor. If they touch different regions, both apply cleanly. If both sides touched the same region, Git has two valid edits and no rule to choose, so it stops and asks you. That refusal is correct behaviour, not a crash (E). Comparing only the two tips (C) would make every difference look like a conflict.

Quiz-style Merge, rebase, squash: three claims about history

Which statements are true? Choose all that apply.

  1. A merge keeps both timelines exactly as they happened, joined by a merge commit with two parents.
  2. A rebase replays your commits on a new base, which gives them new hashes and a straight line.
  3. A squash is a rebase whose commits are collapsed into one.
  4. A rebase keeps the original commit IDs and only moves the branch pointer.
  5. A squash keeps each original commit on main, so git log still shows them one by one.
Show answer

A, B, C. Merge treats history as an accurate ledger. Rebase and squash treat it as a readable story. A replayed commit has a new parent, so it must get a new ID (D is wrong). A squash leaves one commit on main, and the individual commits are not part of main's history (E).

Twist Predict the graph after a rebase 
$ git log --graph --oneline --all
* 9c1d2e3 (HEAD -> feature) Add search box
* 7b2c3d4 Add search route
| * 4e5f6a7 (main) Fix footer typo
|/
* 1a0b2c3 Initial commit

You run git rebase main and there are no conflicts. Which statements are true? Choose all that apply.

  1. git log --oneline feature now lists: Add search box, Add search route, Fix footer typo, Initial commit.
  2. The new copy of "Add search route" has 4e5f6a7 as its parent.
  3. main still points to 4e5f6a7.
  4. 9c1d2e3 is still reachable from feature.
  5. Running git switch main, then git merge feature, is now a fast-forward.
Show answer

A, B, C, E. Rebase copies the two feature commits on top of main's tip, so feature now contains the footer fix and is a straight line ahead of main. Main itself does not move. The old commits get new IDs, so 9c1d2e3 is no longer on feature (D is wrong). You can only find it through the reflog until gc. Since main is now an ancestor of feature, merging just moves main forward.

Quiz-style Delete an unmerged branch, then gc

Branch exp has two commits that are on no other branch. Which statements are true? Choose all that apply.

  1. git branch -d exp refuses with "not fully merged".
  2. After git branch -D exp, the two commits are unreachable but still in the object database.
  3. git gc right after the delete removes them at once.
  4. You can recover them with git branch exp <hash>, using a hash from git reflog.
Show answer

A, B, D. Lowercase -d protects unmerged work, and capital -D forces the delete. Deleting a branch removes only the pointer file. The commits are unreachable but intact. They are also still referenced by the reflog, and gc only prunes them after its grace period (C is wrong). Pointing a new branch at the tip brings back both commits, because each commit links to its parent.

Remotes, undo and recovery (T0L1 + T2L1)

Drill Clean status, but teammates can't see it 
$ git status
On branch main
Your branch is ahead of 'origin/main' by 2 commits.
  (use "git push" to publish your local commits)

nothing to commit, working tree clean

Which statements are true? Choose all that apply.

  1. The local repository and the remote disagree.
  2. git push sends the 2 commits and moves origin's main.
  3. The working directory and the staging area disagree.
  4. git status just asked GitHub how many commits it has.
Show answer

A, B. "Working tree clean" means the first three locations agree. "Ahead by 2" compares your main with origin/main, which is your last downloaded copy of the remote. git status never contacts the server (D is wrong), so the count can be out of date until you git fetch. C is wrong because the tree is clean.

Quiz-style What fetch changes

You are on main with one local commit that isn't pushed and an unstaged edit to api.py. A teammate pushed 3 commits. You run git fetch origin. Which statements are true? Choose all that apply.

  1. origin/main now includes the 3 commits.
  2. Your main is unchanged and api.py keeps your edit.
  3. git status may now say your branch and 'origin/main' have diverged.
  4. Your local commit was uploaded too.
Show answer

A, B, C. Fetch only downloads, and it updates only the remote-tracking pointer. You have 1 commit they don't have, and they have 3 you don't, so the branches have diverged (1 and 3). Uploading is git push (D).

Twist git pull refuses on a diverged branch 
$ git pull
hint: You have divergent branches and need to specify how to reconcile them.
...
fatal: Need to specify how to reconcile divergent branches.

Your push was rejected earlier because main and origin/main diverged. Which commands integrate the teammate's work so that your next push is accepted? Choose all that apply.

  1. git pull --no-rebase (merge), then git push
  2. git pull --rebase, then git push
  3. git fetch, then git merge origin/main, then git push
  4. git push --force
Show answer

A, B, C. Recent Git versions don't guess between merge and rebase when the branches have diverged and no pull.rebase setting exists. You have to pick one. A and C make a merge commit with both commits. B replays your commit on top of theirs (it gets a new ID) and gives a straight line. A force-push overwrites origin's main and erases the teammate's commit (D).

Quiz-style Unstage, but keep the edit

You ran git add config.py secrets.txt. You want secrets.txt out of the next commit, but the file must stay on disk unchanged. Which commands do that? Choose all that apply.

  1. git restore --staged secrets.txt
  2. git reset secrets.txt
  3. git restore secrets.txt
  4. git rm secrets.txt
Show answer

A, B. Both copy the HEAD version back into the staging area and leave the working directory alone. git restore <file> (without --staged) does the opposite: it overwrites the working copy with the staged copy and leaves it staged (C). git rm deletes the file from disk and stages the deletion (D). To keep the file out of git for good, add it to .gitignore as well.

Quiz-style Predict status after reset --soft 
c3 (HEAD -> main) Add retry logic   # changed net.py
c2 Add client
c1 Initial commit

Nothing is pushed and the tree is clean. You run git reset --soft HEAD~1. What does git status show?

  1. main is at c2, and net.py is under "Changes to be committed"
  2. main is at c2, and net.py is under "Changes not staged for commit"
  3. main is at c2, the tree is clean, and the retry change is gone from disk
  4. main is still at c3, with a new commit that undoes c3
Show answer

A. --soft moves only the branch pointer and keeps the staging area and files, so the change is staged and ready to commit again. B is --mixed (the default): pointer and staging area reset, files kept. C is --hard. D describes git revert.

Quiz-style A bad commit is already on shared main

Commit 8f2a1b0 on main broke checkout. It was pushed an hour ago, and three teammates have pulled since. Which statements are true? Choose all that apply.

  1. git revert 8f2a1b0, then git push, is the safe undo.
  2. After the revert, 8f2a1b0 is still in history, followed by a new commit that undoes it.
  3. git reset --hard HEAD~1 then git push --force is just as safe, because it gives a cleaner history.
  4. The revert needs no force-push, because it only adds a commit.
Show answer

A, B, D. Revert undoes the change by adding history, so everyone's clones stay consistent and the push is a fast-forward. Reset and force-push rewrite shared history (C). Teammates who already have 8f2a1b0 would bring it back on their next push, and any commit pushed after it would be lost.

Twist Two commits made on a detached HEAD

You ran git checkout v1.0 (a tag), then made commit d1 and then d2 (which has d1 as its parent). Then you ran git switch main. You want a branch hotfix that contains both commits. Which commands work? Choose all that apply.

  1. git branch hotfix <hash of d2>
  2. git branch hotfix HEAD@{1}
  3. git branch hotfix <hash of d1>
  4. git switch -c hotfix
Show answer

A, B. A branch at d2 includes d1, because d2's parent is d1. In the reflog, HEAD@{0} is the switch to main, so HEAD@{1} is where HEAD was just before: d2. A branch at d1 loses d2 (C). switch -c creates the branch at your current commit, which is main's tip (D).

Twist You rebased a branch you had already pushed

Only you work on feature/search. You pushed it, then ran git rebase main. Now git push is rejected (non-fast-forward). Which statements are true? Choose all that apply.

  1. The push is rejected because the rebased commits have new IDs, so origin's tip is not in your history any more.
  2. git push --force-with-lease is the right fix here.
  3. git pull then git push is the cleanest fix.
  4. The same move on shared main would be dangerous.
Show answer

A, B, D. Rebase made copies, so the old tip on origin is no longer an ancestor of yours. Since nobody else uses the branch, replacing it is fine, and --force-with-lease refuses if origin moved since your last fetch. Pulling (C) would merge the old copies back in, so every commit would appear twice. On a shared branch, rewriting history breaks everyone else's clones.

Drill What stash keeps

You have an unstaged edit to app.py and a brand-new untracked file notes.md. You run git stash. Which statements are true? Choose all that apply.

  1. app.py goes back to its last committed state.
  2. notes.md stays in the folder, because untracked files are not stashed by default.
  3. git stash pop re-applies the edit and drops that stash entry.
  4. The stash is pushed to origin so teammates can see it.
Show answer

A, B, C. A stash is a local "desk drawer" for tracked changes. It saves both staged and unstaged changes. Untracked files need git stash -u. Stashes are never pushed (D).

Quiz-style Inside a conflict 
$ git merge feature/pricing
CONFLICT (content): Merge conflict in price.py
$ cat price.py
<<<<<<< HEAD
TAX = 0.18
=======
TAX = 0.12
>>>>>>> feature/pricing

You are on main. Which statements are true? Choose all that apply.

  1. TAX = 0.18 is main's version.
  2. After editing the file, git add price.py then git commit finishes the merge.
  3. git merge --abort returns to the state before the merge.
  4. Git chose 0.12 because the incoming branch always wins.
Show answer

A, B, C. The part between <<<<<<< HEAD and ======= is your checked-out branch. The part after it is the incoming branch. Staging the resolved file marks it resolved, and the commit records the merge with two parents (git merge --continue works too). Git chose nothing (D). Both sides changed the same line, so it shows both and stops.

Quiz-style .gitignore added too late

debug.log was committed last week. Today you add *.log to .gitignore, but git status still shows modified: debug.log. Which single step stops git from tracking it but keeps the file on disk?

  1. git rm --cached debug.log, then commit
  2. Nothing: wait, and .gitignore applies from the next commit
  3. git restore debug.log
  4. rm debug.log
Show answer

A. .gitignore only affects untracked files. Once a file is tracked, git keeps tracking it. rm --cached removes it from the staging area (so the next commit stops tracking it) and leaves it on disk. Old commits still contain it, which matters if it held a secret. C only throws away the current edits. D deletes the file and stages nothing.

Quiz-style commit -a and a new file

You edited the tracked file app.py and created a new file util.py. You run git commit -am "Add helper". What happens?

  1. The commit has the app.py change. util.py is still untracked.
  2. The commit has both files.
  3. Git refuses, because an untracked file exists.
  4. The commit has only util.py.
Show answer

A. -a stages changes to files git already tracks. A new file needs an explicit git add first. Untracked files never block a commit (C).

Testing and CI (T2L2)

Drill Which of these are integration tests?

Choose all that apply.

  1. POST /api/users twice with the same email, against a disposable test database, expecting 409
  2. calculate_gst(1000) returns 180
  3. A browser opens /signup, creates an account, and lands on /dashboard
  4. A repository function saves a row to a real Postgres test database, then reads it back
Show answer

A, D. Integration tests check real components working together: route, validation, ORM and database. B is a unit test (pure logic, no network or database). C is end-to-end (browser plus the whole stack). A duplicate-email check needs a real database to find the existing row, so it can't be a unit test.

Quiz-style Boundary cases for a range

Rule: "A username has 3 to 12 characters (inclusive)." Which input lengths are boundary cases? Choose all that apply.

  1. 2
  2. 3
  3. 7
  4. 12
  5. 13
Show answer

A, B, D, E. Each edge needs one test just outside it and one exactly on it: 2/3 at the bottom and 12/13 at the top. 7 is a normal (valid-class) case. It's worth having, but it is not on a boundary. Most real defects sit at these edges, such as > written where >= was meant.

Quiz-style 100% coverage, no assertion (pytest) 
def discount(total, is_member):
    if is_member and total > 100:
        return total * 0.9
    return total

def test_discount():
    discount(200, True)
    discount(50, False)

Which statements are true? Choose all that apply.

  1. Line coverage of discount is 100%.
  2. If someone changed 0.9 to 0.5, this test would still pass.
  3. pytest marks this test as failed, because it contains no assert.
  4. Adding assert discount(200, True) == 180 would catch the 0.5 change.
Show answer

A, B, D. Both paths of the if run, so every line executes. Coverage measures execution, not whether anything was checked. pytest passes a test that finishes without an exception, so C is wrong. That is exactly why this test proves nothing. An assertion on the result turns it into a behavioural claim.

Twist A mutant that survives 
# original
def can_vote(age): return age >= 18
# mutant made by the tool
def can_vote(age): return age > 18

def test_child(): assert can_vote(10) is False
def test_adult(): assert can_vote(30) is True

Which statements are true? Choose all that apply.

  1. The mutant survives: both tests still pass against it.
  2. Adding assert can_vote(18) is True kills the mutant.
  3. A surviving mutant proves the original code has a bug.
  4. Line coverage is 100%, so the suite is strong.
Show answer

A, B. 10 and 30 give the same answers under >= and >. Only the boundary value 18 tells them apart. A surviving mutant means the tests can't distinguish the change. It says nothing about a bug in the original code (C). Full coverage with a surviving mutant is exactly the blind spot coverage has (D).

Quiz-style Name the test double

(1) A class with save() and find() that keeps users in a Python dict. (2) A function that always returns the exchange rate 83.0. (3) An object the test checks with email.send.assert_called_once_with("a@x.com"). Which line names them correctly?

  1. (1) fake, (2) stub, (3) mock
  2. (1) mock, (2) fake, (3) stub
  3. (1) stub, (2) mock, (3) fake
  4. All three are mocks. The words mean the same thing.
Show answer

A. A fake is a working but simplified implementation (an in-memory database). A stub returns a fixed, canned value. A mock records how it was called, so the test can assert on that call. Use a double only at a slow, unsafe, costly or external boundary, never in place of the behaviour the test claims to prove.

Quiz-style Over-mocked signup test 
def test_register():
    repo = Mock()
    register(repo, {"email": "a@x.com", "password": "short"})
    repo.save.assert_called()

register is supposed to reject passwords under 8 characters. The test passes. Which statements are true? Choose all that apply.

  1. The test passing shows register saves a user with a 5-character password, which is the bug.
  2. The test proves only that save was called, not that registration behaves correctly.
  3. A behaviour-focused test would assert that the short password is rejected and that no user is stored.
  4. Replacing the Mock with a real production database would make it a better unit test.
Show answer

A, B, C. The test asserts that an interaction happened, so it actually locks in the buggy behaviour. A good test states the rule: invalid input, then rejected, then nothing persisted (an in-memory fake makes the "nothing stored" part checkable). Automated tests must never use production data (D). The integration level uses a disposable test database.

Quiz-style Passes alone, fails in the suite

test_create_user inserts a@x.com into a shared test database and never cleans up. test_user_count asserts the table has 0 rows. Run alone, each passes. pytest on the whole file fails test_user_count. Which statements are true? Choose all that apply.

  1. The tests are not independent: one leaves state that the other trips over.
  2. Each test should set up and clean up its own data (for example a fresh, disposable database per test).
  3. pytest runs tests in a random order by default, which caused this.
  4. Good tests pass whether they run first or last.
Show answer

A, B, D. Test order must not matter, and each test must clean up its own state. pytest runs tests in file order by default, not randomly (C). The order is what exposed the leftover row, but it did not cause it.

Twist Red only on weekends 
def test_shop_open():
    assert is_open(datetime.now()) is True

CI is green Monday to Friday and red on Saturday and Sunday. Which statements are true? Choose all that apply.

  1. The test depends on the clock, which nothing controls, so it is not deterministic.
  2. The fix is to pass fixed dates, e.g. is_open(datetime(2026, 10, 26, 10, 0)), and add a weekend case too.
  3. Re-running the CI job until it is green is an acceptable fix.
  4. A flaky test weakens CI, because people learn to ignore a red status.
Show answer

A, B, D. Tests must give the same result every run. Clock, network and random values are only OK when the test controls them. Re-running hides the problem and keeps the test unreliable (C).

Quiz-style The two-commit fix

A seeded defect: is_valid_length("abcdefgh") returns False (8 characters should be valid). The milestone wants it fixed in two commits. Which statements are true? Choose all that apply.

  1. Commit 1 adds a test that fails against the current code. Commit 2 fixes the code and the test passes.
  2. Seeing the test fail first shows it really reproduces the bug.
  3. A test written after the fix, which has only ever passed, might not detect the bug at all.
  4. CI should be green on both commits, otherwise the workflow is wrong.
Show answer

A, B, C. Reproduce, then red, then fix, then green. The failing test is evidence, in code, that you caught the defect. After that it guards against the bug coming back (a regression). Commit 1 is expected to be red (D).

Quiz-style Which stack for an early product?

  1. A (modular) monolith on one framework, with a managed relational database and PaaS hosting
  2. Six microservices on Kubernetes, each with its own database, behind an API gateway
  3. Serverless functions joined by a cloud workflow orchestrator
  4. Microservices now, so the team doesn't have to rewrite later
Show answer

A. For a small team at an early stage, a monolith removes network overhead and orchestration cost, and it is the fastest path to a safe first release. B and D pay the distributed-systems tax before any measured pain exists ("Monolith First"). C adds orchestration and per-call cost that a simple app doesn't need.

Twist Why Prime Video saved 90%

Which statements explain the Prime Video monitoring case? Choose all that apply.

  1. The serverless pipeline was billed per state transition in the orchestration workflow.
  2. Heavy video frames were passed through S3 between every step, which made an I/O bottleneck.
  3. Moving to one process (on EC2/ECS) passed the data in memory instead.
  4. The lesson is that microservices are always wrong.
Show answer

A, B, C. Sending large data across a network between services or functions is expensive and slow. One memory space removes that cost. The lesson is about fit, not religion (D): "Building evolvable software systems is a strategy, not a religion."

The campus food app is a modular monolith with Ordering, Dispatch and Vendor Ops. Which observations would justify extracting Dispatch into its own service? Choose all that apply.

Twist Serverless meets Postgres on launch day

Quiz-style Prove .env was never committed

.env is listed in .gitignore. You want proof that it was never committed on any branch. Which command shows that (empty output = never)?

  1. git log --all --full-history -- .env
  2. cat .gitignore
  3. git status
  4. ls -a
Show answer

A. It searches every branch's history for commits that touched .env. .gitignore only stops untracked files being added. It says nothing about the past (B). git status describes only the present (C). If a secret was ever pushed, rotate it, because deleting the file doesn't remove it from history, forks or clones.

Quiz-style Configuration as input

Which statements match the twelve-factor rule "store config in the environment"? Choose all that apply.

  1. One build can run in dev, staging and production with different DATABASE_URL values.
  2. Changing the database URL means changing a variable and restarting, not rebuilding.
  3. A committed .env.example with safe defaults documents each variable.
  4. Production passwords belong in a committed config.js so every teammate has them.
Show answer

A, B, C. Config compiled into code is a constant that is true in exactly one place. An environment variable is read fresh each time the process starts. D is the classic leak: scanners find committed credentials within minutes.

Drill Connection refused

On a server, nothing has bound port 5432. An attacker scans that port. What do they see?

  1. Connection refused: nothing is listening
  2. A Postgres login prompt
  3. A crash log with the Postgres version
  4. A timeout, every time
Show answer

A. A port is only "open" when a process has a listening socket bound to it. With no listener, the OS refuses the connection. (A firewall that silently drops packets would make it look like a timeout instead. That is a different setup from "nothing is listening".)

Quiz-style A good CLAUDE.md rule

A, B. The file is operational ground truth: exact commands, a directory map, and hard rules. Concrete negative constraints ("never", "must") get obeyed, while vague suggestions get skimmed (C). Secrets never go in a file the agent or the repo can read (D).

Rapid-fire facts

Read these the night before and again just before the quiz. Each one has decided a multiple-choice option before.

Git internals and history

  • Git = a DAG of content-addressed objects: blob, tree, commit, tag
  • Object id = hash of its content. Change 1 byte and you get a new object with a new id
  • A blob has no name. The tree holds names and modes
  • A commit = tree + parent(s) + author/committer + message. It is a snapshot, not a diff
  • A branch = a small file holding one hash. Committing overwrites only that file
  • Change one commit and it and every later commit get new IDs
  • Amend or rebase = new commits. The old ones stay (reflog) until gc's grace period
  • Myers = shortest edit script, O((m+n)·d) time, O(m+n) memory, git's default
  • On a tie, Myers prefers delete over insert
  • 3-way merge = diff(base,ours) + diff(base,theirs). Same region on both sides = conflict
  • Merge = accurate ledger (2-parent commit). Rebase = readable story (new hashes, straight line)
  • Squash = rebase with the commits collapsed into one
  • Rebase moves only the branch you're on. main stays put
  • git branch -d refuses unmerged work. -D forces it

Remotes, undo and recovery

  • Four locations: working dir, staging, local repo, remote
  • git status never contacts the remote. "ahead/behind" uses the last fetch
  • fetch = download + move origin/main only. pull = fetch + integrate
  • Diverged + plain git pull = "Need to specify how to reconcile". Use --no-rebase or --rebase
  • Rejected push: integrate first. Never --force on shared main
  • restore f = staged copy goes to the working dir. restore --staged f = unstage
  • reset --soft keeps staged, --mixed keeps files, --hard discards
  • Pushed bad commit: git revert (adds an undo commit)
  • Lost commit: git reflog, then git branch name <hash>
  • After switching away, HEAD@{1} = where HEAD was just before
  • Rebased your own pushed branch: push --force-with-lease
  • commit -a skips untracked files. stash skips untracked unless -u
  • .gitignore ignores only untracked files. Use git rm --cached to stop tracking

Testing and CI

  • Arrange, Act, Assert. No assertion = no behavioural check
  • pytest passes a test with no assert if it doesn't raise
  • Cases: normal, boundary (just below and exactly on), invalid/missing, error
  • Unit = pure logic. Integration = real components + DB. E2E = browser journey
  • Pyramid: many unit, some integration, few E2E. It is a budget, not a law
  • Coverage = lines/branches/functions executed, not asserted
  • Mutation testing: a surviving mutant means the tests can't tell the change apart
  • Stub = canned value. Fake = working simplified version. Mock = records calls
  • Tests must be independent, clean up after themselves, and be deterministic (no uncontrolled clock or network)
  • Bug fix = commit 1 failing test (red), commit 2 fix (green)
  • CI = validate, build, test, report status on a change. CD = deliver/deploy
  • A failing step fails the job, and later steps are skipped
  • continue-on-error: true lets the job pass anyway
  • Gate = pull_request trigger + required status check in branch protection
  • Clean runner = only declared dependencies. Read the first meaningful error

Containers and Docker

  • Container = isolated process(es) on the shared host kernel. A VM has its own kernel
  • Namespaces = what you see (PID, mount, net, hostname, user)
  • cgroups = how much you use: over CPU = throttled, over memory = may be killed
  • Main process is PID 1 inside, with a different PID on the host
  • Image layers are read-only and shared (copy-on-write). Each container has its own writable layer
  • A changed input invalidates that step and all steps after it
  • Copy manifests, then install, then copy source. CMD only records metadata
  • COPY cache uses file contents, not timestamps. .dockerignore trims the context
  • npm ci installs exactly the lockfile and fails on a mismatch
  • EXPOSE documents only. -p host:container publishes
  • -p 127.0.0.1:8080:3000 = this machine only. Without the prefix = all interfaces
  • Server inside must listen on 0.0.0.0, not 127.0.0.1
  • stop/start keeps the writable layer. rm deletes it
  • A named volume outlives containers. Only the mounted path is kept
  • New image = new container (rm + run). restart reuses the old image

Database migrations

  • Code, schema and data change independently. Code is reversible, data often isn't
  • Auto-sync rename = drop + add an empty column. Prototype only
  • Runner: read history, run pending files in order, insert a history row, COMMIT
  • History = append-only, ordered, checksum-verified
  • Edited applied file = checksum mismatch, deploy stops before running anything
  • flyway repair fixes checksums and runs no SQL
  • Hand-run SQL = schema changed, no history row, migration still pending
  • Postgres DDL is transactional. Killed before COMMIT = it reruns cleanly
  • Error inside BEGIN: transaction aborted. COMMIT then rolls back
  • Without BEGIN each statement autocommits
  • ADD COLUMN needs ACCESS EXCLUSIVE. It waits for open readers, and later readers queue behind it
  • Locks are held until the transaction ends. lock_timeout limits only the wait
  • PG 11+: constant default = fast. Volatile default (clock_timestamp(), gen_random_uuid()) = full rewrite
  • Down migration can't restore deleted values, only a backup can
  • Expand, backfill, transition, contract. Irreversible at contract (drop)
  • Required column: nullable, writes supply it, batched backfill, CHECK NOT VALID, VALIDATE, SET NOT NULL
  • Use timestamp versions so two branches don't collide
  • PITR = physical base backup + archived WAL. A replica is not a backup. RPO = data loss, RTO = time

Architecture

  • Network call costs: partial failure, retries plus idempotency, distributed transactions, no debugger
  • Timeout = unknown outcome. Retry only idempotent calls, and send an idempotency key
  • 8 fallacies: reliable, zero latency, infinite bandwidth, secure, fixed topology, one admin, zero transport cost, homogeneous
  • Conway's Law: systems copy org communication. Microservices apply it in reverse
  • Monolith First: split only on measured pain (~50+ engineers, very different scaling)
  • Modular monolith = one deployable, enforced boundaries, ACID easy, no network tax
  • Modules talk via public APIs/events, never another module's tables
  • Boundary enforced in CI (Packwerk), not by comments
  • DDD: ubiquitous language, bounded context, context map
  • Five module tests: responsibility, language, rules, data, contract
  • A unique noun or a shared table does not make a module
  • Prime Video: per-transition billing + S3 relay, fixed by one process with in-memory transfer
  • Serverless + Postgres: one connection per invocation exhausts the limit. Use pooling
