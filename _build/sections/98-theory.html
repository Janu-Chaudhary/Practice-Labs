Theory question bank (quiz 2 syllabus)

About 85 new multiple-choice questions in the quiz style (a scenario, then "choose all that apply" or one answer), each with the reason every option is right or wrong.

How to use this

Answer before you open. Write down your letters first, then click Show answer. If you open it first, you only learn to recognise the answer. You don't learn to produce it.

For "choose all that apply", look at each option on its own and decide true or false. Several options can be right, and the wrong ones are common misconceptions.

The explanation says why each wrong option is wrong. Read it even when you got the question right.

Levels: Drill = recall, Quiz-style = quiz level, Twist = harder than the quiz, or mixes two topics.

Git internals: objects, hashes, diff and merge (T2L1)

Drill What a blob knows

A repo has src/app.py and backup/app.py, and the two files have exactly the same bytes. You then rename src/app.py to src/main.py and change nothing else. Which statements are true? Choose all that apply.

  1. The rename creates a new blob, because the name is part of the blob.
  2. A blob stores only the file's bytes. It has no file name or path.
  3. The two identical files are stored as one blob.
  4. The file name lives in the tree object that points to the blob.
Show answer

B, C, D. A blob's id is a hash of its content alone, so identical bytes give the same id, and Git never stores the same bytes twice. Names live one level up, in a tree (100644 blob 3f9a1c2 app.py). After the rename, the tree changes and so the commit is new, but the blob is reused. A is wrong because the name is not inside the blob.

Drill What is inside a commit object?

git cat-file -p HEAD prints a commit object. Which of these does a commit object store? Choose all that apply.

  1. The hash of its parent commit(s)
  2. Author, committer, timestamps and the message
  3. The name of the branch it was made on
  4. The hash of one tree (the snapshot of the whole project)
  5. A diff of the lines that changed since the parent
Show answer

A, B, D. A commit is tree + parent + author/committer + message. It is a full snapshot, not a diff, so E is wrong: git diff works out the changes each time you ask. Branch names are not stored in commits (C). A branch is a separate file that points to a commit.

Quiz-style Two branches, one commit, then a commit

main and feature both point to commit c41a2e0. You are on feature and you make one commit, 9d03b7f. Which statements are true? Choose all that apply.

  1. Git copied all project files into a new folder for feature when the branch was created.
  2. The parent of 9d03b7f is c41a2e0.
  3. .git/refs/heads/feature is overwritten with the hash 9d03b7f….
  4. main also moves, because the two branches shared a commit.
  5. .git/refs/heads/main still holds c41a2e0….
Show answer

B, C, E. A branch is a small text file holding one commit hash. Committing rewrites only the file of the branch HEAD points to. Branches are separate pointers, not containers, so pointing at the same commit doesn't tie them together (D). Making a branch writes one pointer file and copies no files (A). That is why branching is instant.

Quiz-style Amend only the message

You just made commit 5e1f0aa "Add lgoin form". You run git commit --amend -m "Add login form" and change no files. Which statements are true? Choose all that apply.

  1. 5e1f0aa is still listed in git reflog.
  2. 5e1f0aa is deleted from .git/objects at once.
  3. The commit gets a new ID, because the message is part of the hashed content.
  4. The new commit points to the same tree as 5e1f0aa.
Show answer

A, C, D. The ID is a hash of the tree, parent, metadata and message, so a new message means a new commit. No file changed, so the tree hash is identical. The old commit is now unreachable from any branch, but it is still in the object database and in the reflog. It only disappears when git gc prunes it after the grace period, so B is wrong.

Twist Fix one old message: which IDs change? 
d4e5f60 (HEAD -> main) Add tests
c3d4e5f Add search route
b2c3d4e Add databse layer
a1b2c3d Initial commit

You use an interactive rebase to change only the message of b2c3d4e to "Add database layer". Which commits on main get a new ID?

  1. None, because no file content changed
  2. All four, because rebase rewrites the whole branch
  3. That commit and every commit after it ("Add search route" and "Add tests")
  4. Only the commit whose message changed
Show answer

C. Each commit stores its parent's hash. A new message gives "Add database layer" a new ID. Then "Add search route" has a new parent hash, so it gets a new ID too, and the change carries on to the tip. That is why rewriting history changes every later ID. "Initial commit" is not touched, so B is wrong. A is wrong because the message is hashed as well as the files.

Quiz-style One byte flipped on disk

A disk error flips one byte inside a blob file under .git/objects. Which statements are true? Choose all that apply.

  1. Git can detect it, because the content no longer hashes to the object's name.
  2. The content still exists but the address is wrong, so the object can no longer be trusted.
  3. Git can't notice, because objects are looked up by file name.
  4. Content addressing is the same idea used for CDN cache keys and Merkle trees.
Show answer

A, B, D. An object's name is the hash of its content (id = SHA1(content)), so a change of one byte breaks the match and git fsck reports it. Git looks everything up by hash, not by file name (C). Because the name is derived from the content, you can check data without trusting whoever gave it to you.

Quiz-style Predict the diff

The committed steps.txt has 4 lines: a, b, c, d. You delete line b. What does git diff show (ignoring the header)?

  1. Nothing. Git stores diffs only for commits, not for the working tree.
  2. -a

-d
+a
+c
+d
  3.  a

  4.  a

Show answer

C. Myers finds the shortest edit script: one deletion, with the matching lines kept as context (diagonal moves cost 0). B is a valid edit script, but it is 7 edits, not the shortest. D makes no sense. A is wrong: git diff computes the change between the working tree and the staging area on demand.

Twist Two shortest scripts: which one does Myers pick?

Old file: x, y. New file: y, x. Two edit scripts of length 2 exist: (1) delete x, keep y, insert x; (2) insert y, keep x, delete y. Which statements are true? Choose all that apply.

  1. A replace-all script (delete both, insert both, d = 4) is equally good because the result is the same.
  2. Myers picks one at random each run, so the output can change.
  3. Both scripts are shortest (d = 2).
  4. Myers prefers deleting over inserting, so git shows -x, then y, then +x.
Show answer

C, D. When two scripts are equally short, Myers takes the deletion first. That gives the same output every run, so B is wrong. A gives the same file but is not the shortest edit script, and that is the only thing Myers looks for.

Drill Why git diff is fast on huge, almost identical files

Two versions of a 200,000-line file differ in 3 lines. Why does git diff answer at once?

  1. Git compares only the file sizes.
  2. Myers runs in O((m+n)·d) time, and d (the number of edits) is tiny here.
  3. Myers compares every line with every other line, O(m·n), and computers are fast.
  4. Git stored the 3-line diff when you committed.
Show answer

B. Myers's cost grows with the size of the edit script d. It follows the free diagonals (matching lines) and never walks one twice. Its memory is O(m+n). Git stores snapshots, not diffs (D). O(m·n log m) is roughly the older Hunt–McIlroy LCS approach (C). Sizes alone can't say which lines changed (A).

Quiz-style Why a three-way merge needs the base

You merge feature into main. Which statements about the three-way merge are true? Choose all that apply.

  1. A conflict means Git has crashed and the merge must be redone from scratch.
  2. Without the base, Git couldn't tell whether a line was added on one side or deleted on the other.
  3. If main edits line 10 and feature edits line 40, both changes are kept with no conflict.
  4. Git computes diff(base, main) and diff(base, feature) with the same diff engine.
  5. Git compares the two tips directly and makes a conflict wherever they differ.
Show answer

B, C, D. Two Myers edit scripts are made against the common ancestor. If they touch different regions, both apply cleanly. If both sides touched the same region, Git has two valid edits and no rule to choose, so it stops and asks you. That refusal is correct behaviour, not a crash (A). Comparing only the two tips (E) would make every difference look like a conflict.

Quiz-style Merge, rebase, squash: three claims about history

Which statements are true? Choose all that apply.

  1. A rebase keeps the original commit IDs and only moves the branch pointer.
  2. A merge keeps both timelines exactly as they happened, joined by a merge commit with two parents.
  3. A squash is a rebase whose commits are collapsed into one.
  4. A squash keeps each original commit on main, so git log still shows them one by one.
  5. A rebase replays your commits on a new base, which gives them new hashes and a straight line.
Show answer

B, C, E. Merge treats history as an accurate ledger. Rebase and squash treat it as a readable story. A replayed commit has a new parent, so it must get a new ID (A is wrong). A squash leaves one commit on main, and the individual commits are not part of main's history (D).

Twist Predict the graph after a rebase 
$ git log --graph --oneline --all
* 9c1d2e3 (HEAD -> feature) Add search box
* 7b2c3d4 Add search route
| * 4e5f6a7 (main) Fix footer typo
|/
* 1a0b2c3 Initial commit

You run git rebase main and there are no conflicts. Which statements are true? Choose all that apply.

  1. The new copy of "Add search route" has 4e5f6a7 as its parent.
  2. git log --oneline feature now lists: Add search box, Add search route, Fix footer typo, Initial commit.
  3. main still points to 4e5f6a7.
  4. Running git switch main, then git merge feature, is now a fast-forward.
  5. 9c1d2e3 is still reachable from feature.
Show answer

A, B, C, D. Rebase copies the two feature commits on top of main's tip, so feature now contains the footer fix and is a straight line ahead of main. Main itself does not move. The old commits get new IDs, so 9c1d2e3 is no longer on feature (E is wrong). You can only find it through the reflog until gc. Since main is now an ancestor of feature, merging just moves main forward.

Quiz-style Delete an unmerged branch, then gc

Branch exp has two commits that are on no other branch. Which statements are true? Choose all that apply.

  1. git branch -d exp refuses with "not fully merged".
  2. You can recover them with git branch exp <hash>, using a hash from git reflog.
  3. After git branch -D exp, the two commits are unreachable but still in the object database.
  4. git gc right after the delete removes them at once.
Show answer

A, B, C. Lowercase -d protects unmerged work, and capital -D forces the delete. Deleting a branch removes only the pointer file. The commits are unreachable but intact. They are also still referenced by the reflog, and gc only prunes them after its grace period (D is wrong). Pointing a new branch at the tip brings back both commits, because each commit links to its parent.

Drill Clean status, but teammates can't see it 
$ git status
On branch main
Your branch is ahead of 'origin/main' by 2 commits.
  (use "git push" to publish your local commits)

nothing to commit, working tree clean

Which statements are true? Choose all that apply.

  1. The working directory and the staging area disagree.
  2. The local repository and the remote disagree.
  3. git push sends the 2 commits and moves origin's main.
  4. git status just asked GitHub how many commits it has.
Show answer

B, C. "Working tree clean" means the first three locations agree. "Ahead by 2" compares your main with origin/main, which is your last downloaded copy of the remote. git status never contacts the server (D is wrong), so the count can be out of date until you git fetch. A is wrong because the tree is clean.

Quiz-style What fetch changes

You are on main with one local commit that isn't pushed and an unstaged edit to api.py. A teammate pushed 3 commits. You run git fetch origin. Which statements are true? Choose all that apply.

  1. Your local commit was uploaded too.
  2. origin/main now includes the 3 commits.
  3. git status may now say your branch and 'origin/main' have diverged.
  4. Your main is unchanged and api.py keeps your edit.
Show answer

B, C, D. Fetch only downloads, and it updates only the remote-tracking pointer. You have 1 commit they don't have, and they have 3 you don't, so the branches have diverged (1 and 3). Uploading is git push (A).

Twist git pull refuses on a diverged branch 
$ git pull
hint: You have divergent branches and need to specify how to reconcile them.
...
fatal: Need to specify how to reconcile divergent branches.

Your push was rejected earlier because main and origin/main diverged. Which commands integrate the teammate's work so that your next push is accepted? Choose all that apply.

  1. git fetch, then git merge origin/main, then git push
  2. git pull --rebase, then git push
  3. git pull --no-rebase (merge), then git push
  4. git push --force
Show answer

A, B, C. Recent Git versions don't guess between merge and rebase when the branches have diverged and no pull.rebase setting exists. You have to pick one. C and A make a merge commit with both commits. B replays your commit on top of theirs (it gets a new ID) and gives a straight line. A force-push overwrites origin's main and erases the teammate's commit (D).

Quiz-style Unstage, but keep the edit

You ran git add config.py secrets.txt. You want secrets.txt out of the next commit, but the file must stay on disk unchanged. Which commands do that? Choose all that apply.

  1. git reset secrets.txt
  2. git restore --staged secrets.txt
  3. git restore secrets.txt
  4. git rm secrets.txt
Show answer

A, B. Both copy the HEAD version back into the staging area and leave the working directory alone. git restore <file> (without --staged) does the opposite: it overwrites the working copy with the staged copy and leaves it staged (C). git rm deletes the file from disk and stages the deletion (D). To keep the file out of git for good, add it to .gitignore as well.

Quiz-style Predict status after reset --soft 
c3 (HEAD -> main) Add retry logic   # changed net.py
c2 Add client
c1 Initial commit

Nothing is pushed and the tree is clean. You run git reset --soft HEAD~1. What does git status show?

  1. main is at c2, the tree is clean, and the retry change is gone from disk
  2. main is still at c3, with a new commit that undoes c3
  3. main is at c2, and net.py is under "Changes not staged for commit"
  4. main is at c2, and net.py is under "Changes to be committed"

D. --soft moves only the branch pointer and keeps the staging area and files, so the change is staged and ready to commit again. C is --mixed (the default): pointer and staging area reset, files kept. A is --hard. B describes git revert.

Quiz-style A bad commit is already on shared main

Commit 8f2a1b0 on main broke checkout. It was pushed an hour ago, and three teammates have pulled since. Which statements are true? Choose all that apply.

  1. git revert 8f2a1b0, then git push, is the safe undo.
  2. The revert needs no force-push, because it only adds a commit.
  3. After the revert, 8f2a1b0 is still in history, followed by a new commit that undoes it.
  4. git reset --hard HEAD~1 then git push --force is just as safe, because it gives a cleaner history.
Show answer

A, B, C. Revert undoes the change by adding history, so everyone's clones stay consistent and the push is a fast-forward. Reset and force-push rewrite shared history (D). Teammates who already have 8f2a1b0 would bring it back on their next push, and any commit pushed after it would be lost.

Twist Two commits made on a detached HEAD

You ran git checkout v1.0 (a tag), then made commit d1 and then d2 (which has d1 as its parent). Then you ran git switch main. You want a branch hotfix that contains both commits. Which commands work? Choose all that apply.

  1. git switch -c hotfix
  2. git branch hotfix <hash of d1>
  3. git branch hotfix <hash of d2>
  4. git branch hotfix HEAD@{1}
Show answer

C, D. A branch at d2 includes d1, because d2's parent is d1. In the reflog, HEAD@{0} is the switch to main, so HEAD@{1} is where HEAD was just before: d2. A branch at d1 loses d2 (B). switch -c creates the branch at your current commit, which is main's tip (A).

Twist You rebased a branch you had already pushed

Only you work on feature/search. You pushed it, then ran git rebase main. Now git push is rejected (non-fast-forward). Which statements are true? Choose all that apply.

  1. git pull then git push is the cleanest fix.
  2. The push is rejected because the rebased commits have new IDs, so origin's tip is not in your history any more.
  3. The same move on shared main would be dangerous.
  4. git push --force-with-lease is the right fix here.
Show answer

B, C, D. Rebase made copies, so the old tip on origin is no longer an ancestor of yours. Since nobody else uses the branch, replacing it is fine, and --force-with-lease refuses if origin moved since your last fetch. Pulling (A) would merge the old copies back in, so every commit would appear twice. On a shared branch, rewriting history breaks everyone else's clones.

You have an unstaged edit to app.py and a brand-new untracked file notes.md. You run git stash. Which statements are true? Choose all that apply.

  1. notes.md stays in the folder, because untracked files are not stashed by default.
  2. The stash is pushed to origin so teammates can see it.
  3. app.py goes back to its last committed state.
  4. git stash pop re-applies the edit and drops that stash entry.

A, C, D. A stash is a local "desk drawer" for tracked changes. It saves both staged and unstaged changes. Untracked files need git stash -u. Stashes are never pushed (B).

$ cat price.py

Quiz-style .gitignore added too late

debug.log was committed last week. Today you add *.log to .gitignore, but git status still shows modified: debug.log. Which single step stops git from tracking it but keeps the file on disk?

  1. git rm --cached debug.log, then commit
  2. Nothing: wait, and .gitignore applies from the next commit
  3. rm debug.log
  4. git restore debug.log
Show answer

A. .gitignore only affects untracked files. Once a file is tracked, git keeps tracking it. rm --cached removes it from the staging area (so the next commit stops tracking it) and leaves it on disk. Old commits still contain it, which matters if it held a secret. D only throws away the current edits. C deletes the file and stages nothing.

You edited the tracked file app.py and created a new file util.py. You run git commit -am "Add helper". What happens?

Drill Which of these are integration tests?

Choose all that apply.

  1. A repository function saves a row to a real Postgres test database, then reads it back
  2. POST /api/users twice with the same email, against a disposable test database, expecting 409
  3. A browser opens /signup, creates an account, and lands on /dashboard
  4. calculate_gst(1000) returns 180
Show answer

A, B. Integration tests check real components working together: route, validation, ORM and database. D is a unit test (pure logic, no network or database). C is end-to-end (browser plus the whole stack). A duplicate-email check needs a real database to find the existing row, so it can't be a unit test.

Quiz-style Boundary cases for a range

Rule: "A username has 3 to 12 characters (inclusive)." Which input lengths are boundary cases? Choose all that apply.

  1. 7
  2. 13
  3. 2
  4. 3
  5. 12
Show answer

B, C, D, E. Each edge needs one test just outside it and one exactly on it: 2/3 at the bottom and 12/13 at the top. 7 is a normal (valid-class) case. It's worth having, but it is not on a boundary. Most real defects sit at these edges, such as > written where >= was meant.

Quiz-style 100% coverage, no assertion (pytest) 
def discount(total, is_member):
    if is_member and total > 100:
        return total * 0.9
    return total

def test_discount():
    discount(200, True)
    discount(50, False)

Which statements are true? Choose all that apply.

  1. If someone changed 0.9 to 0.5, this test would still pass.
  2. pytest marks this test as failed, because it contains no assert.
  3. Line coverage of discount is 100%.
  4. Adding assert discount(200, True) == 180 would catch the 0.5 change.
Show answer

A, C, D. Both paths of the if run, so every line executes. Coverage measures execution, not whether anything was checked. pytest passes a test that finishes without an exception, so B is wrong. That is exactly why this test proves nothing. An assertion on the result turns it into a behavioural claim.

Twist A mutant that survives 
# original
def can_vote(age): return age >= 18
# mutant made by the tool
def can_vote(age): return age > 18

def test_child(): assert can_vote(10) is False
def test_adult(): assert can_vote(30) is True

Which statements are true? Choose all that apply.

  1. A surviving mutant proves the original code has a bug.
  2. The mutant survives: both tests still pass against it.
  3. Adding assert can_vote(18) is True kills the mutant.
  4. Line coverage is 100%, so the suite is strong.
Show answer

B, C. 10 and 30 give the same answers under >= and >. Only the boundary value 18 tells them apart. A surviving mutant means the tests can't distinguish the change. It says nothing about a bug in the original code (A). Full coverage with a surviving mutant is exactly the blind spot coverage has (D).

Quiz-style Name the test double

(1) A class with save() and find() that keeps users in a Python dict. (2) A function that always returns the exchange rate 83.0. (3) An object the test checks with email.send.assert_called_once_with("a@x.com"). Which line names them correctly?

  1. (1) stub, (2) mock, (3) fake
  2. (1) fake, (2) stub, (3) mock
  3. (1) mock, (2) fake, (3) stub
  4. All three are mocks. The words mean the same thing.
Show answer

B. A fake is a working but simplified implementation (an in-memory database). A stub returns a fixed, canned value. A mock records how it was called, so the test can assert on that call. Use a double only at a slow, unsafe, costly or external boundary, never in place of the behaviour the test claims to prove.

Quiz-style Over-mocked signup test 
def test_register():
    repo = Mock()
    register(repo, {"email": "a@x.com", "password": "short"})
    repo.save.assert_called()

register is supposed to reject passwords under 8 characters. The test passes. Which statements are true? Choose all that apply.

  1. The test passing shows register saves a user with a 5-character password, which is the bug.
  2. Replacing the Mock with a real production database would make it a better unit test.
  3. A behaviour-focused test would assert that the short password is rejected and that no user is stored.
  4. The test proves only that save was called, not that registration behaves correctly.
Show answer

A, C, D. The test asserts that an interaction happened, so it actually locks in the buggy behaviour. A good test states the rule: invalid input, then rejected, then nothing persisted (an in-memory fake makes the "nothing stored" part checkable). Automated tests must never use production data (B). The integration level uses a disposable test database.

A seeded defect: is_valid_length("abcdefgh") returns False (8 characters should be valid). The milestone wants it fixed in two commits. Which statements are true? Choose all that apply.

Rapid-fire facts

Read these the night before and again just before the quiz. Each one has decided a multiple-choice option before.

Git internals and history

  • Git = a DAG of content-addressed objects: blob, tree, commit, tag
  • Object id = hash of its content. Change 1 byte and you get a new object with a new id
  • A blob has no name. The tree holds names and modes
  • A commit = tree + parent(s) + author/committer + message. It is a snapshot, not a diff
  • A branch = a small file holding one hash. Committing overwrites only that file
  • Change one commit and it and every later commit get new IDs
  • Amend or rebase = new commits. The old ones stay (reflog) until gc's grace period
  • Myers = shortest edit script, O((m+n)·d) time, O(m+n) memory, git's default
  • On a tie, Myers prefers delete over insert
  • 3-way merge = diff(base,ours) + diff(base,theirs). Same region on both sides = conflict
  • Merge = accurate ledger (2-parent commit). Rebase = readable story (new hashes, straight line)
  • Squash = rebase with the commits collapsed into one
  • Rebase moves only the branch you're on. main stays put
  • git branch -d refuses unmerged work. -D forces it

Remotes, undo and recovery

  • Four locations: working dir, staging, local repo, remote
  • git status never contacts the remote. "ahead/behind" uses the last fetch
  • fetch = download + move origin/main only. pull = fetch + integrate
  • Diverged + plain git pull = "Need to specify how to reconcile". Use --no-rebase or --rebase
  • Rejected push: integrate first. Never --force on shared main
  • restore f = staged copy goes to the working dir. restore --staged f = unstage
  • reset --soft keeps staged, --mixed keeps files, --hard discards
  • Pushed bad commit: git revert (adds an undo commit)
  • Lost commit: git reflog, then git branch name <hash>
  • After switching away, HEAD@{1} = where HEAD was just before
  • Rebased your own pushed branch: push --force-with-lease
  • commit -a skips untracked files. stash skips untracked unless -u
  • .gitignore ignores only untracked files. Use git rm --cached to stop tracking

Testing and CI

  • Arrange, Act, Assert. No assertion = no behavioural check
  • pytest passes a test with no assert if it doesn't raise
  • Cases: normal, boundary (just below and exactly on), invalid/missing, error
  • Unit = pure logic. Integration = real components + DB. E2E = browser journey
  • Pyramid: many unit, some integration, few E2E. It is a budget, not a law
  • Coverage = lines/branches/functions executed, not asserted
  • Mutation testing: a surviving mutant means the tests can't tell the change apart
  • Stub = canned value. Fake = working simplified version. Mock = records calls
  • Tests must be independent, clean up after themselves, and be deterministic (no uncontrolled clock or network)
  • Bug fix = commit 1 failing test (red), commit 2 fix (green)
  • CI = validate, build, test, report status on a change. CD = deliver/deploy
  • A failing step fails the job, and later steps are skipped
  • continue-on-error: true lets the job pass anyway
  • Gate = pull_request trigger + required status check in branch protection
  • Clean runner = only declared dependencies. Read the first meaningful error

Containers and Docker

  • docker logs shows only stdout and stderr of the main process. Log files inside the container are invisible to it
  • ENTRYPOINT = fixed program. CMD = default args. Words after the image name replace CMD
  • Exit 137 = SIGKILL (OOM kill, or docker stop after 10 s). Exit 143 = SIGTERM. Check OOMKilled to tell
  • Default bridge: no DNS by container name. User-defined network: reach others by name on their container port
  • Empty named volume is pre-filled from the image once. A bind mount hides the image's folder
  • RUN rm doesn't remove a file from earlier layers. ENV and used ARG values show in docker history
  • Container = isolated process(es) on the shared host kernel. A VM has its own kernel
  • Namespaces = what you see (PID, mount, net, hostname, user)
  • cgroups = how much you use: over CPU = throttled, over memory = may be killed
  • Main process is PID 1 inside, with a different PID on the host
  • Image layers are read-only and shared (copy-on-write). Each container has its own writable layer
  • A changed input invalidates that step and all steps after it
  • Copy manifests, then install, then copy source. CMD only records metadata
  • COPY cache uses file contents, not timestamps. .dockerignore trims the context
  • npm ci installs exactly the lockfile and fails on a mismatch
  • EXPOSE documents only. -p host:container publishes
  • -p 127.0.0.1:8080:3000 = this machine only. Without the prefix = all interfaces
  • Server inside must listen on 0.0.0.0, not 127.0.0.1
  • stop/start keeps the writable layer. rm deletes it
  • A named volume outlives containers. Only the mounted path is kept
  • New image = new container (rm + run). restart reuses the old image

Database migrations

  • History row: installed_rank, version, description, type, script (file name), checksum, installed_by, installed_on, execution_time, success. No SQL text
  • Versions compare as numbers, part by part: 1.9 < 1.10 < 2 < 10. File dates never matter
  • R__ repeatable: no version, runs after the versioned ones, reruns when its checksum changes (Outdated, then the old row becomes Superseded)
  • New file below the applied version = Ignored, and migrate refuses. -outOfOrder=true runs it, and the state is Out of Order
  • Deleted applied file: in the middle = Missing (validate fails), above the newest file = Future (warning only). repair marks Missing as Deleted
  • baseline defaults to version 1: set -baselineVersion. clean drops everything and is disabled by default
  • Code, schema and data change independently. Code is reversible, data often isn't
  • Auto-sync rename = drop + add an empty column. Prototype only
  • Runner: read history, run pending files in order, insert a history row, COMMIT
  • History = append-only, ordered, checksum-verified
  • Edited applied file = checksum mismatch, deploy stops before running anything
  • flyway repair fixes checksums and runs no SQL
  • Hand-run SQL = schema changed, no history row, migration still pending
  • Postgres DDL is transactional. Killed before COMMIT = it reruns cleanly
  • Error inside BEGIN: transaction aborted. COMMIT then rolls back
  • Without BEGIN each statement autocommits
  • ADD COLUMN needs ACCESS EXCLUSIVE. It waits for open readers, and later readers queue behind it
  • Locks are held until the transaction ends. lock_timeout limits only the wait
  • PG 11+: constant default = fast. Volatile default (clock_timestamp(), gen_random_uuid()) = full rewrite
  • Down migration can't restore deleted values, only a backup can
  • Expand, backfill, transition, contract. Irreversible at contract (drop)
  • Required column: nullable, writes supply it, batched backfill, CHECK NOT VALID, VALIDATE, SET NOT NULL
  • Use timestamp versions so two branches don't collide
  • PITR = physical base backup + archived WAL. A replica is not a backup. RPO = data loss, RTO = time

Architecture

  • Network call costs: partial failure, retries plus idempotency, distributed transactions, no debugger
  • Timeout = unknown outcome. Retry only idempotent calls, and send an idempotency key
  • 8 fallacies: reliable, zero latency, infinite bandwidth, secure, fixed topology, one admin, zero transport cost, homogeneous
  • Conway's Law: systems copy org communication. Microservices apply it in reverse
  • Monolith First: split only on measured pain (~50+ engineers, very different scaling)
  • Modular monolith = one deployable, enforced boundaries, ACID easy, no network tax
  • Modules talk via public APIs/events, never another module's tables
  • Boundary enforced in CI (Packwerk), not by comments
  • DDD: ubiquitous language, bounded context, context map
  • Five module tests: responsibility, language, rules, data, contract
  • A unique noun or a shared table does not make a module
  • Prime Video: per-transition billing + S3 relay, fixed by one process with in-memory transfer
  • Serverless + Postgres: one connection per invocation exhausts the limit. Use pooling

Architecture and hosting (T4L1, T4L2)

  • A network call is a function call that can fail halfway, silently, on someone else's clock. Its tax: partial failure, retries plus idempotency (one key per payment, reused on every retry), no distributed transactions, no local debugger
  • Fallacy traps: "transport cost is zero" = money (every GB across a region is billed). "Homogeneous" = hardware, kernels, MTUs. Latency (time) and bandwidth (pipe size) are separate fallacies
  • Conway (1967): systems copy the org's communication. Microservices = Conway in reverse, for team velocity, "not for scalability alone". Two-pizza teams = small, accountable, agile
  • Microservices tax: one request, a dozen logs; distributed transactions nearly impossible; one service down, three slow; huge orchestration overhead. All services calling all = distributed, tightly coupled monolith
  • Prime Video (2023): -90% cost by moving Step Functions (billed per state transition) + S3 relays to one process on EC2/ECS. Vogels: "a strategy, not a religion"
  • Shopify = modular monolith: 173B requests over Black Friday weekend, 284M req/min peak, 12 TB/min. Packwerk in CI fails the build. Contracts: placeOrder()/OrderPlaced, getKitchenStatus()/OrderReadyForPickup, assignRider()/DeliveryCompleted
  • Hosting spectrum: VM → container PaaS → managed containers → serverless. Choose by who operates what. "No column wins every row". PaaS = lowest to start; serverless = per invocation + duration, higher lock-in
  • Compute and database are separate decisions. Managed DB gives backups, patching, failover. Still yours: schema, access rules, credentials, restore tests
  • Demo A: -p 127.0.0.1:8000:8000 (not public), Caddy on 443 forwards inward, ufw allow 22,80,443/tcp, DNS A record before the TLS certificate. New env file = docker rm -f + docker run --env-file (restart keeps the old env)
  • Restart policy = supervisor for one host, not an orchestrator. Recovers: crashed process, host reboot. Not: lost VM, crash on every start (loop, no alert), cert/disk/patches, nobody told. docker stop by hand stays stopped
  • Ladder: systemd (one process) → Docker restart policy (one host) → Kubernetes/Swarm (many hosts, desired state) → managed platform. Four jobs: failure detection, scheduling, placement/startup, routing/service discovery. Desired − observed = actions
  • Liveness (/healthz, no DB) fails → restart. Readiness fails → stop routing, no restart (LBs use it). Startup = wait while booting. Scale out needs a load balancer + stateless servers. Trace: 2,300 of 2,319 ms in DB, "waiting for a free connection" (pool max_size=5 per instance)

Safe delivery and the database under load (T5, T6)

  • Time to recover = detect + decide + act. TiffinGo: 7 + 2 + 1 min (19:02 → 19:09 → 19:11 → 19:12). "Most outages are long because nobody noticed"
  • Pipeline order: Test → Build → Migrate → Deploy → Check health. Old code still serves during the migration, so every migration must work with the old code
  • CI runner: a fresh computer, starts empty, deleted at the end. A non-zero exit code stops the job. Secrets come from the repository's settings, never from the code
  • Build the image once, tag it with the commit id (tiffingo:3f9a2c1), and run that same image in staging and production. Rebuilding can give a different image
  • Three ways back: flag off = seconds (nothing deployed), previous image = ~1 min (nothing rebuilt), revert the commit = minutes (the pipeline runs again)
  • "Code is reversible. Data is not. Sent messages are forever." Redeploying 2.3 after the items → order_items rename: checkout fails on 2.3 too. Fix forward
  • Demo: /healthz only runs SELECT 1, so it says "ok" while checkout fails. rollback.sh never touches the database. A failed gate prints "Production is unchanged", but a migration that already ran stays
  • Percentage rollout: hash(user_id) % 100 < 10, not random() < 0.1. Demo: sha256(flag + ":" + user), first 4 bytes, % 100. Raising the % never turns anyone off. Put the flag name in the hash, or every flag hits the same users (978 overlap vs 99)
  • Flags: kill switch, percentage, targeted (Pune first). Reading on every request lands changes at once. A 30 s cache means up to 30 s delay. Every flag needs an owner and a removal date. At 100%, delete the flag and the old code path
  • Knight Capital, 1 Aug 2012: a reused flag name, 1 of 8 servers didn't get the new code, ~$440M in 45 min. Blue-green = switch all at once (old kept warm). Canary = 5% first, then grow only if healthy. In both, readiness checks decide which servers get traffic
  • N+1 = 1 query for the list + 1 per row. 50 rows = 51 queries. 51 × 30 ms ≈ 1.5 s in production, about 51 ms on a laptop. Fix: a JOIN or = ANY($1), so 1 or 2 trips
  • No index = Seq Scan (reads every page). B-tree = a handful of steps. EXPLAIN after the index: Index Scan + Index Cond. Index (a, b) helps a, or a + b, but not b alone. Every index slows every insert and update. Plain CREATE INDEX blocks writes. CONCURRENTLY doesn't, but can't run in a transaction

Serverless: 200 × 5 = 1,000. A pooler in transaction mode loses prepared statements and session locks. Busy 50% = short queue, 90% = long, 99% = explodes
