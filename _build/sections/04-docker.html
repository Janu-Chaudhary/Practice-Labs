Topic 4

Docker: build, run, publish, persist

Build an image from a Dockerfile, run it with the right ports and volumes, and debug it when curl gets nothing.

Mental model

Image = an immutable, tagged stack of read-only layers plus a default command (a recipe that is already cooked). Container = a running instance of an image: ordinary Linux processes, plus their own namespaces, cgroup limits and a thin writable layer on top. Volume = Docker-managed storage with its own lifecycle: it outlives any container. Namespaces = what a process can see (own PIDs, own filesystem, own network). cgroups = how much it can use (CPU, memory). All containers share the host's kernel. Every command in this topic is one of: make an image (build), make a container (run), look at it (ps, logs, exec, inspect), or remove things (stop, rm, image rm, volume rm).

docker build: the trailing dot

In Quiz 2 Q14, docker build -t counter:1.0 (no dot) scored 0. The dot is not decoration. It is the build context: the folder Docker packs up and sends to the builder. Every COPY in the Dockerfile copies from the context. No context, no build. Docker also looks for the file called Dockerfile inside the context unless you say otherwise with -f.

docker build -t counter:1.0 .
  1. the command: turn a Dockerfile into an image
  2. -t name:tag = the image's name and version. Name must be lowercase. No tag means :latest.
  3. . = build context = "this folder" (the one you are standing in). Required. It is the one argument the error message talks about.
docker build -t hello-cli:dev -f Dockerfile.dev .
  1. build
  2. tag
  3. -f = which Dockerfile to read (default: ./Dockerfile)
  4. the context is still needed: -f picks the recipe, . gives the ingredients

docker image ls (or docker images)list images; docker image ls app shows only that repository
docker image rm app:1.0 (or docker rmi)delete an image tag. Fails if a container (even stopped) uses it.

Dockerfile instructions and the layer cache

A Dockerfile is a list of steps. Most steps create a layer. Layers are read-only and shared: 100 containers from one image use the same layers on disk (copy-on-write); each container only adds its own thin writable layer.

InstructionWhat it does
FROM node:24-alpinethe base image: user space + Node runtime. Always first.
WORKDIR /app"cd" for all later steps (created if missing). Relative paths like ./ mean /app/.
COPY package.json package-lock.json ./copy files from the build context into the image
RUN npm ci --omit=devruns at build time; its result is saved as a layer
ENV MODE=devenvironment variable baked into the image (override at run with -e)
EXPOSE 3000documents the port. It does not publish it. Only -p on docker run publishes.
CMD ["node", "server.js"]the default command when a container starts. Not run at build time. Replaced by any command typed after the image name in docker run.

The cache rule: a changed input invalidates that step and every step after it. So put what changes rarely (dependency manifests and the install) before what changes often (your source).

# GOOD ORDER (the slide / Quiz 2 Q15 answer)
FROM node:24-alpine
WORKDIR /app
COPY package.json package-lock.json ./   # 1. only the manifests
RUN npm ci                               # 2. install; cached while the manifests don't change
COPY . .                                 # 3. source last: editing server.js only reruns from here
EXPOSE 3000
CMD ["node", "server.js"]
# after editing only server.js:
$ docker build -t shop-api:1.0 .
#6 [2/5] WORKDIR /app
#6 CACHED
#7 [3/5] COPY package.json package-lock.json ./
#7 CACHED
#8 [4/5] RUN npm ci
#8 CACHED
#9 [5/5] COPY . .                                  # reruns (its input changed)
Why

RUN npm ci before COPY package*.json fails: when the RUN step executes, /app is empty, so there is no lockfile. COPY . . before RUN npm ci builds, but every server.js edit changes the input of COPY . ., so npm ci reruns every time (slow). npm ci installs exactly what package-lock.json pins, and refuses to run without it.

.dockerignore lists what to leave out of the build context, like .gitignore. Typical: node_modules, .git, .env, data. Keeps secrets out of the image, keeps the context small, and stops your laptop's node_modules from overwriting the one built inside the image by COPY . ..

npm error The `npm ci` command can only install with an existing package-lock.json or
npm error npm-shrinkwrap.json with lockfileVersion >= 1.
ERROR: failed to build: failed to solve: process "/bin/sh -c npm ci" did not complete successfully: exit code: 1

Means: the lockfile isn't in the image when RUN npm ci runs (wrong step order, or the lockfile is missing from the folder / excluded by .dockerignore).

Fix: COPY package.json package-lock.json ./ before RUN npm ci.

docker run: options before the image, command after

docker run = create a new container from an image and start it. Each run makes a new container with a fresh, empty writable layer.

docker run -d -p 8080:3000 -v counter-data:/data --name counter counter:1.0
  1. create + start a new container
  2. -d = detached: run in the background, print the container id, give the terminal back
  3. -p HOST:CONTAINER = publish: traffic to host port 8080 goes to container port 3000
  4. -v VOLUME:/path = mount the named volume counter-data at /data inside
  5. --name = a name to use instead of the id (must be unique among all containers)
  6. the image. Everything after this word is the command to run inside the container, replacing CMD.
Trap: options after the image

docker run -d counter:1.0 -p 8080:3000 -v counter-data:/data does not publish anything. -p 8080:3000 -v ... becomes the container's command. With node images it runs node -p 8080:3000 -v ..., prints the Node version and exits: docker ps is empty, docker ps -a says Exited (0), docker logs shows v24.x.x. With alpine: exec: "-p": executable file not found in $PATH. Rule: docker run [options] IMAGE [command].

OptionWhat it does / why
-dbackground. Without it your terminal shows the app's output; Ctrl+C stops the app.
-p 8080:3000publish on every host interface (PORTS shows 0.0.0.0:8080->3000/tcp). Order: host first.
-p 127.0.0.1:8080:3000publish only on the host's loopback: reachable from this machine only, not from the network
-p 127.0.0.1::3000let Docker pick a free host port (see it with docker port NAME)
--name webname the container
-e KEY=valueset an environment variable inside (config, not baked in the image)
-v data:/dataleft side is a name (no /) = named volume
-v "$(pwd)"/data:/dataleft side is a path = bind mount of a host folder
--mount type=volume,src=data,dst=/datalong, explicit form of the named volume (no spaces after commas!)
--mount type=bind,src="$(pwd)"/data,dst=/datalong form of a bind mount (path must exist)

$ docker run --rm -it --name pid1 alpine:3.24 sh

Trap: redirects run on the host

docker run --rm -v notes-data:/data alpine:3.24 echo hi > /data/x.txt: your host shell does the > before Docker even starts: bash: /data/x.txt: No such file or directory. Put it inside: ... alpine:3.24 sh -c 'echo hi > /data/x.txt'.

Ports: ps, EXPOSE vs -p, 0.0.0.0 vs 127.0.0.1, curl

A request from your laptop goes: curl -> host port -> published-port rule -> container's own IP : container port -> the server, which must be listening there.

$ docker ps

Trap: the server listens on 127.0.0.1 inside the container

Quiz 2 Q5. docker ps looks perfect (0.0.0.0:8080->3000/tcp) but curl says (52) Empty reply from server or Connection reset. Inside a container, 127.0.0.1 is the container's own loopback (its own network namespace). Forwarded traffic arrives on the container's network address, so a server bound to 127.0.0.1 never sees it. Fix the app to listen on 0.0.0.0, rebuild, and recreate the container. Adding EXPOSE changes nothing.

Tip

Two different "127.0.0.1"s: -p 127.0.0.1:8080:3000 limits the host side (good, safe). listen(3000, "127.0.0.1") in the app limits the container side (bad: unreachable). Check what the app says with docker logs NAME.

Storage: writable layer, volumes, bind mounts, what survives

Files a container writes go to its private writable layer, unless the path is a mount. The writable layer lives exactly as long as the container. A named volume lives until you docker volume rm it.

ActionWritable layer (e.g. /tmp/session.log)Named volume (e.g. /data/count.txt)
docker stop then docker startkept (same container)kept
docker restartkept (same container)kept
docker rm + a new docker rungone (new container, empty layer)kept: the new container sees it again
docker volume rm-gone (refused while any container, even stopped, uses it)
CommandWhat it does
docker volume create counter-datamake a named volume
docker volume lslist volumes
docker volume inspect counter-datadetails; Mountpoint = where Docker keeps it on the host (/var/lib/docker/volumes/...)
docker volume rm counter-datadelete it and its data, permanently
docker run --rm -v counter-data:/data alpine:3.24 cat /data/count.txtpeek into a volume with a throw-away container
Why named volume vs bind mount

Named volume: Docker manages where it lives; lifecycle separate from containers; use for app data (databases, counters). Bind mount: a specific host folder mapped in; use in development when the host path itself matters (live-edit code). -v name:/data vs -v /abs/path:/data: a leading / (or ./, $(pwd)) silently switches to a bind mount.

Common errors, decoded

ERROR: docker: 'docker buildx build' requires 1 argument

Means: no build context given.

Fix: add . at the end: docker build -t counter:1.0 .

docker: Error response from daemon: ... Bind for 0.0.0.0:8080 failed: port is already allocated

Means: another running container already publishes host port 8080. Docker has already created your new container (status Created) before failing.

Fix: docker ps to find who holds 8080; docker stop or docker rm -f it (or use another host port if allowed); then docker rm your half-made container and run again.

docker: Error response from daemon: Conflict. The container name "/orders" is already in use by container "8da5...". You have to remove (or rename) that container to be able to reuse that name.

Means: a container with that name exists, maybe stopped or Created (docker ps -a).

Fix: docker rm orders (or rm -f if running), then run again. docker start orders would restart the old container, not a new one from a new image.

Unable to find image 'countr:1.0' locally
docker: Error response from daemon: pull access denied for countr, repository does not exist or may require 'docker login'

Means: no local image with that exact name:tag, so Docker tried to download it from Docker Hub and it doesn't exist there either. Usually a typo, a wrong tag, or you never built it.

Fix: docker image ls, use the exact name:tag (or build it first).

ERROR: failed to build: invalid tag "Counter:1.0": repository name must be lowercase

Means: image names must be lowercase (tags may have letters, digits, . _ -).

Fix: -t counter:1.0.

node: bad option: --name        (in docker logs; container Exited)
exec: "--name": executable file not found in $PATH

Means: you put options after the image name; they became the command.

Fix: docker rm it, then put every option before the image.

Error response from daemon: remove counter-data: volume is in use - [8dbd4e17...]
Error response from daemon: conflict: unable to delete counter:1.0 (must be forced) - image is being used by stopped container 8dbd4e17

Means: a container (even a stopped one) still uses it.

Fix: docker rm -f the container first, then remove the volume / image.

invalid argument "type=volume," for "--mount" flag: invalid field '' must be a key=value pair

Means: spaces after commas in --mount split it into separate words.

Fix: --mount type=volume,src=data,dst=/data with no spaces.

curl: (7) Failed to connect to localhost port 8080: Connection refused
curl: (52) Empty reply from server

Means: (7) nothing published on that host port (no -p, wrong port, or container not running). (52)/(56) the port is published but the app inside listens on 127.0.0.1 or crashed.

Fix: check docker ps PORTS, then docker logs.

The Dockerfile is FROM / WORKDIR /app / RUN npm ci / COPY package.json package-lock.json ./ / COPY . . / EXPOSE 3000 / CMD. The build fails. Only reorder lines so it builds and a server.js-only change doesn't rerun npm ci. Build shop-api:1.0. Don't run a container.

npm ci needs the lockfile in the image first. Source is copied last so its changes only invalidate COPY . . and later steps.

Drill Which steps rerun?

Dockerfile: FROM node:24-alpine, WORKDIR /app, COPY package.json package-lock.json ./, RUN npm ci --omit=dev, COPY server.js ./, CMD ["node","server.js"]. (a) You edit server.js. (b) You add a dependency (package.json + lockfile change). What reruns in each case?

Show answer

(a) COPY server.js ./ and everything after it (CMD only records metadata). (b) COPY package.json package-lock.json ./, RUN npm ci, COPY server.js and the rest: a changed input invalidates that step and every step after it. FROM and WORKDIR are cached in both.

Quiz-style What is the count after rm?

docker run -d --name c -v t3data:/data counter:1.0. Three requests: count.txt = 3, and each request also writes a line to /tmp/session.log. You docker rm -f c and run the same command again, then send one request. Count? Old log lines? And what if you had done docker stop c + docker start c instead?

Show answer

After rm + run: count=4 (the volume survived), old log lines are gone (/tmp was in the deleted writable layer). After stop + start: count=4 and the log lines are still there (same container, same writable layer).

Twist Up, published, still unreachable

docker run -d -p 8080:3000 --name web app:1.0. docker ps shows 0.0.0.0:8080->3000/tcp, but curl localhost:8080 gets an empty reply. docker logs web says listening on 127.0.0.1:3000. Fix it.

Show answer
# in server.js: .listen(3000, "0.0.0.0")
$ docker build -t app:1.1 .
$ docker rm -f web
$ docker run -d -p 8080:3000 --name web app:1.1
$ curl localhost:8080

127.0.0.1 inside the container is the container's own loopback. A new image needs a new container: restart would reuse the old image.

Twist Port taken and name taken

orders-old (v1) is running on 8090. A stopped container named orders exists. Run orders:2.0 as orders on 8090 -> 3000. Keep orders-old (stopped) for its logs.

Show answer
$ docker stop orders-old           # frees port 8090, keeps container + logs
$ docker rm orders                  # frees the name
$ docker run -d --name orders -p 8090:3000 orders:2.0

Ports belong to running containers; names belong to all containers. If you run first, you get Conflict ... name already in use, then port is already allocated (which leaves a Created container you must rm).

Drill Namespaces or cgroups?

docker run -d --cpus=0.5 --memory=512m --name api api:1.0. (a) Inside, what PID does the main process have? (b) It wants 2 CPUs. (c) It allocates 1 GB. (d) What hides the host's other processes?

Show answer

(a) PID 1 inside (PID namespace); another PID on the host (docker top api). (b) Throttled: keeps running, slower. (c) The kernel may kill it (OOM), not just slow it. (d) Namespaces (what you see), not cgroups (how much you use).

Quiz-style The password is in the image

A teammate's Dockerfile has ENV DB_PASSWORD=Summer2024! and COPY . ., and there is no .dockerignore. The project folder has a .env with DB_HOST and DB_PASSWORD. They built pay:1.0. (a) Show two ways to read the password from the image. (b) Fix the build and build pay:1.1. (c) Run it as pay on host 8080 -> 3000 with the settings from .env, using one flag. (d) Remove the leaky tag.

Show answer
$ docker history --no-trunc pay:1.0 | grep ENV      # ENV DB_PASSWORD=Summer2024!
$ docker run --rm pay:1.0 cat /app/.env              # COPY . . copied .env in
# delete the ENV DB_... lines from the Dockerfile, then:
$ printf '.env\nnode_modules\n.git\n' > .dockerignore
$ docker build -t pay:1.1 .
$ docker run -d --name pay -p 8080:3000 --env-file .env pay:1.1
$ docker image rm pay:1.0

ENV (and ARG) values are recorded in the image metadata and in docker history. COPY . . copies everything in the build context that .dockerignore doesn't exclude. A later RUN rm .env doesn't help: the file stays in the earlier layer. Config and secrets go in the environment at run time (--env-file or -e), so one image runs anywhere. Lab 10.

Twist web can't reach api on localhost

api runs with -p 8119:3000. web runs with -e API_URL=http://localhost:8119 -p 8111:3000. From your laptop, curl localhost:8119 works, but web logs ECONNREFUSED. Make web reach api by name, and make api internal only (no host port).

Show answer
$ docker network create appnet
$ docker rm -f api web
$ docker run -d --name api --network appnet api:1.0
$ docker run -d --name web --network appnet -p 8111:3000 -e API_URL=http://api:3000 web:1.0
$ docker exec web wget -qO- http://api:3000/stock     # debug from inside

Inside a container, localhost is that container (its own network namespace). 8119 is a host port; container-to-container traffic uses the container port. Names resolve only on a user-defined network, not on the default bridge. Env, ports and networks are fixed at create time, so recreate (restart keeps the old ones). Lab 11.

Twist It exits right after docker run

docker run -d --name report -p 8112:3000 report:1.0 prints an id, but docker ps is empty. The app needs /config/settings.json, which ops keeps on the host in ./config/ and wants to edit without rebuilding. (a) How do you find the reason and the exit code? (b) Run it correctly, config read-only. (c) Ops changes the title in the file. What must you do so the app shows it?

Show answer
$ docker ps -a                                   # report  Exited (3)
$ docker logs report                             # FATAL: cannot read /config/settings.json (ENOENT)
$ docker inspect -f '{{.State.ExitCode}}' report  # 3
$ docker rm report
$ docker run -d --name report -p 8112:3000 -v "$(pwd)/config":/config:ro report:1.0
# (c) after editing config/settings.json on the host:
$ docker restart report

-d only says the container started; the main process exiting ends it. Logs survive on stopped containers. A left side starting with / is a bind mount (a host folder you choose); -v config:/config would create an empty named volume instead. The container sees the edited file immediately, but this app reads it only at start, so restart. Mounts can't be added to an existing container: rm + run. Lab 12.

Twist Prove the cache, then retag

The Dockerfile is FROM / WORKDIR /app / COPY . . / RUN npm ci / CMD, and the folder has a 30 MB logs/ and a laptop node_modules/. Make server.js edits skip npm ci (you may add lines), keep the junk out, build shop:1.2 saving the plain build output to build.log (and on screen), point shop:latest at 1.2 without rebuilding, and delete shop:1.0.

Show answer
FROM node:24-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "server.js"]
$ printf 'logs\nnode_modules\n.git\n.env\n' > .dockerignore
$ docker build --progress=plain -t shop:1.2 . 2>&1 | tee build.log
#8 [4/5] RUN npm ci --omit=dev
