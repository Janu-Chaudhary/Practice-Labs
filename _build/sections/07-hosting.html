Topic 7

Hosting, restart policies, health checks and module boundaries

Run a service the way the T4L2 demo does, pick the right restart policy, write health checks that don't cause restart storms, make an app safe to scale out, and fix a module-boundary violation (T4L1).

Mental model

Three questions: where does it run (VM, container PaaS, managed containers, serverless), who keeps it running, and why that choice. "Who keeps it running" is a ladder: systemd = one process. Docker restart policy = one host. Orchestrator (Kubernetes, Swarm) = many hosts, desired state. Managed platform = the provider runs the control plane. A restart policy brings a crashed process back. It can't move the app if the VM dies. Config and secrets live in the environment (--env-file), never in the image. Liveness (/healthz) must not touch the DB; readiness (/readyz) does. To scale out, app servers must be stateless: state goes to a shared store (Postgres), not process memory. Inside one deployable (modular monolith), modules talk only through public APIs, and a CI check enforces it.

docker run like the demo: restart, loopback port, env file

This is the one command the demo uses to put hello-api on the VM (Step 3 + Step 5). Every flag answers a hosting question: background, fixed name, who restarts it, who can reach it, where its config comes from.

docker run -d --name hello-api --restart unless-stopped -p 127.0.0.1:8000:8000 --env-file /etc/hello-api.env ghcr.io/acme/hello-api:1.0
  1. start a container in the background (detached), give the terminal back
  2. a fixed name, used by docker logs/rm/inspect hello-api
  3. restart after a crash and after a Docker/host restart, but not after you stopped it
  4. HOST_IP:HOST_PORT:CONTAINER_PORT. 127.0.0.1 = only this machine can connect. The reverse proxy (Caddy) on 80/443 is the public door.
  5. read every KEY=value line of a host file into the container's environment (secrets stay out of the image)
  6. the image (registry/owner/repo:tag). Always after all options.

Restart policies: a supervisor for one host

PolicyRestarts when...Use for
no (default)neverone-off commands, --rm tools
on-failure / on-failure:5the process exits with a code that is not 0 (max 5 tries)jobs: migrations, batch work. Retry on failure, stay finished after success.
alwaysany exit. A container you stopped by hand comes back when the Docker daemon restarts.rarely what you want
unless-stoppedany exit and after a daemon/host restart, unless you stopped itlong-running services (the demo)
docker update --restart unless-stopped lab72-api
  1. change settings of an existing container (no recreate)
  2. the new policy (also works for CPU/memory limits; NOT for ports, env, volumes)
  3. the container
$ docker exec lab72-api pkill -9 node      # fake a crash, like the demo's sudo pkill -9
$ docker ps --filter name=lab72-api
... Up 2 seconds ...                        # Docker brought it back
$ docker inspect -f '{{.RestartCount}}' lab72-api
1
$ docker stop lab72-legacy                  # --restart always, but...
$ docker ps -a --filter name=lab72-legacy
... Exited (143) ...                        # ...stays stopped: docker stop is never undone
Trap

docker stop and docker kill both count as "stopped by hand". Docker will not restart after them, whatever the policy. A crash is the process dying on its own. docker restart also doesn't raise RestartCount.

Trap

always/unless-stopped on a job that exits 0 makes it run again and again. A crash on every start gives a restart loop and no alert. Nobody is told.

Why it's not an orchestrator

One VM + unless-stopped covers: process crash ✓, host reboot ✓. It does not cover: VM lost ✗, crash loop ✗, full disk / expired cert ✗. Surviving the loss of a machine needs several hosts + something that reschedules. The four jobs of orchestration: failure detection, scheduling (find capacity), placement/startup, routing/service discovery. It runs a reconciliation loop: desired state − observed state = actions (desired 5, observed 2 → start 3 + update the load balancer).

Exit codes you'll see: 0 success, 1 app error, 137 = 128+9 (SIGKILL), 143 = 128+15 (SIGTERM, a normal docker stop).

Health checks: liveness vs readiness

CheckQuestionWho acts on a failureAction
/healthz livenessis the process alive? (no DB!)orchestratorrestart it
/readyz readinesscan it serve traffic now? (checks DB)load balancerstop routing, no restart
startuphas a slow boot finished?orchestratorhold liveness until then
HEALTHCHECK --interval=5s --timeout=3s --retries=3 CMD wget -qO- http://127.0.0.1:3000/healthz || exit 1
  1. Dockerfile instruction: Docker runs a command inside the container on a timer
  2. every 5 s, each try may take 3 s, 3 failures in a row = unhealthy
  3. the probe. Use a tool the image has: Alpine images have wget, usually not curl. Use 127.0.0.1: localhost can resolve to IPv6 ::1
  4. turn any failure into exit code 1 (0 = healthy)
$ docker ps --filter name=lab73-api
... Up 8 seconds (healthy) ...
$ docker stop lab73-db                       # DB outage
$ docker inspect -f '{{.State.Health.Status}}' lab73-api
healthy                                     # liveness doesn't depend on the DB: correct
$ docker exec lab73-api wget -S -qO- http://127.0.0.1:3000/readyz
  HTTP/1.1 503 Service Unavailable          # readiness fails: LB stops routing
$ docker inspect -f '{{json .State.Health}}' lab73-api   # last results + output of each probe
Trap

If /healthz checks the DB, a 2-minute DB outage makes every replica "dead", and the orchestrator restarts all of them: a restart storm that can't fix the database. And plain Docker only marks a container unhealthy; it does not restart it.

Tip

"/healthz OK" only proves the process is up. /hello (the DB path) can still fail. Two checks catch two different failures.

Scaling out: stateless replicas behind a load balancer

Vertical = a bigger machine: simple, but has a ceiling, needs a restart, and is still one point of failure. Horizontal = more replicas behind a load balancer: survives losing one, but every replica must be able to answer every request. So state (sessions, counters, uploads) must live outside the process: Postgres, Redis, or (in the lab) a shared named volume.

$ curl -s 127.0.0.1:8350/ ; curl -s 127.0.0.1:8350/
visits=1 served-by=3a60136cd6a9
visits=1 served-by=a71545db4393            # each replica counts in its own memory
$ docker run -d --name lab75-web-1 --network lab75-net -v lab75-data:/data lab75-web:1.1
$ docker run -d --name lab75-web-2 --network lab75-net -v lab75-data:/data lab75-web:1.1
$ docker restart lab75-lb                  # nginx resolves upstream names only at start
$ curl -s 127.0.0.1:8350/ ; curl -s 127.0.0.1:8350/
visits=3 served-by=2e9a8ec8046b
visits=4 served-by=5efcd377a970            # shared state: consistent
Trap

Replicas can't all publish the same host port (port is already allocated). Only the load balancer is published. Same reason docker compose up --scale api=3 fails when the service has a fixed ports: or container_name.

Why more instances don't always help

Each instance has its own DB pool (max_size=5), so N instances can open 5×N connections against one Postgres limit. If the trace says the time is spent waiting for a pool connection, the bottleneck is the DB pool, not the API CPU. Serverless is the extreme case: one connection per invocation against a hard server limit.

T4L1: modular monolith and enforced boundaries

A modular monolith is one deployable and one process, split into modules that own their rules and their private data and offer a public contract (functions like get_email(), or events like OrderPlaced). It has no network tax and ACID is easy. The boundary only holds if a tool enforces it in CI (Shopify's Packwerk). A comment or a team agreement doesn't count.

$ pytest -q
FF.
E   Dependency violation: billing -> users (not in users' public API shop.users.api):
E     shop/billing/invoice.py:1 imports shop.users._store
# fix: billing calls users.get_email(user_id) instead of reading USERS_TABLE
$ pytest -q
3 passed
$ git add shop/billing/invoice.py
$ git commit -m "billing: use users public API"
Trap

"It's one process, so a direct query into the other module's table is fine because it's faster" is wrong (Quiz 2A Q13). So are "silence/skip the check" and "move it to a microservice". Split into services only on measured pain (Fowler: more than 50 engineers, or very different hardware scaling).

Tip

Retries over a network need an idempotency key (a unique transaction reference). A timeout doesn't tell you the remote call failed: it may have run and only the reply was lost (partial failure).

Quiz-style Deploy hello-api like the demo

Your folder has a Dockerfile (app on port 8000) and hello.env with LOG_LEVEL and DATABASE_URL. Build hello-api:1.0. Run it in the background as hello-api, restarted after crashes and reboots but not after a manual stop, reachable only from this machine on port 8000, config from the file.

Show answer
$ docker build -t hello-api:1.0 .
$ docker run -d --name hello-api --restart unless-stopped -p 127.0.0.1:8000:8000 --env-file hello.env hello-api:1.0
$ docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' hello-api
unless-stopped
$ docker port hello-api
8000/tcp -> 127.0.0.1:8000

"Not after a manual stop" = unless-stopped, not always. "Only this machine" = the 127.0.0.1: prefix. All flags before the image.

Drill Wrong policy, can't recreate

Container orders runs with no restart policy. You must give it unless-stopped without losing it (don't remove it). Then prove a crash is recovered.

Show answer
$ docker update --restart unless-stopped orders
$ docker exec orders pkill -9 node      # or whatever the app process is
$ docker inspect -f '{{.State.Status}} {{.RestartCount}}' orders
running 1

docker update changes the policy in place. Don't use docker kill/stop to test it: those are manual stops and are not restarted. (Note: if the app is PID 1 in the container, a kill from inside is ignored. The lab starts it with --init so it isn't.)

Quiz-style Which policy for the migration job?

migrate exits 1 while the DB isn't ready and 0 once it applied the migrations. It must be retried after a failure and never run again after a success. Which --restart? What happens with unless-stopped?

Show answer
$ docker run -d --name migrate --restart on-failure -v state:/state jobs:1.0
$ docker ps -a --filter name=migrate
... Exited (0) ...

on-failure restarts only on a non-zero exit. With unless-stopped (or always) Docker restarts it after the success too, forever (Restarting (0)).

Twist Healthy during a DB outage?

The Dockerfile has HEALTHCHECK CMD curl -f http://localhost:3000/healthz || exit 1 on node:24-alpine, and /healthz runs SELECT 1. The container is always unhealthy, even with the DB up. Then, after a fix, it goes unhealthy every time the DB blips. Find the three problems.

Show answer
HEALTHCHECK --interval=5s --timeout=3s --retries=3 CMD wget -qO- http://127.0.0.1:3000/healthz || exit 1

(1) Alpine has no curl: use wget (read the reason in docker inspect -f '{{json .State.Health}}'). (2) localhost may resolve to ::1 while the app listens on IPv4: use 127.0.0.1. (3) Liveness must not touch the DB: move SELECT 1 to /readyz, rebuild, recreate.

Twist Logged out at random

After scaling to 3 replicas behind a load balancer, users get logged out at random. Sessions are kept in a JavaScript Map in the server. What's wrong, and which fixes are real?

Show answer

Each replica only knows the sessions it created; the LB sends the next request elsewhere. Real fix: store sessions in a shared store (Postgres/Redis) or use stateless signed tokens, so any replica can answer. Sticky sessions only hide it: the sessions still die with a replica. Scaling vertically instead removes the symptom but keeps a single point of failure and a ceiling.

Quiz-style Boundary check fails in CI

CI prints Dependency violation: billing → user: User.find(id).email — not in user's public API. Which actions are right? (a) call the user module's public function for the email; (b) add an ignore rule for this file; (c) move billing to a microservice; (d) keep the CI check.

Show answer

(a) and (d). (b) silences the check. (c) adds the network tax without measured pain. In the lab: edit only billing/invoice.py, run pytest, then git add + one git commit.

Practice labs

Cheat sheet

  • docker run -d --name app --restart unless-stopped -p 127.0.0.1:8000:8000 --env-file app.env img:1.0 the demo's run
  • -p 127.0.0.1:H:C loopback only; -p H:C = 0.0.0.0 = public. Host port first.
  • --env-file f all KEY=value lines; -e KEY=value one variable. Options go before the image.
  • docker rm -f app + docker run ... to change env/ports/volumes (restart ≠ recreate)
  • docker update --restart unless-stopped app change the policy in place
  • no · on-failure[:N] (non-zero exit only: jobs) · always · unless-stopped (services)
  • docker stop/docker kill = manual: never restarted. Restart policy = one host, not an orchestrator.
  • docker inspect -f '{{.HostConfig.RestartPolicy.Name}} {{.RestartCount}}' app
  • docker inspect -f '{{json .Config.Env}}' app env of the container; docker image inspect img | grep SECRET must be empty
  • HEALTHCHECK --interval=5s --timeout=3s --retries=3 CMD wget -qO- http://127.0.0.1:3000/healthz || exit 1
  • docker inspect -f '{{.State.Health.Status}}' app starting / healthy / unhealthy (Docker only marks, doesn't restart)
  • liveness /healthz: no DB, fail = restart. readiness /readyz: checks DB, fail = LB stops routing.
  • docker exec app wget -S -qO- http://127.0.0.1:3000/readyz test from inside when there's no curl
  • Scale out = stateless replicas + LB + shared state (-v same-volume:/data or Postgres). Only the LB publishes a port.
  • Orchestration jobs: failure detection, scheduling, placement/startup, routing/service discovery. Reconcile: desired − observed = actions.
  • Modular monolith: one deployable; modules call public APIs only; enforce in CI (Packwerk / a test); never silence the check.
  • Exit codes: 0 ok, 1 app error, 137 SIGKILL, 143 SIGTERM.
