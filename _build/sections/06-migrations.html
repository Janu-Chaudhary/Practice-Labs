Topic 6

Database migrations with Flyway, and migration files in git

Write numbered migration files, apply them with flyway migrate, read the history table through flyway info, and recover from checksum mismatches, hand-run SQL and version collisions.

Mental model

Files in git, memory in the database. A migration is a file of SQL (03_add_currency.up.sql). Saving it changes nothing. The runner (Flyway) connects to the database, reads the history table (flyway_schema_history, one row per applied migration), runs every file that has no row yet, in version order, and inserts a row for each. The history is a log: append-only (never edit an applied file), ordered (03 assumes 01 and 02 ran), checksum-verified (edit an applied file and Flyway stops). Anything done by hand is invisible to it.

Setup: the flyway command (Docker) and the Files panel

Flyway is not installed on your laptop. labs/bin/flyway is a tiny script that runs the official Flyway image (flyway/flyway:13.10.0, already pulled) in Docker. It mounts the current folder, runs as your user (so shop.db is not owned by root), and Flyway reads flyway.toml from that folder. So: always cd work first. Once per terminal, from the Practice-Labs folder:

$ export PATH="$PWD/labs/bin:$PATH"
$ cd labs/06-migrations/02-first-migrate && ./setup.sh && cd work
$ flyway info
docker run --rm -u "$(id -u):$(id -g)" -v "$PWD:/work" -w /work flyway/flyway:13.10.0 migrate
  1. run a throw-away container (removed when it exits)
  2. as your user id, so created files belong to you
  3. mount this folder at /work and run there: Flyway sees flyway.toml, migrations/, shop.db
  4. the pinned official image
  5. your Flyway command (anything you type after flyway)

Every lab's flyway.toml looks like this. The url says which database (an SQLite file next to it), locations where the files are:

[environments.default]
url = "jdbc:sqlite:shop.db"

[flyway]
environment = "default"
locations = ["filesystem:migrations"]
sqlMigrationPrefix = ""            # course naming: no V in front
sqlMigrationSeparator = "_"        # 03_add_currency -> version 03, description "add currency"
sqlMigrationSuffixes = [".up.sql"] # only .up.sql are migrations; .down.sql are ignored
validateMigrationNaming = true     # misnamed file = error, not silently skipped

Your tools. Like in the quiz, you only write files in migrations/ and run flyway (plus git). shop.db is the database. You never open it yourself: flyway info is your window into it. Write files in the lab tool's Files panel: click + New file, type the path with the folder (migrations/03_add_currency.up.sql), write the SQL, save with Ctrl+S. Click an existing file to open and edit it. Use the terminal for flyway, git, ls, mv, and cat to read a file.

Trap

Flyway reads the file on disk, not your editor tab. Save with Ctrl+S before flyway migrate. Typing only 03_add_currency.up.sql in + New file puts it next to flyway.toml, where Flyway never looks.

Tip

The quiz terminal may have Flyway installed directly. Same commands, same output: flyway migrate, flyway info. The wrapper only hides the Docker part.

File names: course naming vs Flyway's default

NamingExampleUsed in
Course (configured above)03_add_currency.up.sql + 03_add_currency.down.sqlquiz 2 Q18, labs 01, 03, 04, 06-11, 13, 14
Flyway defaultV3__add_currency.sql (capital V, two underscores)Flyway docs, labs 02, 12
Timestamp version202610071517_add_search_index.sqlquiz 2 Q17, labs 05, 10

Version = everything before the first separator. Versions compare as numbers: 3 and 03 are the same version (duplicate!), and 05 < 202610261030. The description is the rest, with _ shown as spaces. Flyway (free edition) has no undo command: it never runs a .down.sql. You write it so the change can be undone later (by a tool or a person); it does not show up in flyway info.

Trap

A file that does not match the naming is not a migration. Without validateMigrationNaming Flyway silently skips it. Rule: if flyway info does not list your file, its name is wrong.

Reading flyway info: the history table for you

flyway info puts two lists side by side: the migration files, and the rows of the history table flyway_schema_history (one row per migration Flyway ran: version, script name, checksum, when, success). It is read-only, so run it first and last, every time.

$ flyway info

| Versioned | 01      | create users    | SQL      |                     | Ignored (Baseline) |
|           | 01      | existing schema | BASELINE | 2026-10-27 17:24:07 | Baseline           |
| Versioned | 02      | create orders   | SQL      | 2026-10-27 17:24:17 | Success            |
| Versioned | 03      | add city        | SQL      | 2026-10-27 17:24:17 | Success            |
| Versioned | 05      | create coupons  | SQL      | 2026-10-27 17:24:17 | Success            |
| Versioned | 04      | index orders    | SQL      | 2026-10-27 17:24:26 | Out of Order       |

What you seeWhat it means

Trap

"Last one run" and "schema version" are different questions. Above, 04 ran last, but the schema version is 05. If your new file is not in the table at all, its name is wrong (or it is not in migrations/).

The Flyway commands

CommandWhat it does
flyway infotable of every migration: Success / Pending / Baseline / Out of Order. Read-only. Run it first and last.
flyway migratevalidate, then run every pending migration in version order, each in its own transaction, and record a history row
flyway migrate -target=03apply only up to version 03 (staged rollouts)
flyway validatecompare files with history (checksums, missing, pending). Fails also when something is still pending.
flyway repairrewrite stored checksums to match the files, remove failed rows. Does NOT run SQL.
flyway baseline -baselineVersion=02existing DB without history: "already at 02". Creates the history table with a BASELINE row.
flyway migrate -outOfOrder=trueallow a lower version that arrived after a higher one was applied
flyway migrate -skipExecutingMigrations=true -target=03record 03 as applied without running it (only when the same SQL was already run by hand)

Why

What migrate does per file, as on the slide: BEGIN; run the file's SQL; INSERT the history row; COMMIT;. Both commit together or not at all. On SQLite and PostgreSQL DDL is transactional, so a failing migration prints Changes successfully rolled back and leaves no history row: fix the file and run migrate again.

BEGIN / COMMIT / ROLLBACK, and reverse migrations

What it isExample result
ROLLBACKdiscards changes that have not committedBEGIN; ALTER TABLE users DROP COLUMN bio; ROLLBACK; bio values still there
Reverse (down) migrationnew SQL run after the up committedALTER TABLE users ADD COLUMN bio text; bio is back, NULL in every row
Restorerecover data from a backupvalues as of the backup time

Without BEGIN each statement autocommits: if statement 2 fails, statement 1 stays. A down migration cannot restore values the up deleted (quiz 2 Q9: answer NULL for every row). Downs undo in reverse order (04 then 03), and each down undoes only its own migration. Flyway free edition never runs a down. On a shared database the way back is to roll forward: put the reverse SQL in the next migration.

Files panel, + New file migrations/03_restore_bio.up.sql, write, Ctrl+S:

ALTER TABLE users ADD COLUMN bio TEXT;
$ flyway migrate     # 03 runs: bio is back, NULL in every row
$ flyway info        # 01, 02, 03 Success: the history tells exactly what happened

Errors you must recognise

ERROR: Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 02
-> Applied to database : 1944033762
-> Resolved locally    : 2087934152
Either revert the changes to the migration, or run repair to update the schema history.

Means: someone edited an already-applied file. Flyway stops before running anything.

Fix: put the file back (git restore --source=HEAD~1 file or git revert) and put the change in the next migration (03). repair only makes the error go away: the new SQL never runs, and other databases differ. Use repair only for harmless edits (comments) or to clear a failed row.

ERROR: Migration of schema "main" to version "03 - add full name" failed! Changes successfully rolled back.
Message    : [SQLITE_ERROR] SQL error or missing database (duplicate column name: full_name)

Means: the change was already made by hand, outside Flyway. Hand-run SQL changes the schema but writes no history row, so 03 is still Pending (quiz 2 Q8). PostgreSQL says column "full_name" of relation "users" already exists; for a table: table x already exists.

Fix: if the hand-run SQL is exactly the file's SQL, record 03 without running it: flyway migrate -skipExecutingMigrations=true -target=03, then a plain flyway migrate for the rest. -target=03 matters: without it every pending migration is recorded but never run.

ERROR: Validate failed: Migrations have failed validation
Detected failed migration to version 02 (create coupons).
Please remove any half-completed changes then run repair to fix the schema history.

Means: 02 ran without a transaction (e.g. executeInTransaction=false, or MySQL DDL) and broke halfway. The first statements stayed; flyway info shows 02 Failed.

Fix: fix the file (allowed: it never succeeded) and make it safe to re-run (IF NOT EXISTS, INSERT OR IGNORE), then flyway repair (removes the Failed row) and flyway migrate.

ERROR: Found more than one migration with version 04
Offenders:
-> /work/migrations/04_add_coupons.sql (SQL)
-> /work/migrations/04_add_search_index.sql (SQL)

Means: two branches picked the same number. Git merged fine (different file names); only the runner complains.

Fix: on your branch, git mv your file to a timestamp version, commit, merge main in. Never renumber the one already on main.

ERROR: Found non-empty schema(s) "main" but no schema history table. Use baseline() or set baselineOnMigrate to true ...

Means: the database has tables but was never managed by Flyway.

Fix: flyway baseline -baselineVersion=02 (the version the DB already matches), then flyway migrate.

Detected resolved migration not applied to database: 05.
To ignore this migration, set -ignoreMigrationPatterns='*:ignored'. To allow executing this migration, set -outOfOrder=true.

Means: a lower version showed up after a higher one was applied (e.g. 202610261030 applied, then 05 merged in). The same text without the outOfOrder part comes from flyway validate when something is simply Pending: run migrate.

Fix: flyway migrate -outOfOrder=true.

ERROR: Invalid SQL filenames found:
Invalid versioned migration name format: 04-add-x.up.sql (could not recognise version number 04-add-x)

Means: wrong separator/prefix (here - instead of _; in default naming V3_x.sql with one underscore).

Fix: rename the file.

ERROR: Migration of schema "main" to version "03 - add currency" failed! Changes successfully rolled back.
Message    : [SQLITE_ERROR] SQL error or missing database (Cannot add a NOT NULL column with default value NULL)

Means: SQLite can't add a NOT NULL column to rows that exist without a default.

Fix: the migration rolled back and has no history row, so just fix the file: ADD COLUMN currency TEXT NOT NULL DEFAULT 'INR' (old rows get INR), save, flyway migrate again.

Migrations in git: timestamp versions

Sequence numbers collide when two people write migration 04 the same afternoon. Timestamps (yyyyMMddHHmm) are unique without coordination and sort by when they were written.

git mv migrations/04_add_search_index.sql migrations/202610071517_add_search_index.sql
  1. rename AND stage it (delete + add in one go)
  2. old name (your branch's migration only)
  3. new name: timestamp version, same description
$ git branch --show-current
search
$ git mv migrations/04_add_search_index.sql migrations/202610071517_add_search_index.sql
$ git commit -m "Rename search index migration to timestamp version"
$ git merge main --no-edit          # without --no-edit an editor opens: vim :wq, nano Ctrl+O Enter Ctrl+X
$ ls migrations
01_create_users.sql  02_add_billing.sql  03_add_full_name.sql  04_add_coupons.sql  202610071517_add_search_index.sql
Trap

mv + git commit -am commits the delete but not the new (untracked) file: your migration vanishes from the commit. Use git mv, or git add -A. Rename the .down.sql too when there is one.

Tip

shop.db is usually in .gitignore: git holds the files (the recipe), each database holds its own history (what was cooked).

Expand / backfill / transition / contract

Renaming user_name to full_name while old and new app instances run side by side (quiz 2 Q11):

A single RENAME COLUMN breaks every old instance at once. Backfilling before the app writes both leaves NULLs for rows written meanwhile (Q11 option B).

Twist Down for a contract migration

04_drop_user_name.up.sql drops user_name after full_name was backfilled. Write a down that gives back a useful user_name.

Show answer
ALTER TABLE users ADD COLUMN user_name text;
UPDATE users SET user_name = full_name;

ADD COLUMN alone gives NULLs. Copying works only because full_name still has the values; data that exists nowhere else needs a backup.

Quiz-style flyway info says 02 Failed

02_create_coupons.up.sql = CREATE TABLE coupons, INSERT two coupons, CREATE INDEX. It ran without a transaction and failed on the index (typo coupns). flyway migrate now says Detected failed migration to version 02. Please remove any half-completed changes then run repair. Get 02 fully applied, using only the editor and flyway.

Show answer

Open migrations/02_create_coupons.up.sql in the Files panel, make every step re-runnable and fix the typo, Ctrl+S:

CREATE TABLE IF NOT EXISTS coupons (code TEXT PRIMARY KEY, percent INTEGER NOT NULL);
INSERT OR IGNORE INTO coupons (code, percent) VALUES ('WELCOME10', 10), ('FESTIVE20', 20);
CREATE INDEX IF NOT EXISTS idx_coupons_percent ON coupons (percent);
$ flyway repair       # removes the Failed row; runs no SQL
$ flyway migrate      # 02 runs from line 1: table + rows skipped, index created. Success

Statements 1 and 2 committed before the failure, so a plain re-run fails with table coupons already exists (and a new Failed row). Editing 02 is fine here: it never succeeded anywhere. Don't delete the CREATE/INSERT from 02: a fresh database still needs them. With a transaction (the SQLite/PostgreSQL default) there is no Failed row at all: everything rolls back.

Quiz-style Change a view: new V file or edit the R file?

Default naming. R__active_users.sql (DROP VIEW IF EXISTS + CREATE VIEW) is applied. Users need a city column, and the view must show it. What files do you write, what does flyway info show before migrate, and what is in the history table afterwards?

Show answer

Files panel: + New file migrations/V3__add_city.sql, write, Ctrl+S:

ALTER TABLE users ADD COLUMN city TEXT;

Open migrations/R__active_users.sql, change the SELECT line, Ctrl+S:

  SELECT id, name, city FROM users WHERE active = 1;
$ flyway info       # V3 Pending; old R row "Outdated" + new R row "Pending"
$ flyway migrate    # V3 first, then the repeatable

Versioned (V) = runs once, never edit. Repeatable (R__, no version) = re-runs whenever its checksum changes, after all versioned ones; editing it IS how you change it. History gets a second R__active_users.sql row (version empty, new checksum); info shows the old one as Superseded.

Twist Two lower versions arrive late: outOfOrder or renumber?

Your DB is at 202610251200. Now there are 202610221500_add_order_status (teammate's hotfix, already applied in production) and your own 202610231000_add_order_notes (never committed, never applied anywhere). flyway info shows both as Ignored. Fix it.

Show answer
$ mv migrations/202610231000_add_order_notes.up.sql   migrations/202610271100_add_order_notes.up.sql
$ mv migrations/202610231000_add_order_notes.down.sql migrations/202610271100_add_order_notes.down.sql
$ git add migrations && git commit -m "Add order notes migration (202610271100)"
$ flyway migrate -outOfOrder=true     # hotfix: "Out of Order"; notes: normal Success

Renumber only what ran nowhere (the hotfix's version is in production's history; renaming it would make production run it twice). Rename before outOfOrder, or the old version gets applied too. git mv fails on untracked files (not under version control): use mv + git add.

Twist Read flyway info: last run vs current version

flyway info lists, in run order: the 01 file Ignored (Baseline) + a BASELINE row 01, then 02, 03, 05 Success, then 04 Out of Order. Which version ran last? What is the schema version? Which file's SQL never ran here? Then someone adds only a -- comment to applied 03 and validate fails: repair or new migration?

Show answer
$ flyway info                              # last row, latest Installed On: 04 (Out of Order)
$ flyway info | grep "Schema version"      # 05
# never executed here: 01 (Ignored (Baseline): the BASELINE row stands in for it)
$ git diff HEAD~1 HEAD                     # only a comment line
$ flyway repair                            # records the new checksum; runs no SQL

Row order in info = order Flyway ran things; version = order it wants them. The checksum covers the whole text, comments too. A comment changes nothing in any database, so repair is right; an edit that changes SQL (lab 07) needs a new migration instead.

Practice labs

Cheat sheet

  • export PATH="$PWD/labs/bin:$PATH" once per terminal from the Practice-Labs folder, then cd work
  • flyway info what is applied / pending (start and end with it)
  • flyway migrate run pending migrations in order, record history rows
  • flyway migrate -target=03 stop at version 03
  • flyway validate files vs history (checksums); fails if something is pending
  • flyway repair accept edited checksums / drop failed rows. Runs no SQL. Last resort.
  • flyway baseline -baselineVersion=02 adopt an existing DB
  • flyway migrate -outOfOrder=true apply a lower version that arrived late
  • 03_add_x.up.sql / 03_add_x.down.sql course naming; V3__add_x.sql Flyway default
  • flyway migrate -skipExecutingMigrations=true -target=03 record 03 without running it (SQL was run by hand, identical)
  • Files panel: + New file migrations/03_x.up.sql, write, Ctrl+S (save before you migrate)
  • info states: Success, Pending, Failed (repair), Baseline / Ignored (Baseline), Ignored + Out of Order, Outdated / Superseded (R__)
  • No undo in Flyway free: roll forward with the next migration; still write a .down.sql for each
  • Never edit an applied migration: write the next one
  • Hand-run SQL = schema changed, no history row = runner fails with "already exists"
  • Down of DROP COLUMN = column back, all NULL. Only a backup restores values.
  • git mv old new + commit, then git merge main --no-edit (timestamp rename)
  • Rename: expand -> backfill -> transition -> contract
