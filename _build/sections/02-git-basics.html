Topic 2

Git basics: local work, branches, merging

Move changes between the working directory, staging area and local repo on purpose, make branches, merge them, and fix a conflict without panicking.

Mental model

Your work lives in four places: the Working Directory (files on disk), the Staging Area (what the next commit will contain), the Local Repository (saved commits) and the Remote (the team's copy). git add copies working dir to staging, git commit copies staging to the local repo, git push sends it to the remote. Every commit is a snapshot plus a pointer to its parent. A branch is only a label that points at one commit and moves forward when you commit. git status compares the first three places, never the remote.

Run git status before and after every command. Each heading tells you where a file is.

git status -s is the short form: two columns, left = staging, right = working dir. M staged, M unstaged, MM both, ?? untracked, UU conflict.

add and commit: working dir to staging to repo

A commit takes exactly what is staged, not everything you touched. That is why you choose with git add.

CommandWhat it does
git add file.pystage one file (new or modified) as it is right now
git add .stage everything in this folder and below: new, modified, deleted
git add -Astage everything in the whole repo, including deletions
git commit -m "Msg"save the staging area as a new commit on the current branch
git commit -am "Msg"stage all modified/deleted tracked files, then commit. Skips untracked files!
git commit (no -m)opens an editor for the message (see the editor trap below)
git commit -a -m "Add webhook route"
  1. save staging as a snapshot
  2. -a = first stage every tracked file that changed (new files are NOT included)
  3. -m = the message, so no editor opens
Trap

You create routes/webhooks.py and run git commit -am "...". The new file is not in the commit: -a only knows files git already tracks. Run git add routes/webhooks.py first.

Commit hygiene

One commit = one change. Subject in the imperative, like a command: "Add webhook route", "Fix session timeout", not "updates" or "fixed stuff". Quiz checks compare the message exactly, so copy capitals and spaces.

nothing added to commit but untracked files present (use "git add" to track)

Means: the staging area is empty. Maybe you edited but did not save, or did not git add.

Fix: save the file, git add it, check with git status.

log --oneline --graph --all --decorate: read the graph

git log --oneline --graph --all --decorate
  1. show history
  2. one line per commit: short hash + subject
  3. draw the lines between commits
  4. every branch, not only the current one
  5. show labels: (HEAD -> main), (feature)
$ git log --oneline --graph --all --decorate
*   9e1f0a2 (HEAD -> main) Merge branch 'feature'   # merge commit: 2 lines go into it
|\
| * f03224a (feature) Use friendlier greeting     # on feature only
* | 4a13d04 Welcome returning users               # on main only
|/
* 0fdc766 Add greet                               # common ancestor (base)
  • Newest is on top. Each * is a commit. Lines go down to the parent.
  • HEAD -> main = you are on main. A label in brackets without HEAD is another branch.
  • |/ is where a branch split off. |\ under a commit means it has two parents (a merge).
  • Commits "on main" = everything reachable going down from main, following both parents of a merge. Above: main has 4, feature has 2.
Counting

git log --oneline main | wc -lsame number: one line per commit, wc -l counts lines

branch, switch, checkout -b

A branch is a pointer to one commit. Creating one is instant; no files are copied. Switching rewrites your working dir to match that branch.

CommandWhat it does
git branchlist local branches; * marks the current one
git branch fixcreate fix here, but STAY on the current branch
git switch fixmove to an existing branch
git switch -c fixcreate + switch (modern)
git checkout -b fixcreate + switch (old form, same result)
git switch -c fix maincreate from main even if you are somewhere else
git branch --show-currentprint only the current branch name
git branch -d fixdelete a merged branch (only if the task says so)
Trap

git branch fix-greeting then edit and commit: the commit lands on main, because git branch does not switch. Use switch -c, and check git status line 1 ("On branch ...") before committing.

error: Your local changes to the following files would be overwritten by checkout:
        notes.txt

Means: you have uncommitted edits to a file that differs on the other branch.

Fix: commit them, or git stash, switch, and later git stash pop.

fatal: invalid reference: fix

Means: git switch fix but the branch does not exist. Fix: git switch -c fix.

merge: fast-forward or merge commit?

git merge X brings branch X into the branch you are on. So: switch to the receiving branch first (usually main), then name the other one.

Graph beforeResult
main has no new commits since feature branched (main is below feature on one line)Fast-forward: main label just slides up to feature. No new commit, no editor, can't conflict.
both branches have new commits (the graph forks |/)Merge commit: a new commit with two parents. Adds 1 to the count. Opens the editor unless you pass --no-edit or -m.
both forks changed the same lines of a fileConflict: git stops halfway and asks you.
$ git merge feature
Updating 3f9a1c2..8b41d07
Fast-forward                                  # no new commit
$ git merge feature --no-edit
Merge made by the 'ort' strategy.             # new merge commit, 2 parents
Predict the count

After a merge commit, main's count = all commits on main + feature's commits that main lacked + 1. Quiz 1 Q17: base + main's 1 + feature's 1 + merge = 4. Check with git rev-list --parents -n1 main: a merge commit prints 3 hashes (itself + 2 parents).

Already up to date.

Means: the named branch is already inside the current one. Usually you are on the wrong branch (e.g. on feature merging main, or on main merging main). Check git status.

merge conflicts: markers, resolve, finish

Git compares both sides with their common ancestor. If only one side changed a region, it takes that side. If both changed the same region, it has two valid edits and no rule to choose, so it writes both into the file and stops.

$ git merge feature
CONFLICT (content): Merge conflict in greet.py
Automatic merge failed; fix conflicts and then commit the result.
$ cat greet.py
def greet(name):
<<<<<<< HEAD
    return f"Hello, {name}! Welcome back."      # OURS: the branch you are on (main)
=======
    return f"Hi there, {name}."                 # THEIRS: the branch being merged in
>>>>>>> feature

The steps, always the same:

  1. Open the file (code greet.py / nano greet.py). Delete the 3 marker lines and write the final text the task asks for. Save.
  2. Check no markers are left: grep -n '<<<<<<<\|=======\|>>>>>>>' greet.py prints nothing.
  3. git add greet.py: "add" here means mark as resolved.
  4. git commit --no-edit (keeps git's "Merge branch 'feature'" message) or git commit -m "...".
CommandUse
git merge --abortgive up: back to exactly before git merge
git checkout --ours f / --theirs ftake one side's whole file (then git add f)
git diff --checkwarns about leftover conflict markers
git status"Unmerged paths" lists what is still unresolved
error: Committing is not possible because you have unmerged files.
hint: Fix them up in the work tree, and then use 'git add/rm <file>'

Means: at least one conflicted file was not git added. Fix: git status, resolve and add each "both modified" file.

error: Merging is not possible because you have unmerged files.
fatal: You have not concluded your merge (MERGE_HEAD exists).

Means: you ran git merge / pull again while the old merge is unfinished. Fix: finish it (add + commit) or git merge --abort.

Trap

Git does NOT stop you from committing a file that still contains =======. If you git add with markers inside, they are committed and the content check fails. Look at the file before adding.

Tip

Files that only one side changed, or a new file from the other branch, are already staged during the conflict ("Changes to be committed: new file"). Leave them alone.

The editor trap: commit without -m

git commit without -m, and a merge that makes a merge commit, open a text editor for the message. On this machine the default is vim (no core.editor is set). The message is already filled in; you only need to save and quit.

EditorHow to recognise itSave + quit
vimscreen full of ~ lines, no menupress Esc, type :wq, Enter
nanomenu at the bottom: ^O Write Out ^X ExitCtrl+O, Enter, Ctrl+X
$ git config --global core.editor nano     # make git use nano from now on
$ git commit --no-edit                      # during a merge: no editor at all
$ git merge feature --no-edit               # merge commit with default message, no editor
Trap

In vim, typing letters before pressing i runs commands, not text. If the screen looks wrong, press Esc a few times and type :wq. Lines starting with # in the message are comments and are dropped. To abort the commit from vim use :cq; the merge then stays in progress and you finish later with git commit --no-edit.

git mv, git rm, rm --cached, .gitignore

CommandWhat it does
git mv a.py b.pyrename on disk + stage the rename
git rm old.txtdelete on disk + stage the deletion
git rm --cached .envstop tracking, keep the file on disk
git rm -r --cached folder/same for a folder
echo '*.log' >> .gitignorefuture git add skips matching untracked files

Plain mv/rm also work, but then git sees a deletion and a new untracked file, and you must git add -A to stage both.

Trap

.gitignore only affects untracked files. If .env was already committed, adding it to .gitignore does nothing; you need git rm --cached .env as well. Patterns: *.log any .log file, node_modules/ a folder, .env one file. Always quote patterns in echo.

        notes.txt

Means: the merge needs to change a file you have edited but not committed. Fix: git stash, merge, git stash pop.

Undo a commit (the short version)

SituationCommand
made one commit too many, keep its changesgit reset --soft HEAD~1 (commit gone, changes stay staged)
committed on main, should be on a new branchgit branch newname then git reset --hard HEAD~N then git switch newname (clean tree only)
wrong commit message on the last commitgit commit --amend -m "Right message"

HEAD~1 = the parent of the current commit, HEAD~2 = two back. The full story of reset modes, reflog, detached HEAD, rebase and remotes (push / fetch / pull) is in the git history topic.

Drill Which commits go where?

You edited a.py, b.py and created c.py. You run git add a.py then git commit -am "Fix a". Which files are in the commit?

Show answer

a.py and b.py. -a stages every tracked modified file (a.py, b.py). c.py is untracked, so it stays out. If the task wanted one change per commit, run git commit -m without -a.

Quiz-style Quiz 1 Q16: fix-greeting branch

On main with one commit "Add greet" (return "Hello " + name). Create and switch to fix-greeting, change the line to return f"Hello, {name}!", commit "Use f-string in greeting", stay on fix-greeting.

Show answer
$ git switch -c fix-greeting
$ code greet.py        # edit + SAVE
$ git diff             # check: only the return line
$ git add greet.py
$ git commit -m "Use f-string in greeting"
$ git status           # On branch fix-greeting, clean

Create the branch FIRST, so the commit lands on it. Checked: branch exists, current branch, file content at the branch, tip message.

Quiz-style Quiz 1 Q17: resolve the conflict, main has 4 commits

main and feature both changed greet.py's return line after "Add greet". Merge feature into main, make the line return f"Hi there, {name}! Welcome back.", finish the merge with git's own message.

Show answer
$ git merge feature                 # CONFLICT in greet.py
$ code greet.py                     # remove markers, write the new line, save
$ git add greet.py                  # mark resolved
$ git commit --no-edit              # or: git commit, then :wq in vim
$ git rev-list --count main
4

4 = Add greet + Welcome returning users + Use friendlier greeting + the merge commit. Don't delete feature, make no other commits.

Quiz-style Quiz 1 Q12: keep the staged 60, drop the 6000

Committed TIMEOUT = 30, staged 60, working dir has a typo 6000. Throw away only the typo.

Show answer
$ git restore config.py

Copies the staged version (60) over the working file. Staging is untouched, so 60 stays staged.

Quiz-style Merge blocked by your own edit

You have an unfinished, uncommitted edit in notes.txt. git merge feature says "Your local changes ... would be overwritten by merge". Merge now, keep your edit uncommitted afterwards.

Show answer
$ git stash
$ git merge feature --no-edit
$ git stash pop
$ git status        # modified: notes.txt (unstaged), stash list empty
Twist Two commits on the wrong branch

You made "Add login form" and "Validate login fields" on main. They belong on a new branch login; main must go back to "Add greet". Nothing pushed.

Show answer
$ git branch login          # label the work first
$ git reset --hard HEAD~2   # move main back 2 (clean tree only)
$ git switch login

Branches are labels: you are only moving labels, the commits stay. Doing the reset before git branch leaves the commits without a label (recover with git branch login ORIG_HEAD).

Twist Conflict in two files, keep the other side's whole file

Merge reports conflicts in greet.py and config.py. The task: config.py = feature's version, greet.py = a combination you type.

Show answer
$ git checkout --theirs config.py   # theirs = branch being merged in
$ code greet.py                     # hand-combine, remove markers
$ git add config.py greet.py
$ git status                        # All conflicts fixed but you are still merging.
$ git commit --no-edit
