# T4L1 — Architecture & the Stack Decision (study brief)

Source: T4L1 slides (62 PDF pages; image-only pages 5, 7, 16, 17, 24, 25, 28 were read from the PDF). Course outline T4 section. Quiz 2A Q12 and Q13 (already test T4L1).

Tagline: **"The architecture is the shape. The stack is what it is built from. Choose the system shape, the stack follows its trade-offs."**

---

## 1. One-paragraph summary

On localhost everything works: latency is zero and memory is shared. Once real users arrive over a network, every call between parts of a system becomes a **network call**, which can fail halfway, silently, "on someone else's clock" (the *distributed tax*). The lecture walks through the **eight fallacies of distributed computing**, then the three architecture choices: the **traditional monolith** (simple, but decays into a "Big Ball of Mud" where one team's change breaks another's), **microservices** (the industry's reaction, driven by **Conway's Law** and team scaling, but they pay the distributed-systems tax; Amazon Prime Video cut costs **90%** by *removing* microservices), and the **modular monolith** (one deployable, one process, but with module boundaries enforced by tools, e.g. Shopify's **Packwerk**). The main argument: **start as a monolith (Fowler, "Monolith First"), default to a modular monolith with enforced seams, and split into services only when a measured pain forces it.** **Domain-Driven Design** (ubiquitous language, bounded contexts, context map) tells you *where* the seams go. The worked example is a campus food-delivery app. Finally, **the stack follows the architecture and the product**: early SaaS, a high-volume store and a data-heavy video pipeline each get a different right answer.

## 2. Slide-by-slide outline

**Opening (p1–3)**
- Title: "Architecture & the Stack Decision". T4, Lecture 1 of 2.
- `$ npm run dev ✓ ready on http://localhost:3000`. "Latency zero. Memory shared. Everything works."

**The distributed tax (p4–8)**
- *Anatomy of a function call*: `def checkout(cart): total = calculate_total(cart); return total`. "Same process. Same address space. Same memory. If it fails, you know instantly."
- Diagram (p5): a network call has 5 steps: **1 function call** (`fetch_total_from_service(cart)`) → **2 serialize** (cart → JSON) → **3 packetize** (seq 0–4) → **4 transmit** (via the NIC, across routers; some packets **dropped**) → **5 reassemble** (server merges).
- "THE CS UNDERNEATH": what a network call costs that a function call doesn't:
  - **Partial failure**: did it not run, or did it run and the reply get lost?
  - **Retries and idempotency**: is it safe to run twice, or does it double-charge?
  - **Distributed transactions, and the working local debugger, gone.**
  - Key line: **"A network call is a function call that can fail halfway, silently, on someone else's clock."**
- Meme (p7): "It works on my computer" / "yes but we are not going to give your computer to the client".
- **The eight fallacies of distributed computing** (full list in section 4).

**Predict before you check #1 (p9)**
- "A new engineer assumes the network behaves like local memory. Which assumption breaks first, in production?" A Latency / B Reliability / C **Both, and you can't fix one without touching the other**. (The slides do not show the answer. C fits the lecture best.)

**The fallacies one by one (p10–14)**
- Fallacy 1 "The network is reliable": hardware fails, power drops, cords get tripped over. Handle it *mechanically*: **retries, acknowledgements, idempotent messaging**. If you skip this, code "waits forever for a reply that is never coming, leaking memory until someone restarts it by hand."
- Fallacy 2 "Latency is zero": **LAN** = same rack, **sub-millisecond**. **WAN** = a server in **Virginia**, a phone in **Tokyo**, "bounded by the speed of light in fiber."
- Fallacy 3 "Bandwidth is infinite": the pipe grows, but the volume grows faster (massive JSON payloads, HD video, verbose XML). Unbounded traffic means **dropped packets** and "a bottleneck that looks like someone else's bug."
- Fallacy 4 "The network is secure" (marked **RETURNS · T9**): attackers adapt; "Treat every hop as hostile by default. Encrypt in transit, verify constantly". Details come in **Topic 9**.
- Fallacies 5–8, "the reality check: a hostile, ever-shifting environment":
  - Topology doesn't change → racks get swapped mid-quarter.
  - There is one administrator → competing teams, competing badges.
  - Transport cost is zero → every gigabyte crossing a region has a bill attached.
  - The network is homogeneous → never: hardware, kernels, **MTUs**, all diverse.

**The traditional monolith (p15–18)**
- "Everything, one process": UI + Business Logic + Data Access, one process, one memory space.
- Benefits: a **single deployable unit**; **simple local development**; **standard ACID database transactions**; **zero network overhead, internally**.
- Diagram (p16): a tangled monolith. 13 modules (Billing, Shipping, Email, Payments, Notifications, Search, Inventory, Catalog, Auth, Orders, Cart, Reporting) all depend on **User = "bottleneck"**. Red dashed lines mark **circular dependencies** (Billing↔Shipping, Payments↔Search, Notifications↔Inventory, Catalog↔Orders, Reporting↔Auth).
- Meme (p17): spaghetti on a photocopier, "Hope you have red the sauce code?" (spaghetti code).
- Predict #2: "A mature monolith's biggest late-stage risk is usually…" A too slow / **B one team's change silently breaks another team's feature** / C hosting cost. (The answer B is implied by the lecture: Big Ball of Mud and coupling.)

**Conway's Law (p19–21)**
- "Why do four teams building one compiler end up with a four-pass compiler? Conway's Law."
- Quote: **"Any organization that designs a system will produce a design whose structure is a copy of the organization's communication structure." (Melvin Conway, 1967)**
- **Amazon's two-pizza teams**: teams small enough to be fed by two pizzas, which gives accountability and agility.
- "Microservices weren't popularised for scalability alone. They apply **Conway's Law in reverse**: the system is shaped to maximise team velocity."

**Microservices (p22–26)**
- "Neat, independent boxes": the industry's answer to team scaling and spaghetti code. User / Billing / Shipping / Notification / Inventory, **each with its own DB**.
- Promise: "Independent deploys. Polyglot. Fault isolation. Infinite horizontal scale **— on the slide**" (that is, only in theory).
- **The 7 Principles of Microservices (Sam Newman, *Building Microservices*)**. Full list in section 4.
- "The microservice reality" diagram (p24): 6 services (User, Auth, Billing, Inventory, Shipping, Notification), each with its own DB, but **every one calls every other** (a full mesh of service calls). User, Billing and Shipping are flagged "busiest / most coupled".
- Meme (p25): unmasking "Microservices" reveals a **"Distributed, tightly coupled monolith"**.
- **The distributed-systems tax**:
  - Observability, suddenly complex: **one request, a dozen logs**.
  - Distributed transactions, **nearly impossible**.
  - **Cascading partial failures**: one service down, three others slow.
  - Orchestration overhead, staggering.

**Case study: Amazon Prime Video (p27–31)**
- **"Reducing costs 90% by deleting microservices." Amazon Prime Video, 2023.**
- The original **serverless** pipeline (p28): **AWS Step Functions** orchestration over 3 components: **Media Converter → S3 bucket → Defect Detector → S3 bucket → Real-Time Notification**. Each orchestration transition costs money, and each S3 round-trip carries the **full video**.
- Where the money went:
  - Billed **per state transition** in the orchestration workflow.
  - Heavy video payloads relayed **through S3 between every hop**.
  - Result: **massive I/O bottlenecks and prohibitive cost at scale**.
- The monolithic pivot: "3 services + S3 relay, AWS Step Functions orchestration" → **consolidated** into **one process on EC2 / ECS with in-memory transfer**.
- Quote: **"Building evolvable software systems is a strategy, not a religion. And revisiting your architectures with an open mind is a must." (Werner Vogels, CTO, Amazon)**

**The synthesis: the modular monolith (p32–36)**
- "One deployable · one process", with internal modules Billing, Inventory, Shipping, Notifications.
- **"Organizational autonomy of microservices. Zero network tax of a monolith."**
- **Rules of engagement**:
  - Modules talk **only through explicit public APIs**.
  - **Billing may not query User's database tables directly.**
  - **Without mechanical enforcement, it relapses into the Big Ball of Mud.**
- **"Start as a monolith. Earn the right to split it."**
- **Martin Fowler, "Monolith First"**: "Split when the pain is measured, not guessed." Early products should almost always start as a monolith, because development speed and simplicity are the point. Evolve to microservices only at **specific, measurable thresholds: the team exceeds 50 engineers, or components need drastically different hardware scaling.**
- **Designing for seams**: "A seam in denim is a natural, reinforced line. Cut there, and the garment survives." A good modular monolith has seams: **enforced module boundaries where code can be extracted into a service later, without a rewrite.**

**Domain-Driven Design (p37–48)**
- "What does 'Product' mean? Depends who's asking." "How do you decide where the seams go? Domain-Driven Design."
- **DDD: "Model the business, not the database"** (**Eric Evans, 2003**):
  - **Ubiquitous language**: one vocabulary, shared by engineers and domain experts, used in conversation **and in code**.
  - **Bounded context**: a boundary inside which a term has **one precise meaning**.
  - **Context map**: how bounded contexts relate and integrate.
  - "The output of DDD isn't a diagram. It's the **seam map for a modular monolith**, or the **service map for microservices**."
- Bounded context example: **Inventory team**: "Product" = weight, dimensions, warehouse location. **Marketing team**: "Product" = SEO tags, high-res images, copy.
- Worked example: **a campus food-delivery app**. Students order from campus eateries, riders pick up and deliver, vendors manage menus and see incoming orders in real time. "One word, 'Order', is about to mean something different to almost every team."
- **Live workshop (25–30 min): finding the modules, together**. Six steps (see section 4). Ending: "The answer is never 'all of them.' **Dispatch** might extract later if real-time location or rider-matching load becomes operationally distinct. Until then, it's a module in one deployable application."
- **Three bounded contexts**:
  - **Ordering**: "Order" = cart, items, price, payment status.
  - **Dispatch**: "Order" = pickup point, drop point, rider, ETA.
  - **Vendor Ops**: "Order" = ticket, prep time, kitchen queue position.
  - "Three legitimate, incompatible definitions of the same word, each correct inside its own boundary."
- **"A feature is not automatically a module"** table (see section 4).
- **The five tests for a module boundary**: Responsibility, Language, Rules, Data, Contract (see section 4). "If you cannot state the module's responsibility and public contract in one or two sentences, you have not found a module yet."
- **Context map**: Ordering → (**event: OrderPlaced**) → Dispatch, and Vendor Ops → (**event: OrderReadyForPickup**) → Dispatch. Contexts integrate through **explicit APIs and events**, not by reading or writing each other's private data.
- From contexts to modules: **3 bounded contexts, 1 modular monolith**. Each becomes an enforced module. **"DDD answers where the seams go. Monolith-First answers when to cut along them."** Split Dispatch out only if rider load genuinely outgrows the rest.
- **Module contracts table** (see section 4). "They can all hold an 'order-like' record. They must not share one giant mutable Order object across the codebase."

**Shopify and hard questions (p49–52)**
- **Shopify: a modular monolith at planetary scale**: **173B requests over the Black Friday weekend**, **284M requests per minute at peak**, **12TB of data every minute**.
- Hard question 1: "If something is just a unique keyword, does it become a module?" **No.** A unique keyword is only a clue to investigate. "Coupon" may just be an Ordering concern (adjust the checkout price by a discount rule). It becomes a candidate module only when it owns real independent policy: **campaign eligibility, merchant-funded promotions, abuse limits, budget caps, reporting**. "A module is created around an owned responsibility and its rules, not because we discovered a new noun."
- Hard question 2: "Does one bounded context always equal one module?" Default rule for this course: **one bounded context is usually one module candidate**, but it is not a mathematical law:
  - A very small context may stay inside a larger module until it earns enough independent rules.
  - A module may contain a few tightly related sub-concepts.
  - A context should not become a microservice merely because you named it.
- **Packwerk: the border patrol** (CI output, see section 6). `bundle exec packwerk check` finds "Dependency violation: billing → user" and the build fails.

**Making the stack decision (p53–61)**
- Predict #3: "**12 engineers. One Postgres database. Growing steadily, not explosively.** What do you build?" A microservices from day one / **B a modular monolith with enforced module boundaries** / C one undivided monolith. (Answer B follows from the lecture.)
- "Same architecture problem. Three different products. Three different right answers."
- **Scenario A, early-stage SaaS** (e.g. a university portal, an HR tool). Architecture: **traditional or modular monolith**. Stack: a framework (**Node.js or Rails**), a **managed relational DB (Supabase, AWS RDS)**, **PaaS hosting (Render, Railway)**. Why: the team is small and time-to-market is critical. A monolith removes network latency and orchestration overhead, so it is the fastest and cheapest way to iterate.
- **Scenario B, high-volume e-commerce** (Shopify-scale storefront). Architecture: **modular monolith**. Stack: one large codebase with **Packwerk-style boundary enforcement**, a **sharded relational database**, **Redis for caching and background job queues**. Why: data is deeply interconnected (users, carts, inventory, payments). Hundreds of developers can work safely across domains, with **no distributed-call latency during a flash sale**.
- **Scenario C, data-heavy processing** (Prime Video-style stream monitoring). Architecture: **monolithic compute process**. Stack: **scalable VMs (EC2) or containers (ECS), single process**, **not serverless functions relying on cloud orchestration**. Why: sending massive data (live video frames) across a network between services or serverless functions is a financial and performance bottleneck. One memory space removes that I/O cost.
- **Summary table** (see section 4).
- **"The architecture is the shape. The stack is what it's built from."**
- **What each architecture demands of its stack** (see section 4).
- **One product, three complete stacks** (the campus SaaS from Scenario A, built three ways; see section 4). "For a small team, the monolith usually reaches a safe first release much sooner and with less operational overhead. The microservice version requires substantially more platform and operational capability before it is safe to run."

**Recap (p62)**
- Monoliths degrade into a Ball of Mud. Microservices answer team-scaling, but tax you with the network.
- A network call is a function call that can fail, halfway, silently.
- Default to a modular monolith with enforced seams. Split only when a measured pain point forces it.
- The right stack follows the product: an early SaaS, a flash-sale storefront and a video pipeline each answer differently.

## 3. Key concepts & definitions

- **Distributed tax**: the extra cost you pay when parts of a system talk over a network instead of in memory. That cost is partial failure, retries and idempotency, no distributed transactions, and no local debugger. Example: `checkout(cart)` as a local call compared with `fetch_total_from_service(cart)` over the network.
- **Partial failure**: the caller cannot tell whether the remote call never ran, or ran and the reply was lost. A local function call fails "instantly" and visibly.
- **Idempotency**: running an operation twice has the same effect as running it once. You need it before retries are safe (otherwise you get a double charge). Quiz 2A Q12: use an **idempotency key / unique transaction reference** on every retry.
- **Eight fallacies of distributed computing**: eight false assumptions that engineers new to distributed systems make (see list).
- **Traditional monolith**: UI, business logic and data access in **one process and one memory space**, deployed as **one unit**. You get ACID transactions and no internal network cost. Risk: it turns into a **Big Ball of Mud** (tangled, circular dependencies, "User" as bottleneck) where one team's change breaks another team's feature.
- **Big Ball of Mud / spaghetti code**: a codebase with no enforced internal boundaries. Everything depends on everything.
- **Conway's Law**: a system's structure copies the organisation's communication structure (Conway, 1967). Example: four teams build a four-pass compiler.
- **Inverse Conway (Conway's Law in reverse)**: shape the teams and the system together to maximise team velocity. Example: Amazon's two-pizza teams and microservices.
- **Two-pizza team**: a team small enough to be fed by two pizzas, which keeps it accountable and agile (Amazon).
- **Microservices**: independently deployable services, each owning its own DB, split by business domain. They promise independent deploys, polyglot code, fault isolation and horizontal scale, but they pay the distributed-systems tax.
- **Distributed (tightly coupled) monolith**: microservices that all call each other, so you get the costs of distribution *and* the coupling of a monolith (p24/p25).
- **Modular monolith**: **one deployable, one process**, split into modules (Billing, Inventory, Shipping, Notifications) that talk **only through explicit public APIs or events**, with boundaries **enforced mechanically** (e.g. Packwerk in CI). "Organizational autonomy of microservices. Zero network tax of a monolith."
- **Seam**: an enforced module boundary where code can later be pulled out into a service **without a rewrite** (denim seam analogy).
- **Monolith First (Martin Fowler)**: start with a monolith and split only when the pain is *measured, not guessed* (>50 engineers, or very different hardware scaling needs).
- **Domain-Driven Design (Eric Evans, 2003)**: model the business, not the database. Its output is a seam map (modular monolith) or a service map (microservices).
- **Ubiquitous language**: one shared vocabulary for engineers and domain experts, used in conversation and in code.
- **Bounded context**: a boundary inside which a term has one precise meaning. Example: "Product" for Inventory compared with Marketing, and "Order" for Ordering, Dispatch and Vendor Ops.
- **Context map**: shows how bounded contexts relate and integrate. Example: OrderPlaced and OrderReadyForPickup events flowing to Dispatch.
- **Module (in this course)**: built around an **owned responsibility and its rules**, with private data and a public contract. It is **not** another word for a feature, screen, API endpoint, database table or unique keyword.
- **Packwerk**: Shopify's tool that checks module boundaries in CI (`bundle exec packwerk check`) and fails the build on a dependency violation.
- **Orchestration (AWS Step Functions)**: a cloud workflow service that coordinates serverless steps and is **billed per state transition**. This was a main cost driver in the Prime Video case.

**Live workshop (25–30 min), 6 steps:**
1. List **actions/events, not nouns**: menu updated, cart checked out, order placed, kitchen starts preparing, order ready, rider assigned, delivery completed.
2. For each event ask: **who owns the decision and rule?**
3. **Cluster** events into candidate modules.
4. Run the **five boundary tests** on each cluster.
5. Draw arrows **only through public APIs/events, never a shared table**.
6. Ask: which module could become a service later, and **what measured pain would justify it?**

**"A feature is not automatically a module" table:**

| Observation | New module? | Reason |

5. **Contract**: which public commands, queries or events may other modules use?

| | Monolith | Modular Monolith | Microservices |
|---|---|---|---|
| Deployment | single unit | single unit | many, independent |

**What each architecture demands of its stack:**
- Monolith: one runtime (Next.js/Bun, SvelteKit, TanStack, Nuxt); one Postgres (e.g. Neon or Supabase); one deploy target (Vercel or Fly.io etc.).
- Modular monolith: same runtime + DB, **plus enforced module boundaries** (Packwerk, or TS module linting); **a queue for async jobs** (Redis / Upstash, BullMQ); **still one deploy pipeline**.
- Microservices: per-service runtime + datastore; **orchestrator (Kubernetes / Amazon EKS) + API gateway**; **message broker (Kafka)**; **OpenTelemetry tracing**.

**One product (campus SaaS), three complete stacks:**
- Monolith: Next.js (App Router), one codebase; Postgres on **Neon**, single branch; **Trigger.dev** for background jobs; deployed on **Vercel**, single project; built-in edge routing, no gateway.
- Modular monolith: Next.js with module boundaries enforced via **TS project refs**; Postgres (**Supabase**), single branch; **Redis** for cache + queue; Vercel, single project; built-in edge routing, no gateway.
- Microservices: **6 Bun/Hono services in their own repos**; **6 Postgres instances** (Neon/RDS); **Kafka (Confluent Cloud)** for inter-service events; **Kubernetes on EKS**, per-service deploys; **Kong API gateway + OpenTelemetry tracing**.
- Takeaway: for a small team the monolith reaches a safe first release much sooner, with less ops overhead.

## 5. Decision rules / trade-offs

1. **Default rule**: start as a monolith, default to a **modular monolith with enforced seams**, and "earn the right to split it". Split only when pain is **measured, not guessed**.
2. **When to split (Fowler)**: more than **50 engineers**, OR a component needs **drastically different hardware scaling**. Example: extract Dispatch only if real-time location or rider-matching load becomes operationally distinct.
3. **Monolith vs modular monolith vs microservices**: use the summary table. Small team and early stage → monolith. Growing team in one org → modular monolith. "Outgrown one team's reach" → microservices.
4. **Why not microservices early**: every boundary call pays the network tax (partial failure, retries, idempotency, no ACID across services, no local debugger, complex observability, cascading failures, orchestration overhead). They need much more platform capability (Kubernetes, gateway, Kafka, tracing) before they are safe.
5. **Why not a plain monolith forever**: with no enforced boundaries it becomes a Big Ball of Mud, and one team's change silently breaks another's.
6. **Modular monolith = best of both**: team autonomy through boundaries, plus ACID and zero network tax. But **only if enforced mechanically** (CI check / Packwerk), not by comments or good intentions.
7. **Where to cut (DDD)**: around **responsibility + rules + private data + public contract** (the five tests), not around nouns, tables, screens or endpoints. **DDD = where the seams go; Monolith-First = when to cut.**
8. **How modules integrate**: through public APIs (`placeOrder()`) or events (`OrderPlaced`). Never through a shared table, a direct cross-module query, or a shared mutable object.
9. **Heavy data (Prime Video)**: when big payloads move between steps, keep them in **one process / one memory space** (EC2/ECS). Serverless + orchestration billed per transition, plus S3 relays, makes it expensive and slow.
10. **Flash-sale e-commerce (Shopify)**: interconnected data and a latency-critical peak → modular monolith + sharded relational DB + Redis.
11. **Stack follows architecture, and architecture follows the product**: there is no single "best stack". The same architecture problem can have three right answers for three products.
12. **Strategy, not religion (Vogels)**: revisit architecture choices with an open mind (moving back to a monolith is allowed).

## 7. Common misconceptions / traps (distractor material)

- "Microservices are mainly for scalability." The slide says they were popularised **not for scalability alone**: they apply Conway's Law in reverse for **team velocity**.
- "Microservices = scale from day one, so build them early" (Predict #3 option A). Wrong for 12 engineers with steady growth. The answer is a modular monolith.
- "A plain monolith with no boundaries is fine because it's simplest" (option C). It decays into a Ball of Mud.
- "Inside one process a direct SQL query into another module's tables is fine because it's faster" (Quiz 2A Q13 B). Wrong: it breaks the boundary.
- "A code comment / team agreement is enough to keep boundaries" (Q13 D). Wrong: it needs **mechanical enforcement** (CI check, Packwerk, TS module linting / project refs).
- "If one module misbehaves, move it to its own microservice" (Q13 C). Wrong: distribution needs measured pain.
- "Fix an unsafe retry with a longer timeout / immediate retry / try-catch" (Q12 B–D). Only an **idempotency key** makes the retry safe.
- "A timeout means the remote operation didn't run." Wrong: it may have run and the reply got lost (partial failure).
- "Every unique noun (e.g. Coupon) deserves a module." No: a noun is only a clue. Responsibility and rules decide.
- "Two features sharing a table today → they're one module" / "table design defines modules". No: table design must not decide boundaries.
- "One bounded context must be exactly one module / one microservice." No: it is *usually* one module candidate, not a law, and naming it does not make it a service.
- "Modules should share one canonical Order object." No: each context has its own order-like record. No giant shared mutable object.
- "Serverless is always cheaper." Prime Video shows per-transition billing plus S3 relays of heavy payloads was **prohibitively expensive**, and a single process on EC2/ECS saved 90%.
- "Prime Video moved *to* microservices to save money." The reverse: it moved *from* distributed/serverless *to* a monolith.
- "Shopify uses microservices at scale." It is a **modular monolith** at planetary scale.
- "Modular monolith = multiple deployables." No: **one deployable, one process**, still one deploy pipeline.
- "Modular monoliths lose ACID." No: ACID is easy in both monolith and modular monolith. Only microservices make transactions distributed and hard.
- "Microservices have no network overhead between services." They have it **on every boundary call**.
- "Team autonomy needs microservices." The modular monolith also gives **high** autonomy (via boundaries).
- Mixing up names: Conway (1967, Conway's Law); Evans (2003, DDD); Fowler (Monolith First); Sam Newman (7 principles); Werner Vogels (strategy, not religion).
- Mixing up the split threshold: it is **50 engineers** (or very different hardware scaling), not "when traffic grows" in general.
- Fallacy-list traps: "Latency is zero" and "Bandwidth is infinite" are separate fallacies; "Transport cost is zero" is about money (cross-region GB bills), not latency. "The network is homogeneous" covers hardware, kernels and MTUs. A distractor might add a fake fallacy such as "the CPU is infinite" or "storage is unlimited".
