## 1. One-paragraph summary

The lecture follows one tiny app, **hello-api** (FastAPI, two endpoints, one Postgres database, a connection pool of **max_size=5**), from source code to production. It asks three questions: **where does the app run** (hosting: VM, container PaaS, managed containers, serverless), **who keeps it running** (restart policy, process supervisor, orchestrator, managed platform), and **how do we justify that choice**. A live demo deploys hello-api by hand on one Linux VM: build and push an image, `docker run` with a restart policy, then Caddy, DNS, firewall and TLS, then config and secrets in an env file, then health checks, then killing the process. The demo shows that **a restart policy is a process supervisor for one host, not an orchestrator**. If the VM dies, nothing moves the app. The lecture then scales out (load balancer, 3 to 5 replicas, state kept in Postgres) and names the **four jobs of orchestration**: failure detection, scheduling, placement/startup, routing/service discovery. It explains **liveness / readiness / startup** checks and the **reconciliation loop** (desired state − observed state = actions). It ends with observability (logs, metrics, traces, alerts), traced to the pool limit of 5. **Main argument:** choose hosting by *who operates what*. No hosting model wins on every row. Compute and database are separate decisions. "Managed" does not mean "no responsibility". Do not pay for orchestration (Kubernetes) until the problem needs it. A two-person team at 40 req/min is better served by a PaaS plus a managed DB.

   - Secrets: credentials and other sensitive values (`DATABASE_URL=postgres://app:•••@db`).

   - Did not recover: ✗ VM lost (no other machine takes over), ✗ crash on every start (restart loop, no alert), ✗ certificate, disk, OS patches, backups, ✗ nobody was told anything happened.
   - "**A restart policy is a process supervisor for one host. It is not an orchestrator.**"
20. **The same app on a PaaS** — Developer `git push` → Git repository (main branch) → PaaS builds and deploys it → hello-api on a platform-provided hostname. "The platform typically handles: **build and deploy, runtime, routing, TLS, process restarts**." "You still own: **custom-domain DNS, configuration and secrets, database, health endpoints, logs, scaling limits, cost**." "Products differ in build pipelines, scale-to-zero, regions and pricing. Check what yours does."
21. **Traditional process vs serverless execution**
   - Traditional process (VM, PaaS, container): starts once, stays running; listens on a port; keeps memory and connections between requests; billed while it runs.
   - Serverless function: invoked by the platform per request or event; receives an event, returns a response; execution environments are ephemeral, so do not rely on local state persisting; billed per invocation and duration.
22. **Vertical vs horizontal scaling**
   - Vertical, a bigger machine (1 vCPU / 2 GB → 8 vCPU / 32 GB): simple, nothing else changes; has a ceiling and needs a restart; still one point of failure.
   - Horizontal, more instances (1 copy → copy 1, 2, 3): survives losing an instance; needs a load balancer in front; needs state kept outside each copy.
23. **hello-api, scaled out** — Load balancer (routes traffic) → hello-api-1/2/3 (healthy) → Postgres (persistent state). "How does the system know when an instance is unhealthy?" "**hello-api scales out because its persistent state lives in Postgres, not in process memory.**"
24. **Five containers on two machines** — VM A: hello-api-1, 2, 3 running. VM B: hello-api-4, 5 running. A load balancer in front.
25. **One machine disappears** — VM A ✗ unreachable, so 1, 2, 3 are gone. VM B: 4, 5 still running. "Even if the load balancer stops sending traffic to the dead instances, **who replaces the three missing containers?**"
26. **The orchestration problem: four jobs, no owner**
   1. Who notices the failure? · **failure detection**
   2. Who finds capacity? · **scheduling**
   3. Who places and starts the workload? · **workload placement / startup**
   4. Who updates traffic to the new addresses? · **routing / service discovery**
27. **Three questions every instance can answer**
   - **Liveness**: "Am I alive?" Fails → **restart me**. `/healthz`
   - **Readiness**: "Can I serve traffic?" Fails → **stop routing to me. No restart.** `/readyz` (here: `/hello`)
   - **Startup**: "Have I finished booting?" Fails → **wait before running other checks.** Use case: slow start, big cache.
   - "**Load balancers use readiness to choose targets. Orchestrators use liveness to restart.**" "In production, use a dedicated readiness endpoint that checks the dependencies required to serve traffic. /hello is used here only to make the distinction visible."
28. **The CS underneath: Orchestrators run a reconciliation loop** — "**desired state − observed state = actions**". Desired: 5 hello-api containers, healthy. Observed: 2. Actions: start 3 containers on machines with free capacity, update the load balancer. "The loop keeps attempting recovery automatically. **Humans are paged when it cannot recover or user-facing symptoms persist.**" "**You declare what should be true. The orchestrator keeps making it true.**"
29. **From process supervisor to managed platform** (a ladder):
   - Process supervisor: **systemd**, restarts one process.
   - Container runtime: **Docker restart policy**, one host.
   - Orchestrator: **Kubernetes, Swarm**, many hosts, desired state.
   - Managed platform: the provider operates the scheduling and control plane for you.
   - "Docker's restart policy handles one host. It does not find capacity or reroute traffic. That takes an orchestrator."
30. **PREDICT** — "Two engineers run hello-api and one Postgres, about **40 requests a minute**. Which setup fits?" A) Kubernetes on three nodes you operate. **B) A PaaS container and a managed database.** C) Docker Swarm on two VMs you maintain. (Answer not on the slide. B is the intended answer, from the course objective "when [orchestration's] complexity is not yet worth paying" — **(inferred)**.)
31. **Five different questions** — Deployment: how does new code get there? (git push, a pipeline, docker run). Hosting: where does it run? (VM, PaaS, managed containers, serverless). Orchestration: who keeps the desired number of healthy instances running? (restart, reschedule, reroute). Observability: how do we know what is happening? (logs, metrics, traces, alerts). Recovery: what happens when something fails? (restart, roll back, fail over, page a human).
32. **How do you know a production system is healthy?** — Logs: what happened? (`GET /hello 500 db timeout`). Metrics: how much, how often? (`p95 latency 2.3 s`, `error rate 4%`). Traces: where did this request spend its time? (`API 14 ms, DB 2,300 ms`). Alerts: when does a human need to react? (`errors above 2% for 5 min`).

   - **An image is the artifact. A tag names one exact version.**
   - **A restart policy is not an orchestrator.**
   - **Liveness means "restart me". Readiness means "stop sending me traffic".**
   - **Scaling out needs stateless app servers.**

## 3. Key concepts & definitions

- **Image**: the packaged artifact, made of the app plus its runtime dependencies, built from a Dockerfile (the recipe). The same image runs the same way on compatible container hosts. Example: `ghcr.io/acme/hello-api:1.0`.
- **Tag**: "a tag names one exact version" (e.g. `:1.0`). The registry also reports a content **digest** (`sha256:…`). (general knowledge: a tag can be moved to a different image later; the digest cannot.)
- **Container**: a running instance of an image. Example: the `hello-api` container running `uvicorn main:app`.
- **Registry**: stores images. It is how the artifact gets from the build machine to the run machine. Example: `ghcr.io` (GitHub Container Registry).
- **VM**: a whole virtual machine with its own operating system (kernel, packages, users). You manage the OS and runtime.
- **Hosting**: where the app runs. The four models are VM, container PaaS, managed containers and serverless. You choose by **who operates what**.
- **Container PaaS**: you `git push` and the platform builds, deploys, routes, adds TLS and restarts processes. You still own DNS for your custom domain, config and secrets, the DB, health endpoints, logs, scaling limits and cost. (Course tools: Railway or Render. Enterprise: AWS ECS/Fargate, GCP Cloud Run. From the course outline, not the slides.)
- **Managed containers**: the provider manages the container fleet and scheduling. You supply images and replica counts.
- **Serverless**: the provider invokes your code per request or event. The environment is short-lived (ephemeral), so local state may not persist. You are billed per invocation and duration.
- **Managed database**: the provider does backups, patching and failover (Supabase, AWS RDS). You still own the schema, access rules, credentials and **restore tests**.
- **Configuration vs secrets vs code**: code is the same everywhere and lives in Git. Config changes per environment and may be non-secret (`LOG_LEVEL`). Secrets are credentials (`DATABASE_URL` with a password). Secrets never go in code or images. Inject them at run time (`--env-file`).
- **Reverse proxy**: "one public door, forwards inward". Example: Caddy on 443 forwards to 127.0.0.1:8000 and also gets the TLS certificate.
- **Restart policy**: Docker restarts a crashed container on the same host (`--restart unless-stopped`). It is a process supervisor for one host, **not an orchestrator**.
- **Process supervisor**: systemd restarts one process.
- **Orchestrator**: manages many hosts toward a desired state (Kubernetes, Swarm). It does four jobs: failure detection, scheduling, placement/startup, routing/service discovery. In short it restarts, reschedules and reroutes.
- **Scheduling**: finding a machine with free capacity for a workload.
- **Service discovery / routing**: updating traffic (the load balancer) to point at the new instance addresses.
- **Desired state / reconciliation loop**: you declare what should be true (5 healthy containers). The orchestrator keeps comparing it with what it observes (2) and acts on the difference (start 3, update the LB). "desired − observed = actions." Humans are paged only when it cannot recover or users still see symptoms.
- **Managed platform**: the provider runs the scheduling and the control plane for you.
- **Liveness probe**: "Am I alive?" If it fails, the instance is **restarted**. Example: `/healthz`. Orchestrators use it.
- **Readiness probe**: "Can I serve traffic?" If it fails, traffic **stops being routed** to the instance, with **no restart**. Example: `/readyz` (the demo used `/hello`, which needs the DB). Load balancers use it.
- **Startup probe**: "Have I finished booting?" If it fails, the other checks wait. Example: slow start, big cache.
- **Vertical scaling**: a bigger machine. Simple, but has a ceiling, needs a restart, and is still one point of failure.
- **Horizontal scaling**: more copies. Survives losing one copy, but needs a load balancer and state kept outside the copies (stateless app servers).
- **Stateless app server**: keeps no persistent state in process memory. hello-api keeps it in Postgres, which is why it can scale out.
- **Observability**: logs (what happened), metrics (how much, how often, e.g. p95 latency, error rate), traces (where one request spent its time), alerts (when a human must react).
- **Connection pool** (`max_size=5`): each instance can open at most 5 DB connections. When all 5 are busy, requests queue ("waiting for a free connection"). This was the root cause in the trace example.

## 5. Decision rules / trade-offs

- **Choose hosting by "who operates what"**, not by habit (course objective: "choose deliberately … rather than defaulting to whatever is familiar").
  - Want the most control or unusual OS needs → **VM**. In exchange you get many chores (OS patching, TLS, firewall, backups, restarts) and you scale by hand.
  - Small team, normal web app, fastest start → **Container PaaS** ("lowest to start"). Lock-in is low to medium.
  - Need many replicas or services with container-level control, but do not want to run the control plane → **managed containers** (replica counts, medium lock-in).
  - Spiky or event-driven, short work, no long-lived state → **serverless**. Billing is per invocation, it is "simple until debugging", and lock-in is higher.
- **Database is a separate decision.** Managed DB removes backups, patching and failover work. It does NOT remove schema, access rules, credentials or restore testing.
- **Don't adopt an orchestrator before you need one.** Two engineers, one app, 40 req/min → PaaS + managed DB, not self-run Kubernetes or Swarm. Kubernetes solves multi-host failure detection, scheduling, placement and rerouting. If you have one small app, you pay its operating cost without getting the benefit (course objective: "when its complexity is not yet worth paying").
- **Restart policy vs orchestrator**: one VM plus `--restart unless-stopped` covers process crashes and host reboots. It does not cover losing the host. If you need to survive losing a machine, you need several hosts plus something that reschedules (an orchestrator or a managed platform).
- **Vertical vs horizontal**: vertical first is simple (nothing else changes), but it has a ceiling, needs a restart, and is still a single point of failure. Horizontal survives an instance loss, but needs an LB and stateless servers.
- **Scaling out needs state outside the process** (Postgres), not in memory or the local disk.
- **Serverless + relational DB caution**: each invocation may open its own connection, so many invocations can hit the DB's connection limit. (From the course outline's T4 theory thread: "connection pooling as the specific reason that serverless compute and relational databases interact badly: one connection per invocation against a hard server limit". Not on these slides.) Related slide fact: the pool is 5 per instance, so N instances can use up to 5×N connections **(inferred arithmetic)**.
- **Health endpoints**: use liveness for "restart if dead". Use a separate readiness check that tests the dependencies (DB) for "remove from LB but don't restart". Do not make liveness depend on the DB **(general knowledge)**: a DB outage would then restart every healthy instance for nothing.
- **Secrets** go in the environment or server-side file, never in Git or the image. One image is used in every environment, and only the config changes.
- **Backups** are only proven by a tested restore.


```bash
# Step 3 — run on VM
ssh deploy@203.0.113.10
docker run -d --name hello-api --restart unless-stopped \
   -p 127.0.0.1:8000:8000 ghcr.io/acme/hello-api:1.0
#  -d                       detached (background)
#  --name hello-api         fixed container name (used by logs/rm)
```

**Not shown on slides, but likely needed for hands-on tasks (general knowledge):**
- Why recreate rather than restart in Step 5: `docker restart` keeps the old env. Env vars are only read at `docker run`/create. (Fits T3's "Restart is not recreate".)
- `docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' hello-api` shows the restart policy. `docker update --restart unless-stopped hello-api` changes it on a running container.
- Restart policies: `no` (default), `on-failure[:N]`, `always`, `unless-stopped`. The difference: `always` also restarts a container you stopped by hand once the Docker daemon restarts. `unless-stopped` does not.
- `docker tag hello-api:1.0 ghcr.io/acme/hello-api:1.0` adds a registry name to an existing image.
- `docker run -e KEY=value` sets one env var. `--env-file` reads `KEY=value` lines.
- Docker HEALTHCHECK in a Dockerfile: `HEALTHCHECK --interval=10s --timeout=3s --retries=3 CMD curl -f http://localhost:8000/healthz || exit 1`. Plain Docker only marks the container `unhealthy`. It does **not** restart it (Swarm/orchestrators act on it).
- Docker Compose equivalent (the course uses Compose for local environments):
  ```yaml
  services:
    api:
      image: ghcr.io/acme/hello-api:1.0
      restart: unless-stopped
      env_file: /etc/hello-api.env
      ports: ["127.0.0.1:8000:8000"]
      healthcheck:
        test: ["CMD", "curl", "-f", "http://localhost:8000/healthz"]
        interval: 10s
        retries: 3
      depends_on: [db]
    db:
      image: postgres:16
      environment: { POSTGRES_PASSWORD: dev }
      volumes: [pgdata:/var/lib/postgresql/data]
  volumes: { pgdata: {} }
  ```
  `docker compose up -d`, `docker compose ps`, `docker compose logs api`, `docker compose up -d --scale api=3` (scaling only works if there is no fixed host port or `container_name`).
- Kubernetes equivalents: Deployment `spec.replicas: 5` (desired state); `livenessProbe` / `readinessProbe` / `startupProbe` with `httpGet: {path: /healthz, port: 8000}`; `kubectl apply -f deploy.yaml`, `kubectl get pods`, `kubectl scale deployment hello-api --replicas=5`, `kubectl delete pod X` (the Deployment recreates it, which is reconciliation); a Service gives a stable name and does service discovery; a Secret or ConfigMap holds env values.

## 7. Common misconceptions / distractor traps

- "Restart policy = orchestration / high availability." **False.** It covers one host only. If the VM dies, nothing reschedules.
- "`--restart` will alert me / fix a crash loop." **False.** A crash on every start gives a restart loop with no alert. Nobody is told.
- "A managed DB means I don't have to think about backups or restores." **False.** Restore tests, schema, access rules and credentials are still yours. "Managed does not mean responsibility-free."
- "Nightly backups for a year = data is safe." **False.** It only proves the script ran. Only a tested restore proves recoverability.
- "A replica will be promoted automatically" (for a self-hosted DB with cron dumps). Nothing on the slide says a replica or failover exists.
- "A PaaS handles everything." **False.** You still own custom-domain DNS, config and secrets, DB, health endpoints, logs, scaling limits, cost.
- "A PaaS is really just VMs, so it's the same as choosing a VM." **False.** VMs inside are a provider detail, not the abstraction you choose.
- "Readiness failure restarts the container." **False.** Readiness → stop routing, **no restart**. Liveness → restart.
- "The load balancer uses liveness." **False.** LBs use **readiness**. Orchestrators use **liveness** to restart.
- "/healthz OK means the app works." **False.** It only shows the process is up. /hello (the DB path) can still fail. Two checks catch two different failures.
- "The load balancer will replace dead instances." **False.** It only stops routing. Replacing them is scheduling/placement (the orchestrator).
- "Vertical scaling removes the single point of failure." **False.** It is still one machine, has a ceiling and needs a restart.
- "Any app can scale horizontally." **False.** It needs stateless app servers, with state in Postgres or similar, and an LB.
- "Serverless keeps memory/connections between calls" or "listens on a port." **False.** It is ephemeral, invoked per event, and billed per invocation and duration.
- "Serverless has the lowest lock-in." **False.** It has the *highest* ("Higher"). VM is Low.
- "Kubernetes is the professional default." **False** for 2 engineers at 40 req/min. Complexity has a cost.
- "Bake DATABASE_URL into the image so it's consistent." **False.** Never bake secrets into code or images. Inject per environment.
- "`-p 127.0.0.1:8000:8000` makes the app public." **False.** It is localhost-only. The reverse proxy is the public door.
- "Get the TLS certificate first, then set DNS." **False.** DNS must point to the server first.
- "Changing the env file is picked up automatically / by `docker restart`." **False (general knowledge).** The demo removes and re-runs the container.
- "Adding more instances fixes DB slowness." Not necessarily. The trace shows the time is in the DB, waiting on the pool (max_size=5). More instances means more connections hitting Postgres **(inferred)**.
- "Orchestrator pages a human for every failure." **False.** It keeps reconciling automatically. Humans are paged when it cannot recover or user-facing symptoms persist.
- "systemd/Docker restart can find capacity on another host." **False.** That takes an orchestrator.

## 8. Likely quiz angles

**MCQ scenarios (choose-all-that-apply style)**
1. *hello-api runs on one VM with `--restart unless-stopped`.* Which events recover automatically? ✓ process crash, ✓ host reboot. ✗ VM lost, ✗ crash on every start (loops, no alert), ✗ expired cert/full disk.
2. *Backup predict variant*: cron dumps every night for a year, the disk dies. What do you know? → only that the script ran; a restore was never tested.
3. *Probe semantics*: the DB goes down; `/healthz` is OK, `/readyz` fails. What should happen? ✓ LB stops sending traffic to it, ✓ the container is NOT restarted. ✗ the orchestrator restarts it. ✗ liveness fails.
4. *Which component uses which probe*: LB → readiness, orchestrator → liveness; startup probe → slow boot / big cache.
5. *VM A with 3 of 5 replicas disappears*. Which job is "who finds capacity"? → scheduling. "Who updates traffic to new addresses"? → service discovery/routing. Desired 5, observed 2 → actions: start 3 + update LB.
6. *Team of 2, 40 req/min, one Postgres* → PaaS container + managed DB (distractors: self-run K8s on 3 nodes, Swarm on 2 VMs).
7. *Ownership on a PaaS + managed DB*: which are still yours? ✓ custom-domain DNS, ✓ secrets, ✓ schema, ✓ restore tests, ✓ cost/scaling limits. ✗ OS patching, ✗ TLS issuance on the platform hostname, ✗ process restarts.
8. *Trade-off table*: which model is "billed per invocations + duration" with "higher" lock-in? → serverless. "Lowest to start"? → container PaaS. "Highest control"? → VM.
9. *Scaling*: why can hello-api scale out? → state lives in Postgres, not in memory. Which are true of horizontal scaling? ✓ survives losing an instance, ✓ needs an LB, ✓ needs external state. ✗ needs a restart / has a hard ceiling (those describe vertical).
10. *Secrets*: where should the prod `DATABASE_URL` go? ✓ env file on the server / platform secret store. ✗ Dockerfile `ENV`, ✗ committed .env, ✗ inside the image. And "same image, new configuration" is the goal.
11. *Going public*: `curl https://api.acme.dev` fails with the certificate pending. Why? → no DNS A record yet. Also: why can't outsiders reach :8000? → bound to 127.0.0.1; only 22/80/443 are open; the proxy forwards inward.
12. *Observability diagnosis*: alert p95 > 1 s after the 14:02 deploy, trace 2,300 of 2,319 ms in the DB, log "waiting for a free connection (pool max_size=5)". What is the bottleneck? → the DB connection pool, not the API CPU. Which signal answers "where did the time go"? → trace. "When must a human react"? → alert.
13. *Five questions mapping*: "git push / pipeline / docker run" → Deployment. "Restart, reschedule, reroute" → Orchestration. "Roll back, fail over, page a human" → Recovery.
14. *Serverless*: which are true? ✓ no reliance on local state, ✓ invoked per event, ✓ billed per invocation and duration. ✗ keeps DB connections between requests. (Outline link: each invocation opening a DB connection can exhaust Postgres limits.)
15. *Ladder*: match systemd / Docker restart policy / Kubernetes-Swarm / managed platform to one process / one host / many hosts with desired state / provider-run control plane.

**Hands-on terminal tasks (graded on final state)**
- **Build, tag, run**: `docker build -t hello-api:1.0 .`, then run detached named `hello-api`, restart policy `unless-stopped`, port `127.0.0.1:8000:8000`. *Checked:* image exists with that tag; container running; `RestartPolicy=unless-stopped`; port bound to 127.0.0.1:8000→8000.
- **Config via env file**: create `hello.env` with `LOG_LEVEL=info` and `DATABASE_URL=…`; recreate the container with `--env-file`. *Checked:* container env contains those keys; the image does NOT contain the secret (no `ENV DATABASE_URL` in the Dockerfile); `.env` not committed / in `.gitignore`.
- **Fix a Dockerfile that bakes a secret** (`ENV DATABASE_URL=postgres://...`): remove it and pass it at run time. *Checked:* `docker inspect` of the image shows no DATABASE_URL; the running container has it.
- **Demonstrate the restart policy**: kill the main process (`docker kill`, or `pkill` inside); the container comes back. *Checked:* container running, RestartCount ≥ 1.
- **Change the restart policy without recreating**: `docker update --restart unless-stopped <name>`.
- **Retag for a registry**: `docker tag hello-api:1.0 ghcr.io/acme/hello-api:1.0` (a push might be to a local registry, e.g. `localhost:5000/hello-api:1.0`). *Checked:* the tag exists / the registry has the repo:tag.
- **Compose file**: write or fix `compose.yaml` with `restart: unless-stopped`, `env_file`, `ports: "127.0.0.1:8000:8000"`, a `healthcheck` on `/healthz`, `depends_on: db`, a named volume for Postgres. Then `docker compose up -d`, maybe `--scale api=3` (drop the fixed host port / `container_name`). *Checked:* services running, N replicas, health status healthy, volume exists.
- **Inspect / logs**: `docker logs --tail 2 hello-api > reports/last.txt`; `docker ps` filters; grep the logs for `500` (like Quiz 1A Q18).
- **Probe endpoints**: add `/readyz` that checks the DB, separate from `/healthz` (if the task is code-based). *Checked:* `/healthz` 200 without the DB; `/readyz` non-200 when the DB is down.
- **(If K8s/kind is in the portal, less likely)**: a Deployment with `replicas: 3` plus liveness on `/healthz` and readiness on `/readyz`; `kubectl scale`; delete a pod and observe it come back.
