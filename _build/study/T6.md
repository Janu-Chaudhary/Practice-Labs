## 1. One-paragraph summary

The lecture follows one story. **RailBook** opens **Tatkal** booking at **10:00**. A few thousand people wait on the page and all click at once. Every app server and every request share **one database**, so the database is what breaks. The deck covers **four things that go wrong, one per section**:
- **(A) Round trips:** the **N+1** query pattern multiplies network latency.
- **(B) Finding rows:** with no index the database does a **sequential scan**. A **B-tree index** fixes this, and for a **composite index** the **leading-column rule** matters. Indexes also have costs.
- **(C) Connections:** Postgres has a hard **max_connections** limit (default 100). Connections **multiply when you scale out**, so you size pools on purpose, use wait timeouts, use a pooler, and remember that **queues explode near 100%**.
- **(D) The last seat:** **check-then-act races** oversell a seat even inside a transaction. The three fixes are **one atomic UPDATE**, **SELECT … FOR UPDATE**, and **constraints as a safety net**.

The main argument: code that works for one user at a time on your laptop fails under real concurrency and distance. You must **predict, break it on purpose, measure, and fix**, and let the database enforce correctness.

## 3. Key concepts and definitions

**Round trip / network latency.** Each query goes to the database and back. That trip costs about 1 ms when the DB is on your laptop, and tens of ms when it is in another data centre. Example: 50 items bought one at a time means 50 trips to the shop.

**N+1 query.** You run one query for a list, then one more query per row. N rows give N+1 queries. Example: 1 query for 50 bookings plus 50 passenger queries = **51 queries**. It is cheap on a laptop (51 × 1 ms) and slow in production (51 × 30 ms ≈ 1.5 s). The fix is to fetch all children in one go (general knowledge on the exact method; the slides demo "count, fix, measure"):
- a `JOIN`, or
- `WHERE booking_id = ANY($1)` / `IN (...)` with all the booking ids, or
- eager loading in an ORM.

Result: 1–2 queries instead of 51. The course outline adds: N+1 is "invisible in code review and obvious in a trace".

**Sequential scan (Seq Scan).** A table is stored as pages on disk. With no usable index, Postgres reads every page to find matching rows. Example: finding PNR 4521873390 among 1,00,000 unsorted names.

**Index / B-tree.** An index is a sorted copy of some columns with pointers back to the rows, like the index at the back of a book. Postgres uses a B-tree, a short, wide search tree, so a lookup takes a handful of steps even among crores of rows. Example: 3 steps to find PNR 4521873390.

**Composite index and the leading-column rule ("phone directory rule").** A multi-column index is sorted by the first column, then by the second within each value of the first. It helps queries that filter on the **leading (first) column**, alone or together with the next column. It does not help queries that filter only on a later column. Example: index `(from_station, journey_date)`:
- station alone: fast
- station + date: fast
- date alone: no help.

**Indexes are not free.** Every INSERT or UPDATE must also update every index, and indexes use disk space. So index the queries you run often, not every column. This is a write cost: more indexes make writes slower.

**EXPLAIN.** Shows the plan Postgres chose. Before an index you see `Seq Scan`. After it you see `Index Scan` with an `Index Cond`, and a lower execution time. (`EXPLAIN ANALYZE` actually runs the query and shows real times: general knowledge.)

**CREATE INDEX vs CREATE INDEX CONCURRENTLY.**
- Plain `CREATE INDEX` blocks writes while it builds.
- `CONCURRENTLY` lets writes continue, but it **cannot run inside a transaction** and takes longer.

**Connection.** A connection to Postgres is a "phone line to one operator". Each one starts a separate server process with its own memory, so the number is capped by `max_connections` (default **100**).

**Connection pool.** Keeps a few connections open and lends them to requests. Example: one app server with pool: 10 holds 10 connections.

**Connections multiply when you scale.** Each new app server (or serverless instance) brings its own pool. Example: 8 servers × 10 = 80; 200 serverless functions × 5 = 1000.

**Past the limit.** Connection 101 is refused and the request that needed it fails with `FATAL: sorry, too many clients already`.

**Pool wait timeout.** Instead of failing at once, a request waits a bounded time for a free pooled connection.

**Pooler (PgBouncer, Supavisor).** A "reception desk" in front of Postgres that lets many app connections share a few DB connections. Example: 12 app connections share 5 DB processes.
- **Session mode:** a DB connection stays with one client until it disconnects.
- **Transaction mode:** a DB connection is lent for one transaction and then returned. It can't keep state between transactions, such as **prepared statements or session locks**.

**Queueing near 100% utilisation.** With one counter and random arrivals, waiting time is small at 50% busy, long at 90%, and explodes at 99%. Latency rises without bound as utilisation approaches 1. The course outline says: "Queues, not processors, are what fail." (General knowledge: for a simple M/M/1 queue, wait is proportional to ρ/(1−ρ). That gives 1 at 50%, 9 at 90% and 99 at 99%, so 90% is 9× worse than 50% and 99% is 99× worse.)

**Race condition / check-then-act.** You read state (check), then write based on it (act). Another request can change the state in the "danger window" between the two. Example: two requests both read booked = 99, capacity = 100, both decide to book, and you get 2 bookings for 1 seat. Tests pass because they send one request at a time.

**Transaction (BEGIN … COMMIT).** All or nothing: every statement lands together or none does. Example: a UPI transfer, where the debit and credit of ₹1,450 happen together. A transaction alone does **not** stop two requests reading the same count. (General knowledge: Postgres's default isolation level is READ COMMITTED.)

**Fix 1: atomic conditional UPDATE.** Put the check inside the write's `WHERE` clause (`booked < capacity`) so checking and acting happen in one statement. If 1 row comes back you got the seat. If 0 rows come back the train is full, so return **HTTP 409** (Conflict).

**Fix 2: pessimistic row lock (`SELECT … FOR UPDATE`).** Lock the train's row first, then count and insert, then COMMIT. Other requests wait on that row until you commit ("holds the pen").

**Fix 3: constraints.** `CHECK (booked <= capacity)` and `UNIQUE (train_id, seat_no)`. The database refuses a bad row even if your code has a bug. They are a safety net, not the main logic.

**SERIALIZABLE isolation (AWARE).** Postgres detects conflicting transactions and aborts one, and you **retry** it.

**Optimistic locking (AWARE).** Uses a `version` column. Your update fails if someone changed the row first (for example `UPDATE … SET …, version = version + 1 WHERE id = $1 AND version = $2`; 0 rows means retry: general knowledge on the exact syntax).

**Distributed locks (AWARE).** Redis and similar tools, for state **outside one database**.

**Little's law (course outline only, not on slides; general knowledge).** L = λ × W: items in the system = arrival rate × time each spends in it. Example: 200 req/s × 0.05 s = 10 requests in flight, so you need about 10 connections busy at once.

**Load-testing methodology (course outline only; general knowledge).**
- **Ramp:** increase load step by step. It answers "where does it break?"
- **Soak:** hold steady load for hours. It answers "does it leak or degrade over time?"
- **Spike:** a sudden jump, like Tatkal at 10:00. It answers "does it survive a burst?"

The course tool is **k6**, with Locust, JMeter and Gatling as alternatives.

## 5. Decision rules and trade-offs

1. **Many small queries vs one bigger query.** When the DB is far away, the number of round trips dominates. Batch or join to cut trips. Check by counting queries before and after the fix, then measure response time.
2. **Index or not?** Index the columns your frequent queries filter or join on. Don't index every column, because each index slows every INSERT/UPDATE and uses disk. Read-heavy tables gain more from indexes; write-heavy tables pay more for them.
3. **Composite column order.** Put the column you **always** filter on first. If some queries filter only on the second column, they need their own index (general knowledge).
4. **Planner may ignore an index (course outline: "a correctly built index can be correctly ignored").** If a query returns a large share of the table (low selectivity), a Seq Scan can be cheaper, so the planner picks it on purpose. Stale statistics can also mislead it, and `ANALYZE` refreshes them (general knowledge / outline).
5. **Building an index on a live table.** Use `CREATE INDEX CONCURRENTLY` to avoid blocking writes. The cost is a slower build and no transaction wrapper, which matters for migration tools that wrap each migration in a transaction (general knowledge).
6. **Pool sizing.** Add up **all** clients (every server's pool, cron/reporting jobs, humans with psql) and stay under `max_connections` minus spare. Leave headroom for autoscaling. Serverless with per-instance pools blows past limits quickly, so put a pooler in front.
7. **Fail fast vs wait.** Without a wait timeout, requests fail when the pool is empty. A wait timeout queues them briefly so short spikes degrade gracefully. It must be bounded so requests don't hang forever.
8. **Session vs transaction pooling.**
   - Transaction mode shares connections far better (more clients per DB connection), but you lose session-level features: prepared statements and session locks (and `SET`/temp tables: general knowledge).
   - Session mode keeps those features but gives less sharing.
9. **Don't run near 100% utilisation.** Waiting time grows non-linearly. Keep headroom, because going from 90% to 99% does not cost "9% more", it makes the queue explode.
10. **Choosing a race fix:**
    - **Fix 1 (single conditional UPDATE):** the simplest, no explicit lock held across statements. Best when the check fits in one `WHERE`.
    - **Fix 2 (FOR UPDATE):** use when the logic needs several statements (count, then insert). The cost is that others wait (serialised), so keep the transaction short.
    - **Fix 3 (constraints):** always add as a backstop. They catch bugs in your code.
    - **SERIALIZABLE / optimistic locking:** no waiting, but conflicts cause errors that you must **retry**.
    - **Distributed locks:** only for state outside a single DB.
11. **HTTP status on a full train:** **409 Conflict**, not 500 (it is an expected business outcome, not a server crash).

## 6. Commands, tools, config and code shown

**N+1 code (JavaScript, node-postgres style):**
```js
const bookings = await db.query(
  "SELECT * FROM bookings WHERE user_id = $1 LIMIT 50", [userId]);   // 1 query
for (const b of bookings) {
  b.passengers = await db.query(
    "SELECT * FROM passengers WHERE booking_id = $1", [b.id]);       // + 50 queries
}
```
The `$1` placeholders are parameterised queries. The `await` inside the loop is the warning sign. A possible fix (general knowledge):
```sql
SELECT * FROM passengers WHERE booking_id = ANY($1);   -- $1 = array of the 50 booking ids
-- or: SELECT b.*, p.* FROM bookings b JOIN passengers p ON p.booking_id = b.id WHERE b.user_id = $1;
```

**EXPLAIN demo (statements are general knowledge; the slide only names the plan nodes):**
```sql
EXPLAIN ANALYZE SELECT * FROM trains WHERE from_station='PUNE' AND journey_date='2026-11-14';
-- before: Seq Scan on ...      after: Index Scan using ... ; Index Cond: (...)
CREATE INDEX idx_trains_station_date ON trains (from_station, journey_date);
CREATE INDEX CONCURRENTLY idx_name ON tbl (col);   -- no write blocking; NOT inside BEGIN/COMMIT
```

**Break connections on purpose (exact slide command, terminal "t6-connections"):**
```sh
docker compose exec db sh -c \
  'for i in $(seq 30); do
     psql -U postgres -c "select pg_sleep(5)" >/dev/null &
   done; wait'
# ✗ psql: error: FATAL:  sorry, too many clients already   (×3 shown)
```
- `docker compose exec db` runs a command inside the running `db` service container.
- `sh -c '...'` runs a shell script there.
- `for i in $(seq 30)` loops 30 times.
- `psql -U postgres -c "select pg_sleep(5)"` opens a connection as user postgres and holds it for 5 seconds.
- `>/dev/null` hides normal output.
- `&` runs each one in the background so all 30 are open **at once**.
- `wait` waits for all of them to finish.
- With the limit set to 20, about 10 get the FATAL error.

How to set the limit (general knowledge; slide just says "Set the limit to 20"):
- `max_connections = 20` in postgresql.conf, or
- `command: postgres -c max_connections=20` in docker-compose, or
- `ALTER SYSTEM SET max_connections = 20;` followed by a restart.

Note: max_connections needs a **restart**, not just a reload. Check it with `SHOW max_connections;`. Count current connections with `SELECT count(*) FROM pg_stat_activity;`.

**Pool sizing check:** `8 servers × 10 = 80 ≤ 100 − 10 spare`. (In node-postgres a pool is `new Pool({ max: 10, connectionTimeoutMillis: 2000 })`, where `max` is the pool size and `connectionTimeoutMillis` is the wait timeout: general knowledge.)

**Poolers:** PgBouncer, Supavisor. In PgBouncer config, `pool_mode = transaction` or `pool_mode = session` (general knowledge).

**Transactions:** `BEGIN; … COMMIT;`

**Fix 1:**
```sql
UPDATE trains
   SET booked = booked + 1
 WHERE id = $1 AND booked < capacity
RETURNING booked;
-- 1 row → seat booked;  0 rows → full → HTTP 409
```

**Fix 2:**
```sql
BEGIN;
SELECT capacity FROM trains WHERE id = $1 FOR UPDATE;
SELECT count(*) FROM bookings WHERE train_id = $1;
-- if count < capacity: INSERT INTO bookings ...
COMMIT;
```

**Fix 3:**
```sql
CHECK (booked <= capacity)
UNIQUE (train_id, seat_no)
-- e.g. ALTER TABLE trains ADD CONSTRAINT booked_le_capacity CHECK (booked <= capacity);
--      ALTER TABLE bookings ADD CONSTRAINT uniq_seat UNIQUE (train_id, seat_no);   (general knowledge)
```

## 7. Common misconceptions and traps

- **"It's fast on my laptop, so it's fine."** Wrong. On a laptop 51 queries × 1 ms ≈ 51 ms; in production 51 × 30 ms ≈ 1.5 s. Distance multiplies round trips.
- **"N+1 is about the database being slow."** No. Each query may be fast. The cost is the **number of round trips × latency**.
- **"Any index on those columns helps any query on them."** Wrong. With `(from_station, journey_date)`, a query on **date alone gets no help**, and a query on `train_no` can't use it at all.
- **"Column order in a composite index doesn't matter."** It does: leading-column rule.
- **"More indexes = faster."** Reads may get faster, but **every write updates every index**, and indexes take disk space.
- **"An index always gets used."** The planner can correctly choose a Seq Scan for low-selectivity queries or because of stale stats (outline).
- **"CREATE INDEX CONCURRENTLY is strictly better / can go in a migration transaction."** It **can't run inside a transaction** and builds slower.
- **"CREATE INDEX blocks reads."** The slide says it **blocks writes**. (Reads continue: general knowledge.)
- **"Scaling out app servers fixes load."** Each server adds its own pool, so **connections multiply**, and the DB limit (100) is hit sooner. The outline says the DB, not the app, is usually the first to fail.
- **"Serverless scales infinitely."** 200 functions × pool 5 = 1000 connections against a limit of 100.
- **"Past the limit, requests just queue at Postgres."** No. Connection 101 is **refused** with a FATAL error and the request fails. Queuing only happens if *your pool* has a wait timeout.
- **"Only the app servers use connections."** Reporting jobs and your own psql session count too.
- **"Transaction-mode pooling is a free upgrade."** You lose prepared statements and session locks between transactions.
- **"90% CPU/DB busy is fine, there's 10% left."** Queues grow non-linearly: 90% gives a long queue, 99% makes it explode.
- **"Wrapping check + insert in BEGIN/COMMIT prevents overselling."** **False.** Both transactions can read the same count before either inserts (poll answer B). A transaction gives all-or-nothing, not mutual exclusion.
- **"The transaction wasn't committed" / "Postgres doesn't support transactions under load."** These are the poll's wrong options.
- **"Tests passed, so there is no race."** Tests send one request at a time; races need concurrency.
- **"Constraints replace the locking fix."** They are a **safety net** for bugs. You still need Fix 1 or Fix 2 for correct, friendly behaviour (409 instead of a constraint error).
- **"On a full train return 500 / 404."** The slide says **409**.
- **"FOR UPDATE locks the whole table."** It locks the selected **row(s)**, here the train's row. Others wait on that row only.
- **"SERIALIZABLE means no errors."** Postgres **aborts** one conflicting transaction, and you must **retry**.
- **"Optimistic locking waits for the lock."** No. It doesn't lock; the update **fails** (0 rows) if the version changed.
- **"Distributed locks are needed for the seat problem."** Only for state **outside one database**. In one Postgres, use Fix 1/2/3.

## 8. Likely quiz angles

### MCQ / scenario ideas (choose-all-that-apply style)

1. **Calculation, N+1:** "A page lists 40 orders and fetches each order's items in a loop. The DB is 25 ms away. About how long do the DB trips take?" → 41 × 25 = **1,025 ms ≈ 1 s**. Distractors: 25 ms, 65 ms (one trip + one), 40 s.
2. **N+1 fixes, choose all:**
   - ✓ fetch all passengers with one `WHERE booking_id = ANY(...)`
   - ✓ JOIN bookings and passengers
   - ✗ add an index on passengers.booking_id (helps each query but still 51 trips)
   - ✗ increase pool size
   - ✗ move the loop to a faster CPU
3. **Composite index**, index `(from_station, journey_date)`, choose all that use it:
   - ✓ `from_station='PUNE'`
   - ✓ `from_station='PUNE' AND journey_date='…'`
   - ✗ `journey_date='…'`
   - ✗ `train_no='12124'`

   Variant: "Most queries filter only by date; which index?" → put `journey_date` first, or add a separate index.
4. **EXPLAIN reading:** given before/after output, which statements are true?
   - ✓ before shows Seq Scan
   - ✓ after shows Index Scan with Index Cond
   - ✓ execution time dropped
   - ✗ "the index made inserts faster"
5. **Index costs, choose all:**
   - ✓ every insert updates every index
   - ✓ uses disk
   - ✗ indexes slow down SELECTs on unindexed columns
   - ✗ Postgres automatically indexes every column
6. **Live index build:**
   - ✓ plain CREATE INDEX blocks writes while building
   - ✓ CONCURRENTLY doesn't block writes
   - ✓ CONCURRENTLY can't run inside BEGIN/COMMIT
   - ✗ CONCURRENTLY is faster to build
7. **Calculation, connections:** "max_connections = 100. 12 app servers with pool 8, plus a cron job with pool 5. What happens at peak?" → 96 + 5 = 101 > 100, so one connection is refused with `FATAL: sorry, too many clients already`. Also: "With 10 spare, what's the largest per-server pool for 9 servers?" → 9 × p ≤ 90, so **p = 10**.
8. **Serverless:** "300 concurrent functions, each pool size 2, limit 100" → 600. Fixes, choose all:
   - ✓ pooler in front (PgBouncer/Supavisor)
   - ✓ smaller per-instance pool
   - ✗ "raise to 600 is free" (each connection is a process with its own memory)
9. **Pooler modes:**
   - ✓ transaction mode lends a connection per transaction
   - ✓ transaction mode can't keep prepared statements/session locks
   - ✓ session mode keeps the connection per client until disconnect
   - ✗ session mode shares a connection among clients mid-session
10. **Queueing:** "DB at 50% → 90% → 99% utilisation; which describes latency?" → grows slowly, then explodes (non-linear). Distractor: "rises linearly with utilisation". Discussion-prompt variant from the outline: "Median unchanged, p99 tripled" → plausible causes: occasional queueing near saturation / pool waits, a few requests hitting Seq Scans or lock waits (FOR UPDATE contention), periodic jobs (reporting) holding connections (general knowledge).
11. **Oversell, choose all true:** with check then insert inside BEGIN/COMMIT, 10 concurrent requests for 1 seat:
    - ✓ more than one can succeed
    - ✓ both read the same count before either inserted
    - ✗ the transaction wasn't committed
    - ✗ Postgres disables transactions under load
    - ✓ unit tests sending one request at a time would pass
12. **Fixes, choose all that guarantee only one wins:**
    - ✓ `UPDATE … WHERE booked < capacity RETURNING`
    - ✓ `SELECT … FOR UPDATE` then count/insert in the same transaction
    - ✓ `CHECK (booked <= capacity)` (rejects the overflow)
    - ✗ wrapping the original check+insert in BEGIN/COMMIT
    - ✗ adding a retry loop
    - ✗ adding an index on train_id

    Follow-ups: "UPDATE returned 0 rows, what should the API return?" → **409**. "Which approach aborts a transaction and expects you to retry?" → SERIALIZABLE. "Which uses a version column?" → optimistic locking. "Seat state lives in Redis and Postgres?" → distributed lock.

### Hands-on terminal task ideas (graded on final state)

(Past quizzes used Docker/compose, git, migrations with flyway on `shop.db`, and pytest, so expect similar wrappers.)

1. **Add the right composite index via a migration.** For example, write `migrations/03_index_trains.up.sql` with `CREATE INDEX idx_trains_station_date ON trains (from_station, journey_date);` (and a `.down.sql` with `DROP INDEX …`), then apply it. **Checked:** the index exists with columns in the right order; `EXPLAIN` of the target query shows `Index Scan`/`Index Cond` (SQLite equivalent: `EXPLAIN QUERY PLAN` shows `SEARCH … USING INDEX` instead of `SCAN`).
2. **Fix an N+1 in code.** Rewrite the loop to one batched/JOIN query. **Checked:** tests pass; query count logged ≤ 2; the endpoint returns the same JSON.

7. **Create the index without blocking writes.** Use `CREATE INDEX CONCURRENTLY …` outside a transaction. **Checked:** the index exists and is valid.
