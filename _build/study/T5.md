## 1. One-paragraph summary

The lecture is about how code travels from your laptop to production servers **and how it gets back out when it breaks**. It opens with an incident: the food-delivery app **TiffinGo** ships v2.4 on a Friday dinner rush, checkout breaks, and they recover in 12 minutes by redeploying the old image (`tiffingo:2.3`). The main argument is: (1) **build the image once** and promote that same image through staging and production; (2) run the pipeline in a fixed order — test, build, **migrate before deploy**, deploy, check health — and keep migrations **compatible with the old code**, because old and new code run side by side during a deploy; (3) there are **three ways back** — revert the commit (minutes), redeploy the previous image (~1 minute), switch a feature flag off (seconds); (4) **code is reversible, data is not** — going back cannot undo a dropped/renamed column, deleted/overwritten rows, or messages already sent; (5) **feature flags** switch behaviour without a deploy, but they carry risks (Knight Capital lost ~$440M in 45 minutes from a reused flag name) and **flag debt**; (6) rollout strategies **blue-green** and **canary** limit the blast radius. Recovery time = detect + decide + act, and "most outages are long because nobody noticed."

## 3. Key concepts and definitions

- **CI/CD pipeline** — the automated route from `git push` to running servers. In the slides it sits above the app servers and "deploys ↓" into them.
  - **CI (continuous integration)**: every push/PR is built and tested automatically (T2L2). **Continuous delivery**: every change that passes is *ready* to go to production through the pipeline. **Continuous deployment**: every passing change goes to production automatically with no human click. *(the delivery vs deployment split is general knowledge; the slides just say "CI/CD pipeline". The course outline's Milestone 2 asks for "deployed to production by continuous delivery".)*
- **CI job / runner** — a fresh computer that starts empty, runs your list of steps, and is deleted when the job ends. Example steps: checkout, install, test, deploy. Nothing carries over between runs *(general knowledge: so state/caches must be explicit)*.
- **Exit code as gate** — each step's exit code is pass (0) or fail (non-zero). One failed step stops the job, so later steps (like deploy) never run.
- **Secrets** — come from the repository's settings (e.g. GitHub Actions secrets), never from the code.
- **Build once, promote the same image ("the same parcel")** — build one container image, tag it with the commit id (`tiffingo:3f9a2c1`), and run that exact image in staging and production. Rebuilding per environment ("repack") can give a different image, so what you tested is not what you shipped.
- **Image tag = commit id** — ties a running server back to the exact commit; also makes "redeploy the previous image" possible because old images still exist under their tags (`tiffingo:2.3`).
- **Environments** — staging (a production-like copy for checking) and production (real users). Same image in both.
- **Pipeline step order** — Test → Build image → Migrate DB → Deploy new code → Check health. Old code is still serving while the migration runs; during deploy old and new run side by side.
- **Migrate before deploy, compatible with old code** — because old code is still live when the migration runs (and during the deploy), the new schema must still work for the old code. A rename breaks this; use expand/contract (T3L2).
- **Health check (`/healthz`)** — an endpoint that reports the app is up and (in the demo) which version is running. Step 5 of the pipeline; also the basis for **readiness checks** that decide which servers get traffic.
- **Time to recover = detect + decide + act** — TiffinGo: 7 + 2 + 1 minutes. Detection is usually the biggest part ("Most outages are long because nobody noticed"), which is why alerts (errors above 2% for 5 minutes) matter. *(DORA calls this "time to restore service / MTTR" — general knowledge; DORA metrics are NOT on the slides.)*
- **Three ways back**:
  - **Revert the commit, then deploy** — makes a new commit that undoes the bad one; the whole pipeline (test, build, deploy) runs again → **minutes**.
  - **Redeploy the previous image** — point servers back at the old tag (`tiffingo:2.3`); nothing is rebuilt → **~1 minute**.
  - **Switch the feature off with a flag** — change a stored value; nothing is deployed → **seconds**. Only works if the feature was behind a flag.
- **Rollback vs roll-forward** *(general knowledge terms)*: rollback = go back to the previous version (redeploy old image / flag off); roll-forward = ship a new fix (revert commit is technically a roll-forward: a *new* commit goes through the pipeline). The slides call all three "ways back".
- **Code is reversible, data is not** — going back cannot undo a dropped/renamed column, deleted/overwritten rows, or sent messages (SMS/email/push like "Your group order is on the way!"). Same idea as T3L2: a down migration re-adds a column but fills it with NULL; only a backup brings values back.
- **Feature flag** — "an if-statement whose condition lives outside the code" (in a DB table or a flag service). Change the stored value → behaviour changes, no deploy. Lets you separate *deploy* (code is on servers) from *release* (users see the feature). *(the deploy-vs-release wording is general knowledge; the idea is on the slide.)*
- **Kill switch** — on/off for everyone. Example: turn off "split the bill".
- **Percentage rollout** — on for 10%, then 50%, then 100% of users. Must use `hash(user_id) % 100 < 10` so the **same users** stay in the group on every request (sticky). `random() < 0.1` would flip a user in and out on each request.
- **Targeted flag** — on for a chosen group first, e.g. one city, Pune.
- **Flag read latency trade-off** — read every request = instant change, DB hit on every request; cache 30 s = 1 read per 30 s, change takes up to 30 s; cache 5 min = very few reads, change takes up to 5 min. "Choose the delay you can live with."
- **Flag debt** — old flags and dead code paths pile up and become dangerous (Knight Capital). Rule: every flag has an owner and a removal date; at 100% rollout, delete the flag and the old code path.
- **Flag services** (AWARE) — hosted flag systems instead of your own table *(general knowledge examples: LaunchDarkly, Unleash, Flagsmith, GrowthBook)*.
- **Blue-green** — run new (green/v2.5) beside old (blue/v2.4, "kept warm"), switch all traffic at once at the load balancer; switch back at once if bad.
- **Canary** — send 5% of traffic to new, watch errors, grow only if healthy (95/5 split).
- **Readiness checks** — in both blue-green and canary, they decide which servers get traffic (a server that is not ready gets none).
- **Rolling deploy** *(general knowledge; the slide just says "During step 4, old and new code run side by side", and T3L2 says "Rolling deployments create mixed versions")* — replace servers a few at a time, so old and new versions serve together for a while.

## 5. Decision rules and trade-offs

**Which way back?**
| Situation | Best way back | Why |
|---|---|---|
| Bad feature is behind a flag | **Flag off** | Seconds; no deploy; the rest of the release stays. |
| Bad release, no flag, schema still compatible with old code | **Redeploy previous image** (e.g. `tiffingo:2.3`) | ~1 min; nothing rebuilt; the old image is the exact thing that ran before. |
| You want the bad change gone from `main` for good / no previous image available | **Revert the commit, then deploy** | Minutes (pipeline reruns), but history and the next build are clean. *(general knowledge: usually done after the quick fix, too.)* |
| The release ran a **breaking migration** (dropped/renamed column) | Redeploying old code **does not help** — old code expects the old schema (TiffinGo v2.3 fails). Need a roll-forward fix or data restore from backup. | Data is not reversible. |

- Speed order: **flag (seconds) < previous image (~1 min) < revert + pipeline (minutes)**.
- **"Which is unavailable once the schema has already changed?"** (outline wording) → **redeploying the previous artifact** (and reverting the commit, which also brings back old code) cannot work if the old code needs a column that is gone. The flag still works only if the new code behind the flag-off path doesn't need the old column *(inference)*. Safest answer: going back in code does not restore schema/data, so make migrations backward compatible in the first place.

**Migrations in the pipeline**
- Migrate **before** deploy (step 3 before step 4), because new code needs the new schema when it starts.
- But old code is still serving during and after the migration → **the migration must be compatible with the old code** (additive: add a column/table; never rename/drop in the same release).
- **Rename a column that live code depends on (slide 11 discussion)** — expand/contract from T3L2, as separate deploys:
  1. Migration: **add** the new column (`order_items`) — expand. (Old code ignores it.)
  2. Deploy code that **writes both** columns.
  3. **Backfill** old rows in batches.
  4. Deploy code that **reads the new column**, still writes both. (Rollback to step-2 code is still safe.)
  5. Deploy code that reads/writes **only** the new column (stop writing old).
  6. Migration: **drop** the old column — **contract**. ← **the irreversible point**. After this, no previous image that reads the old column can run, and the old column's data is gone.
  - (Quiz 2A Q11 tested exactly this: "Add full_name. Deploy code that writes both columns. Backfill … Deploy code that reads full_name and still writes both. Drop user_name once nothing uses it.")

**Flag read strategy**: fresh reads = instant changes but DB load on every request; caching = fewer reads but delay up to the cache time (30 s, 5 min). Pick the delay you can tolerate for a kill switch.

**Percentage rollout**: use a deterministic hash of the user id so a user gets a consistent experience; random per request gives flicker (button appears and disappears) and makes errors hard to attribute.

**Blue-green vs canary**
- Blue-green: all-or-nothing switch; instant switch back because old is kept warm; costs double capacity during the switch *(general knowledge)*; all users hit the new version at once.
- Canary: small blast radius (5%), real-traffic check, grow only if healthy; slower; old and new run together, so needs compatible schema *(general knowledge, but follows from "side by side")*.
- Both rely on **readiness checks** to decide which servers get traffic.

**Flags hygiene**: owner + removal date per flag; delete flag and old path at 100%; **never reuse an old flag name** (Knight Capital); make sure **every server** got the new code (1 of 8 missed → disaster).

**Detection**: shorten "detect" with alerts on error rate (e.g. >2% for 5 min) and health checks; it was 7 of the 10 minutes in TiffinGo.

## 6. Commands, config and code shown

Flag code (slide 18), exactly:
```js
1   const flags = await getFlags();   // read from a table or a flag service
2   if (flags.group_order) {
3       showGroupOrderButton();
4   }
```
- Line 1: fetch current flag values at runtime from outside the code (DB table or flag service). `await` = it's a network/DB read (hence the caching trade-off on slide 20).
- Line 2: the condition is the stored value of flag `group_order`.
- Line 3: only show the new feature when the flag is on. Turning the stored value off hides it on the next read — no deploy.

Percentage rollout rule (slide 19):
```
hash(user_id) % 100 < 10      ✓ same 10% of users every request (sticky)
random() < 0.1                ✗ a different random 10% on every request
```
- `hash(user_id) % 100` maps each user to a fixed bucket 0–99; `< 10` = buckets 0–9 = 10%. Raising to `< 50` keeps the first 10% in and adds more.

Image tags (slides 4, 9):
- `tiffingo:3f9a2c1` — image named `tiffingo`, tagged with commit id `3f9a2c1`.
- `tiffingo:2.3` — previous version image redeployed to recover.
- Health endpoint: `/healthz` — reports the running version in the demo.

No pipeline YAML is on the T5 slides. Related YAML from T2L2 (for hands-on tasks):
```yaml
name: CI
on: { pull_request: { branches: [main] }, push: { branches: [main] } }
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
      - name: Install dependencies
        run: <INSTALL_COMMAND>
      - { name: Run unit tests, run: <UNIT_TEST_COMMAND> }
      - { name: Build, run: <BUILD_COMMAND> }
```
"Any step exiting non-zero fails the job."

Likely commands for "three ways back" *(general knowledge — check against the demo-script brief)*:
```bash
git revert <bad-sha>                 # new commit that undoes <bad-sha>; history kept; then push → pipeline runs
git revert --no-edit HEAD            # revert the last commit without opening an editor
docker build -t tiffingo:$(git rev-parse --short HEAD) .   # build once, tag with commit id
docker tag tiffingo:3f9a2c1 tiffingo:staging               # promote same image (retag, don't rebuild)
docker rm -f web && docker run -d --name web -p 8080:3000 tiffingo:2.3   # redeploy previous image
curl -s http://localhost:8080/healthz                      # check which version is running
# flag off: edit the stored value, e.g. flags.json {"group_order": false} or
#   UPDATE flags SET enabled = false WHERE name = 'split_the_bill';
```
- `git revert` ≠ `git reset`: revert adds a new commit (safe on shared `main`); reset rewrites history *(T0/T2 knowledge)*.
- Secrets in GitHub Actions: `${{ secrets.NAME }}` from repo settings *(general knowledge)*.

## 7. Common misconceptions / distractor traps

1. "Redeploying the old version undoes the migration / the database brings the old column back." **False** — code rollback never touches the schema (slide 6, option C).
2. "Rollback always restores the system to how it was." False — data changes, deleted/overwritten rows and **sent messages** stay.
3. "A down migration restores the old values." False (T3L2 / Quiz 2A Q9) — it recreates the column filled with NULL; only a backup restores values.
4. "Reverting the commit is the fastest way back." False — it reruns the whole pipeline (minutes). Flag = seconds, previous image ≈ 1 minute.
5. "Rebuild the image for production from the same commit — it's the same thing." False — rebuilding can give a different image (different base image, dependencies). Build once, promote.
6. "Tag images `latest`" vs commit id — the slide says tag with the commit id so you know exactly what runs and can go back *(the `latest` point is general knowledge)*.
7. "Deploy first, then migrate." Wrong order — migrate (step 3) before deploy (step 4); but the migration must still work with the *old* code.
8. "During a deploy only one version is live." False — old and new run side by side in step 4 (and old code serves during step 3).
9. "Renaming a column in one migration with the new code is fine." False — breaks the old code still running (and breaks rollback).
10. "Percentage rollout = `random() < 0.1`." False — use `hash(user_id) % 100 < 10` for sticky assignment.
11. "Flag changes are always instant." Depends — if cached for 30 s / 5 min, the change can take up to that long.
12. "Flags are free; leave them in." False — flag debt; owner + removal date; delete flag and old code path at 100%.
13. Knight Capital: "caused by a bad flag service / a test failure / a hack." The slide's causes: **reused old flag name** + **one of eight servers didn't get new code** → old retired code ran. $440M in **45** minutes (not hours).
14. "Secrets can go in the repo if it is private / in the workflow file." False — from repository settings, never in code.
15. "The CI runner keeps files from the last run." False — fresh, empty, deleted at end.
16. "A failed step just logs a warning and the job continues." False — one failure stops the job (unless someone adds `continue-on-error`, which hides failures — Quiz 2A Q3).
17. "Blue-green sends 5% first." No — that's canary. Blue-green switches **all at once** and switches back at once.
18. "Canary/blue-green don't need health checks." False — readiness checks decide which servers get traffic.
19. "Outages are long because fixing is slow." The slide says they are long because **nobody noticed** (detect = 7 of 10 min).
20. "A flag fixes the damage already done." No — turning off "split the bill" stops new wrong charges; charges already made are data.

## 8. Likely quiz angles

### MCQ scenario ideas (choose all that apply style)
1. **TiffinGo rename**: v2.4 renamed `items`→`order_items`; you redeploy `tiffingo:2.3`. True: checkout still fails; the DB keeps `order_items`; redeploying code does not change schema. False: DB restores `items`; checkout recovers.
2. **Fastest safe fix**: a feature behind a flag misbehaves → switch flag off (seconds, no deploy). Distractors: revert + deploy, redeploy previous image, hotfix.
3. **Rank by speed**: flag off < redeploy previous image < revert commit and run pipeline; with reasons (nothing deployed / nothing rebuilt / pipeline reruns).
4. **Build once**: a team builds separately for staging and prod from the same commit; prod breaks though staging passed. Which are true? Rebuilding can give a different image; tag with commit id and promote the same image; staging passing doesn't prove the prod image.
5. **Pipeline order**: pick the correct order (test → build → migrate → deploy → health) and which statements hold (old code serves during the migration; migration must be old-code compatible; old and new run side by side during deploy).
6. **Rename sequence + irreversible point**: choose the safe expand/contract sequence; identify the drop-old-column step as irreversible.
7. **Time to recover**: given a timeline (bug at 14:00, alert 14:12, decision 14:15, fixed 14:16), compute detect/decide/act and identify the biggest lever (better alerting).
8. **What rollback can't undo**: pick all — dropped column, overwritten rows, sent SMS/email; NOT the code version, NOT the container image.
9. **Percentage rollout code**: which implementation keeps a user consistently in the 10% group? `hash(user_id) % 100 < 10`. And: raising to `< 50` keeps the original 10% in.
10. **Flag caching**: flags cached 5 minutes; you flip the kill switch; some users still see the bug for up to 5 minutes; trade-off is fewer DB reads.
11. **Knight Capital**: which practices would have prevented it? Don't reuse flag names; delete retired code/flags (flag debt); verify all servers got the new code (one of eight missed); have a kill switch. Distractor: "add more unit tests" alone.
12. **Blue-green vs canary**: "send 5% and grow only if healthy" = canary; "keep old warm, switch all at once, switch back at once" = blue-green; both use readiness checks.
13. **CI runner facts**: fresh, empty, deleted after; exit code decides; one failure stops the job; secrets from repository settings.
14. **Flag debt policy**: owner + removal date; at 100% delete the flag and old code path.

### Plausible hands-on terminal tasks (graded on final state)
1. **Redeploy the previous image**: container `web` runs `app:2.4` and `/healthz` reports 2.4 with errors. Task: run `app:2.3` with the same name/ports. *Checked*: a container from `app:2.3` running, publishing the same port; `curl /healthz` returns version 2.3; no `app:2.4` container running.
2. **Flip a feature flag**: `flags.json` (or a SQLite `flags` table) has `"split_the_bill": true`. Task: turn it off without changing code or redeploying. *Checked*: stored value is false; app code files unchanged; container not restarted (same container ID/start time).
3. **Revert a bad commit**: `main` has a bad commit "Add group order"; task: undo it without rewriting history. *Checked*: a new commit whose message starts with `Revert "…"`; the bad commit still in history (not reset); file content equals pre-bad state; tests pass.
4. **Build once, tag with commit id**: build image tagged `shop:<short-sha>` (from `git rev-parse --short HEAD`) and retag the same image as `shop:staging` / `shop:prod`. *Checked*: tags exist and share the same image ID (not two builds).
5. **Fix a pipeline YAML**: reorder steps so tests run before build, migrate before deploy, health check last; or remove a hard-coded password and use `${{ secrets.DB_PASSWORD }}`; or remove `continue-on-error: true`. *Checked*: step order in the file, no secret literal in the repo, secret referenced from settings.
6. **Ship a rename safely (expand step only)**: write migration `03_add_order_items.up.sql` that **adds** `order_items` and backfills from `items`, without dropping `items`; apply it (flyway/sqlite). *Checked*: both columns exist; `order_items` filled for all rows (`count(*) WHERE order_items IS NULL = 0`); `items` still present; old query still works.
7. **Percentage rollout fix**: replace `random() < 0.1` with a deterministic hash of `user_id` in a small function; tests check the same user gets the same answer across calls and ≈10% of 1000 ids are enabled.
8. **Measure rollback time**: time the redeploy (`time docker run …` / until `/healthz` reports the old version) and write it to a file. *Checked*: file exists with a number; old version running.
