Topic 1

Shell basics: files, grep, pipes and redirects

Move around, create/move/copy/delete files, and filter log files into report files with grep, | , > and >> without guessing.

Mental model

You are always standing in one folder (pwd). Every path you type is either relative to that folder or starts from /. Commands are small tools that read lines of text and write lines of text to the screen. | plugs one tool's output into the next tool's input. > and >> send the final output into a file instead of the screen. The shell sets up all the plumbing (opens files, expands *) before any command runs, which explains most of the surprises below.

The quiz terminal starts in the task's folder. Before anything else, find out where you are and what is there. A path without a leading / is relative: it starts from the current folder.

Trap: mv into a folder that doesn't exist

Trap: rm -r is forever

Read the line before Enter. rm -r tmp / (stray space) tries to delete the whole disk. Use ls with the same pattern first to see what would be hit.

echo, quotes, >, >>, < and |

Every command writes to the screen ("standard output"). The shell can redirect that stream:

SymbolMeaning
cmd > fwrite output to file f. Creates f, or wipes it first if it exists
cmd >> fadd output to the end of f (creates it if missing). Keeps what was there
cmd < ffeed file f as the input
cmd1 | cmd2pipe: cmd1's output becomes cmd2's input. No file in between
echo "text" > fwrite one line. echo just prints its arguments + a newline
$ echo "first line" > hello.txt
$ echo "second line" >> hello.txt
$ cat hello.txt
first line
second line
$ echo "oops" > hello.txt     # > starts from empty again
$ cat hello.txt
oops

Quoting. The shell splits your line on spaces and treats | > < * $ as special. Put patterns in single quotes ('method=(GET|DELETE)') so the shell passes them to grep untouched. Double quotes also protect spaces and | but still expand $var.

Why "redirect into a missing folder" fails

> can create a file, never a folder. The shell opens reports/orders-500.txt before grep starts; if reports doesn't exist you get bash: reports/orders-500.txt: No such file or directory and grep never runs. Fix: mkdir reports (or mkdir -p) first.

Trap: never redirect into the file you are reading

sort visitors.txt > visitors.txt or grep -v x app.log > app.log leaves the file empty: the shell wipes the > target before the command reads it. Write to a new file. (In a "don't change the log" task this loses all marks.)

grep: keep only matching lines

grep PATTERN FILE... prints every line of the file(s) that contains PATTERN. It never changes the file. With no file name it reads its input (the pipe, or the keyboard, which looks like a hang: Ctrl+C).

grep -h 'status=500' logs/access.log.1 logs/access.log > reports/x.txt
  1. the filter command
  2. option: hide file names
  3. the pattern, quoted, as exact as possible
  4. files, read in the order you list them
  5. save the result instead of printing it

Trap: the pattern is a substring

grep 500 also matches 3500ms and user=500. grep error misses ERROR. Match the whole field: 'status=500', 'level=ERROR', -i when case varies, -w for whole words.

AND, OR and regex basics

AND = two greps in a pipe. The first reads the file; the second has no file, so it filters what comes down the pipe. OR = one grep -E 'a|b'.

$ grep 'service=orders' logs/access.log | grep 'status=500'
2026-09-28T09:03:29 service=orders method=POST status=500 2987ms
2026-09-28T09:06:48 service=orders method=GET status=500 3104ms
$ grep -E 'level=(WARN|ERROR)' logs/app.log      # WARN or ERROR
Trap: the Quiz 1 hint grep P1 file1 | grep P2 file2 > file3

If the second grep is given a file, it reads that file and ignores the pipe completely. So grep service=orders access.log.1 | grep status=500 access.log just prints today's status=500 lines (including other services) and yesterday is lost. In an AND chain only the first grep gets file names. To combine two files, either list both in the first grep (grep -h P1 f1 f2 | grep P2) or run one chain per file with > then >>.

Regex pieceMeansExample
.any one character'status=5..' = any 5xx
.*anything (zero or more chars)'service=orders.*status=500' = AND in one grep, if the order is fixed
^start of line'^2026-09-27' = lines from that day
$end of line'ms$'
[0-9]one digit'status=5[0-9][0-9]'
{4,} (needs -E)4 or more of the previous thing-E '[0-9]{4,}ms' = 1000ms or more
a|b (needs -E)a or b-E 'GET|DELETE'
Trap: forgetting -E or the quotes

grep 'GET|DELETE' (no -E) finds nothing: in basic grep | is a plain character. grep -E GET|DELETE f (no quotes): the shell makes a pipe, prints DELETE: command not found, and grep waits for keyboard input. Ctrl+C.

Quiz 1 Q18 step by step (order matters)

Task: put every service=orders + status=500 line from yesterday's logs/access.log.1 then today's logs/access.log into reports/orders-500.txt, then move access.log.1 into a new logs/archive.

$ mkdir reports                                  # 1. > can't create folders
$ grep 'service=orders' logs/access.log.1 | grep 'status=500' > reports/orders-500.txt    # 2. yesterday, >
$ grep 'service=orders' logs/access.log | grep 'status=500' >> reports/orders-500.txt    # 3. today, >>
$ cat reports/orders-500.txt
2026-09-27T10:02:17 service=orders method=POST status=500 3021ms
2026-09-28T09:03:29 service=orders method=POST status=500 2987ms
2026-09-28T09:06:48 service=orders method=GET status=500 3104ms
$ mkdir logs/archive                             # 4. mv won't create it
$ mv logs/access.log.1 logs/archive/              # 5. grep FIRST, move LAST
$ ls -R logs
Why this order

Grep before mv: once the log is moved, logs/access.log.1 no longer exists and grep says No such file or directory. > for the first write (start clean), >> for the second (keep yesterday on top). One-liner alternative: grep -h 'service=orders' logs/access.log.1 logs/access.log | grep 'status=500' > reports/orders-500.txt.

Common errors and what they mean

bash: reports/orders-500.txt: No such file or directory

Means: a folder in the path doesn't exist (here reports). Same for grep: logs/x.log: No such file or directory: wrong name, wrong folder, or you already moved it.

Fix: ls, pwd, use Tab completion; mkdir -p the folder.

rm: cannot remove 'tmp': Is a directory
grep: logs: Is a directory

Means: you gave a folder to a command that wants a file.

Fix: rm -r tmp; for grep name the files (logs/*.log) or use grep -r.

mv: cannot move 'a.log' to 'logs/archive/': Not a directory

Means: the destination folder doesn't exist (the trailing / protected you from a silent rename).

Fix: mkdir -p logs/archive then repeat (up-arrow).

mkdir: cannot create directory 'project/src/utils': No such file or directory

Means: parent folders are missing.

Fix: mkdir -p project/src/utils.

bash: ./run.sh: Permission denied

Means: the file isn't executable, or you can't write to that place.

Fix: bash run.sh or chmod +x run.sh; write inside your own folders.

bash: DELETE: command not found
bash: gerp: command not found

Means: a typo, or an unquoted | split your pattern into a second "command".

Fix: check spelling; put patterns in single quotes.

(nothing happens, no prompt)

Means: the command is waiting for input: usually grep/cat/sort with no file name and no pipe.

Fix: Ctrl+C, then add the file name.

logs/access.log.1 (yesterday) and logs/access.log (today). Create reports/no-health.txt with every line that is not service=health, yesterday first. Then move access.log.1 into a new logs/old/.

Twist Which users hit the API most?

logs/access.log lines contain user=NAME somewhere. Create reports/top-users.txt: the 3 users with the most requests, biggest first, as COUNT user=NAME.

Quiz-style Validate AI code: does the function exist?

A generated pull request calls send_invoice(...). In the repo folder src (many sub-folders), save every line that mentions send_invoice as path:line:text, sorted, into reports/invoice.txt. Then save just the number of files under src that contain TODO into reports/todo-files.txt.

Show answer
$ mkdir -p reports
$ grep -rn 'send_invoice' src | sort > reports/invoice.txt
$ grep -rl 'TODO' src | wc -l > reports/todo-files.txt
$ grep -r 'def send_invoice' src        # no output = it is never defined: reject the PR

-r walks every sub-folder, -n adds line numbers, -l prints each matching file once (so wc -l counts files, not lines). sort because -r's order isn't guaranteed. Trap: grep -rc TODO src prints one count per file (src/a.py:2...), not one number.

Twist Keep only the errors of a build, log a failure

./build.sh prints progress on stdout and problems on stderr, and exits non-zero when it fails. Run it so that the screen stays quiet, the progress is thrown away, and only the problems go into build-errors.txt. In the same command line, append <today> build failed to build.log only if the build failed (date from date +%F).

Show answer
$ chmod +x build.sh                 # only if you get "Permission denied"
$ ./build.sh > /dev/null 2> build-errors.txt || echo "$(date +%F) build failed" >> build.log
$ echo $?                          # exit code of the LAST command on that line

> is stream 1 (stdout), 2> is stream 2 (stderr), /dev/null throws output away. a || b runs b only when a failed (exit code not 0); a && b only when it succeeded. $(date +%F) is replaced by e.g. 2026-10-28, but only inside double quotes. Both streams into one file: > all.txt 2>&1 (2>&1 after the file).

Twist Sum and maximum from a CSV with a header

payments.csv starts with the header id,amount,currency, then lines like 17,250,GBP. Save the total amount of the GBP payments into gbp-total.txt, and the whole line of the single biggest payment (any currency) into biggest.txt.

Show answer
$ awk -F, '$3 == "GBP" { s += $2 } END { print s }' payments.csv > gbp-total.txt
$ tail -n +2 payments.csv | sort -t, -k2 -rn | head -n 1 > biggest.txt

awk -F, splits on commas, $3 == "GBP" compares the whole field (a grep for GBP could also hit an id or note), END prints once at the end. tail -n +2 skips the header; sort -t, -k2 -rn = split on commas, sort by field 2, as numbers, biggest first. Without awk: grep ',GBP$' payments.csv | cut -d, -f2 | paste -sd+ | bc.

Quiz-style Count, record and delete month-old logs

Under srv (many sub-folders) find every .log file not modified for more than 30 days. Save their paths, sorted, into old.txt and see how many there are on screen, in one command. Then delete exactly those files.

Show answer
$ find srv -type f -name '*.log' -mtime +30 | sort | tee old.txt | wc -l
3
$ cat old.txt                                         # read the list before deleting
$ find srv -type f -name '*.log' -mtime +30 -delete

tee FILE writes its input to the file and passes it on down the pipe (a T-junction), so you save the list and count it at once. -mtime +30 = older than 30 days (-30 = newer), -size +1M works the same way for size. -type f skips folders named like logs. Moving instead of deleting: -exec mv {} archive/ \;.

Topic 2

Git basics: local work, branches, merging

Move changes between the working directory, staging area and local repo on purpose, make branches, merge them, and fix a conflict without panicking.

Mental model

Your work lives in four places: the Working Directory (files on disk), the Staging Area (what the next commit will contain), the Local Repository (saved commits) and the Remote (the team's copy). git add copies working dir to staging, git commit copies staging to the local repo, git push sends it to the remote. Every commit is a snapshot plus a pointer to its parent. A branch is only a label that points at one commit and moves forward when you commit. git status compares the first three places, never the remote.

git status: read every section

Run git status before and after every command. Each heading tells you where a file is.

$ git status
On branch main                                  # the branch HEAD points at
Changes to be committed:                        # STAGING differs from LAST COMMIT
  (use "git restore --staged <file>..." to unstage)
        modified:   config.py
        new file:   routes/webhooks.py
Changes not staged for commit:                  # WORKING DIR differs from STAGING

Topic 3

Git remotes, history and recovery

Push, fetch and pull with confidence, fix "rejected" and "diverged", find lost commits with the reflog, and rewrite or undo history (rebase, cherry-pick, reset, revert) without losing anyone's work.

Mental model

Four locations: working directory → staging area → local repository → remote repository. git status only compares the first three, plus your last downloaded copy of the remote.

A commit is a snapshot + the hash of its parent. Its id is a hash of all of that, so changing anything (even just the parent) makes a new commit with a new id.

A branch is a pointer: a tiny file holding one hash. origin/main is also a pointer, your local note of "where main was on origin last time I talked to it". HEAD says which branch (or bare commit) you're on.

Almost every command here just moves pointers or adds commits. Commits that nothing points to aren't gone yet: the reflog still remembers them.

Remotes: origin is just a name

A remote is just another repository (GitHub hosts the same format you have locally). origin is not special: it's the nickname git gives the first remote (on git clone), or the one you add yourself. The remote only knows what you've pushed.

In the labs, the "GitHub" is a bare repository remote.git in the same folder: a repository with no working directory (just what's normally inside .git). You can't edit files in it; you only push to it and fetch from it. Make one with git init --bare remote.git.

cherry-pick: copy one commit here

git cherry-pick <hash> takes the change that commit made (its diff against its parent) and applies it as a new commit on your current branch. New parent → new hash. The original commit and its branch stay as they are. Typical use: a hotfix made on one branch that main needs right now.

$ git restore --staged debug.log   # unstage the file that shouldn't be in it
$ git commit -m "Add discount"      # recommit, fixed

Why

Reset on a pushed commit moves your main behind origin's: the push is rejected, and forcing it rewrites history everyone else already has. Rule: not pushed → reset is fine. Pushed → revert.

Trap

git revert HEAD undoes the latest commit, which may not be the bad one. Look up the hash with git log --oneline | grep. Without --no-edit, revert opens an editor for the message.

Topic 4

Docker: build, run, publish, persist

Build an image from a Dockerfile, run it with the right ports and volumes, and debug it when curl gets nothing.

Mental model

Image = an immutable, tagged stack of read-only layers plus a default command (a recipe that is already cooked). Container = a running instance of an image: ordinary Linux processes, plus their own namespaces, cgroup limits and a thin writable layer on top. Volume = Docker-managed storage with its own lifecycle: it outlives any container. Namespaces = what a process can see (own PIDs, own filesystem, own network). cgroups = how much it can use (CPU, memory). All containers share the host's kernel. Every command in this topic is one of: make an image (build), make a container (run), look at it (ps, logs, exec, inspect), or remove things (stop, rm, image rm, volume rm).

docker build: the trailing dot

In Quiz 2 Q14, docker build -t counter:1.0 (no dot) scored 0. The dot is not decoration. It is the build context: the folder Docker packs up and sends to the builder. Every COPY in the Dockerfile copies from the context. No context, no build. Docker also looks for the file called Dockerfile inside the context unless you say otherwise with -f.

  2. -t name:tag = the image's name and version. Name must be lowercase. No tag means :latest.
  3. . = build context = "this folder" (the one you are standing in). Required. It is the one argument the error message talks about.

  4. the context is still needed: -f picks the recipe, . gives the ingredients

Dockerfile instructions and the layer cache

A Dockerfile is a list of steps. Most steps create a layer. Layers are read-only and shared: 100 containers from one image use the same layers on disk (copy-on-write); each container only adds its own thin writable layer.

.dockerignore lists what to leave out of the build context, like .gitignore. Typical: node_modules, .git, .env, data. Keeps secrets out of the image, keeps the context small, and stops your laptop's node_modules from overwriting the one built inside the image by COPY . ..

docker run: options before the image, command after

docker run = create a new container from an image and start it. Each run makes a new container with a fresh, empty writable layer.

docker run -d -p 8080:3000 -v counter-data:/data --name counter counter:1.0
  1. create + start a new container
  2. -d = detached: run in the background, print the container id, give the terminal back
  3. -p HOST:CONTAINER = publish: traffic to host port 8080 goes to container port 3000
  4. -v VOLUME:/path = mount the named volume counter-data at /data inside
  5. --name = a name to use instead of the id (must be unique among all containers)
  6. the image. Everything after this word is the command to run inside the container, replacing CMD.
Trap: options after the image

docker run -d counter:1.0 -p 8080:3000 -v counter-data:/data does not publish anything. -p 8080:3000 -v ... becomes the container's command. With node images it runs node -p 8080:3000 -v ..., prints the Node version and exits: docker ps is empty, docker ps -a says Exited (0), docker logs shows v24.x.x. With alpine: exec: "-p": executable file not found in $PATH. Rule: docker run [options] IMAGE [command].

Topic 5

Testing with pytest, the failing-test-then-fix workflow, and reading CI config

Run and select tests, write boundary tests that catch real bugs, commit "failing test" then "fix" in exactly the right order, undo a wrong commit, and read a GitHub Actions workflow.

Mental model

A test is a claim you can run: set up (Arrange), call the code (Act), check the result (Assert). No assert = no claim. A bug fix is two commits: commit 1 adds a test that is red on the old code (proof the bug exists), commit 2 is the smallest change that makes it green. The grader looks at those commits by position: HEAD~1 = your test commit, HEAD = your fix. CI just reruns the same tests on a clean machine; branch protection is what turns a red CI run into a blocked merge.

Writing tests: assert, boundaries, pytest.raises

A pytest test is just a function named test_... that uses plain assert. Name it like a specification: the name should say what broke when it goes red.

# test_validate.py
import pytest
from validate import is_valid_length

def test_accepts_exactly_eight_characters():   # boundary, at the limit
    # Arrange
    password = "abcdefgh"
    # Act
    result = is_valid_length(password)
    # Assert
    assert result is True

def test_rejects_seven_characters():           # boundary, one below
    assert is_valid_length("abcdefg") is False

def test_none_is_rejected():                   # invalid input -> must raise
    with pytest.raises(TypeError):
        is_valid_length(None)
with pytest.raises(ValueError): is_adult(-1)
  1. passes only if the indented block raises ValueError (or a subclass); otherwise the test fails with DID NOT RAISE
  2. the call that should blow up goes inside the block

Which values to test for a rule "at least N": N-1 (last bad), N (first good), one normal value, one invalid input. 3 and 20 are useless for the edge: they give the same answer for >= 8, > 8 and >= 7.

A test with no assert always passes unless the code crashes:

def test_ten_percent_off_200():
    result = apply_discount(200, 10)
    print("result is", result)      # green, even though result is 190, not 180

Also weak: assert result (any non-zero number passes) and assert status != 201 (a 500 passes). Assert the exact value.

Trap

Two test functions with the same name in one file: Python keeps only the last one, so the first test silently disappears. pytest -v shows the real list.

Failed: DID NOT RAISE <class 'ValueError'>

Means: the code inside with pytest.raises(...) returned normally.

Fix: either the code has a bug (good, you found it) or you put the wrong call / wrong exception type in the block.

NameError: name 'pytest' is not defined

Fix: add import pytest at the top of the test file (only needed for pytest.raises etc.; plain asserts don't need it).

Topic 6

Database migrations with Flyway + sqlite3, and migration files in git

Write numbered migration files, apply them with flyway migrate, read the history table with sqlite3, and recover from checksum mismatches, hand-run SQL and version collisions.

Mental model

Files in git, memory in the database. A migration is a file of SQL (03_add_currency.up.sql). Saving it changes nothing. The runner (Flyway) connects to the database, reads the history table (flyway_schema_history, one row per applied migration), runs every file that has no row yet, in version order, and inserts a row for each. The history is a log: append-only (never edit an applied file), ordered (03 assumes 01 and 02 ran), checksum-verified (edit an applied file and Flyway stops). Anything done by hand is invisible to it.

Drill What a blob knows

A repo has src/app.py and backup/app.py, and the two files have exactly the same bytes. You then rename src/app.py to src/main.py and change nothing else. Which statements are true? Choose all that apply.

  3. The rename creates a new blob, because the name is part of the blob.
  4. The file name lives in the tree object that points to the blob.
Show answer

A, B, D. A blob's id is a hash of its content alone, so identical bytes give the same id, and Git never stores the same bytes twice. Names live one level up, in a tree (100644 blob 3f9a1c2 app.py). Drill What is inside a commit object?

  4. Author, committer, timestamps and the message
  5. The name of the branch it was made on

A, B, D. A commit is tree + parent + author/committer + message. It is a full snapshot, not a diff, so C is wrong: git diff works out the changes each time you ask. Branch names are not stored in commits (E). A branch is a separate file that points to a commit.

A. Myers's cost grows with the size of the edit script d. It follows the free diagonals (matching lines) and never walks one twice. Its memory is O(m+n). Git stores snapshots, not diffs (B). Rapid-fire facts

Read these the night before and again just before the quiz. Each one has decided a multiple-choice option before.

Git internals and history

  • Git = a DAG of content-addressed objects: blob, tree, commit, tag
  • Object id = hash of its content. Change 1 byte and you get a new object with a new id
  • A blob has no name. The tree holds names and modes
  • A commit = tree + parent(s) + author/committer + message. It is a snapshot, not a diff
  • A branch = a small file holding one hash. Committing overwrites only that file
  • Change one commit and it and every later commit get new IDs
  • Amend or rebase = new commits. The old ones stay (reflog) until gc's grace period
  • Myers = shortest edit script, O((m+n)·d) time, O(m+n) memory, git's default
  • On a tie, Myers prefers delete over insert
  • 3-way merge = diff(base,ours) + diff(base,theirs). Same region on both sides = conflict
  • Merge = accurate ledger (2-parent commit). Rebase = readable story (new hashes, straight line)
  • Squash = rebase with the commits collapsed into one
  • Rebase moves only the branch you're on. main stays put
  • git branch -d refuses unmerged work. -D forces it

Remotes, undo and recovery

  • Four locations: working dir, staging, local repo, remote
  • git status never contacts the remote. "ahead/behind" uses the last fetch
  • fetch = download + move origin/main only. pull = fetch + integrate
  • Diverged + plain git pull = "Need to specify how to reconcile". Use --no-rebase or --rebase
  • Rejected push: integrate first. Never --force on shared main
  • restore f = staged copy goes to the working dir. restore --staged f = unstage
  • reset --soft keeps staged, --mixed keeps files, --hard discards
  • Pushed bad commit: git revert (adds an undo commit)
  • Lost commit: git reflog, then git branch name <hash>
  • After switching away, HEAD@{1} = where HEAD was just before
  • Rebased your own pushed branch: push --force-with-lease
  • commit -a skips untracked files. stash skips untracked unless -u
  • .gitignore ignores only untracked files. Use git rm --cached to stop tracking

Testing and CI

  • Arrange, Act, Assert. No assertion = no behavioural check
  • pytest passes a test with no assert if it doesn't raise
  • Cases: normal, boundary (just below and exactly on), invalid/missing, error
  • Unit = pure logic. Integration = real components + DB. E2E = browser journey
  • Pyramid: many unit, some integration, few E2E. It is a budget, not a law
  • Coverage = lines/branches/functions executed, not asserted
  • Mutation testing: a surviving mutant means the tests can't tell the change apart
  • Stub = canned value. Fake = working simplified version. Mock = records calls
  • Tests must be independent, clean up after themselves, and be deterministic (no uncontrolled clock or network)
  • Bug fix = commit 1 failing test (red), commit 2 fix (green)
  • CI = validate, build, test, report status on a change. CD = deliver/deploy
  • A failing step fails the job, and later steps are skipped
  • continue-on-error: true lets the job pass anyway
  • Gate = pull_request trigger + required status check in branch protection
  • Clean runner = only declared dependencies. Read the first meaningful error

Containers and Docker

  • Container = isolated process(es) on the shared host kernel. A VM has its own kernel
  • Namespaces = what you see (PID, mount, net, hostname, user)
  • cgroups = how much you use: over CPU = throttled, over memory = may be killed
  • Main process is PID 1 inside, with a different PID on the host
  • Image layers are read-only and shared (copy-on-write). Each container has its own writable layer
  • A changed input invalidates that step and all steps after it
  • Copy manifests, then install, then copy source. CMD only records metadata
  • COPY cache uses file contents, not timestamps. .dockerignore trims the context
  • npm ci installs exactly the lockfile and fails on a mismatch
  • EXPOSE documents only. -p host:container publishes
  • -p 127.0.0.1:8080:3000 = this machine only. Without the prefix = all interfaces
  • Server inside must listen on 0.0.0.0, not 127.0.0.1
  • stop/start keeps the writable layer. rm deletes it
  • A named volume outlives containers. Only the mounted path is kept
  • New image = new container (rm + run). restart reuses the old image

Database migrations

  • Code, schema and data change independently. Code is reversible, data often isn't
  • Auto-sync rename = drop + add an empty column. Prototype only
  • Runner: read history, run pending files in order, insert a history row, COMMIT
  • History = append-only, ordered, checksum-verified
  • Edited applied file = checksum mismatch, deploy stops before running anything
  • flyway repair fixes checksums and runs no SQL
  • Hand-run SQL = schema changed, no history row, migration still pending
  • Postgres DDL is transactional. Killed before COMMIT = it reruns cleanly
  • Error inside BEGIN: transaction aborted. COMMIT then rolls back
  • Without BEGIN each statement autocommits
  • ADD COLUMN needs ACCESS EXCLUSIVE. It waits for open readers, and later readers queue behind it
  • Locks are held until the transaction ends. lock_timeout limits only the wait
  • PG 11+: constant default = fast. Volatile default (clock_timestamp(), gen_random_uuid()) = full rewrite
  • Down migration can't restore deleted values, only a backup can
  • Expand, backfill, transition, contract. Irreversible at contract (drop)
  • Required column: nullable, writes supply it, batched backfill, CHECK NOT VALID, VALIDATE, SET NOT NULL
  • Use timestamp versions so two branches don't collide
  • PITR = physical base backup + archived WAL. A replica is not a backup. RPO = data loss, RTO = time

Architecture

  • Network call costs: partial failure, retries plus idempotency, distributed transactions, no debugger
  • Timeout = unknown outcome. Retry only idempotent calls, and send an idempotency key
  • 8 fallacies: reliable, zero latency, infinite bandwidth, secure, fixed topology, one admin, zero transport cost, homogeneous
  • Conway's Law: systems copy org communication. Microservices apply it in reverse

Method for any terminal task

The checker grades the final state: which branch you're on, where each branch points, how many commits there are, what is inside the files. It does not see your commands. So read the "What was checked" list first. That list is the real task.

A 6-step routine

  1. Read "What was checked" first. Turn each line into a goal, e.g. "main has 4 commits" or "branch X points at commit Y".
  2. Look before you act: pwd, ls, git status, git branch, git log --oneline --graph --all, docker ps -a.
  3. Predict the final state in one line, e.g. "after the merge, main = base + mine + theirs + merge commit = 4".
  4. One command at a time. Read each command's output before typing the next. Errors are usually explained in that output.
  5. Verify against the checks with the same look-commands as step 2. Count commits with git log --oneline | wc -l.
  6. Respect the "Stop" line. Don't push, delete or add commits that it forbids. An extra commit fails a commit-count check.

Look-commands to type before and after

$ git status                               # branch + staged/unstaged/untracked

$ git log --oneline --graph --all --decorate   # the whole history picture
$ git log --oneline | wc -l                # how many commits on this branch
